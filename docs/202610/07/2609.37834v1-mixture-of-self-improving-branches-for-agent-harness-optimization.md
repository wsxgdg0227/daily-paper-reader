## 摘要
Harness 优化为递归自我改进（RSI）提供了一个实用场景，其中智能体生成的修改通过执行反馈影响后续修改。近期工作如 Meta-Harness 通过迭代式代码生成与评估实现这一过程，但保留固定的开发集和提议策略。这些约束使演化沿单一搜索轨迹进行，增加了收敛到局部最优的风险。我们通过将搜索组织为具有演化开发子集和提议策略的分支，使改进过程本身具有自适应性。每个分支保留被其更多领先 harness 解决（相较其他分支的领先 harness）的开发案例，丢弃被所有分支中每个领先 harness 都解决的案例，并利用自身搜索历史修订其提议策略。为部署由此得到的互补 harness，我们提出一种路由器，在执行前为每个新输入选择一个基于开发集选出的分支头。在数学推理和智能体编程基准上，我们的系统相较 Meta-Harness 取得相对提升：奥赛级数学推理 34.8%，Terminal-Bench 2.0 11.6%，SWE-bench Lite 3.8%，且 harness 选择与路由器配置仅基于开发数据。这些结果表明，演化分支目标和提议策略可以产生互补的 harness，路由器无需访问测试结果即可结合其优势。

## Abstract
Harness optimization provides a practical setting for recursive self-improvement (RSI), where agent-generated modifications inform subsequent changes through execution feedback. Recent work such as Meta-Harness implements this process through iterative code generation and evaluation, but retains a fixed development set and proposal policy. These constraints channel evolution along a single search trajectory, increasing the risk of converging to a local optimum. We make the improvement process itself adaptive by organizing search into branches with evolving development subsets and proposal policies. Each branch retains development cases solved by more of its leading harnesses than by those of other branches, drops cases solved by every leading harness across all branches, and revises its proposal policy using its own search history. To deploy the resulting complementary harnesses, we propose a router to select one development-selected branch head for each new input before execution. Across mathematical reasoning and agentic coding benchmarks, our system achieves relative improvements over Meta-Harness of 34.8% on Olympiad-level mathematical reasoning, 11.6% on Terminal-Bench 2.0, and 3.8% on SWE-bench Lite, with harness selection and router configuration based solely on development data. These results show that evolving branch objectives and proposal policies can yield complementary harnesses whose strengths a router combines without access to test outcomes.

## 1. 核心问题与整体含义

- **研究背景**：LLM Agent 的能力不仅取决于底层模型，还取决于其外围 **harness**（检索、工具接口、控制流、验证与修正机制等）。Harness 优化因此成为递归自我改进（RSI）的实用场景：Agent 生成的修改通过执行反馈影响后续修改。
- **核心问题**：Meta-Harness 等已有方法通过迭代代码生成与评估来自动优化 harness，但始终使用**固定开发集**和**固定提议策略**，导致搜索沿单一轨迹推进，容易陷入局部最优。
- **关键缺陷**：
  - 固定开发集可能忽略“互补能力”：某个 harness 能解决领先 harness 遗漏的案例，但总体排名较低，因此难以继续发展。
  - 固定提议指令无法根据搜索过程中涌现的优势与未解决失败来调整探索优先级。
- **整体含义**：论文试图让“改进过程本身”自适应——通过多分支搜索、动态开发子集和分支专属提议策略，发现互补 harness，并在部署时用路由器组合其优势。所有选择仅基于开发数据，不使用测试结果。

## 2. 方法论：核心思想、关键技术细节与算法流程

### 2.1 核心思想

- 将 harness 演化组织为多个**独立搜索分支**。
- 每个分支拥有自己的：
  - 开发子集 \(X_t^b\)；
  - 候选 harness 历史与文件系统 \(D_t^b\)；
  - 提议指导 \(S_t^b\)（存储于 `SKILL.md`）。
- 分支通过**比较前沿覆盖度**动态调整开发子集，使不同分支专注于不同失败案例，从而产生互补 harness。
- 部署时用**路由器**为每个新输入选择一个开发集最优的分支头，无需测试反馈。

### 2.2 分支局部搜索与目标

- 分支 \(b\) 的目标为：
  \[
  J_t^b(H)=\frac{1}{|X_t^b|}\sum_{x\in X_t^b}\mathbb{E}[r(f_M(H,x),x)]
  \]
  其中 \(H\) 为候选 harness，\(M\) 为动作语言模型，\(f_M(H,x)\) 为执行轨迹，\(r\) 为任务奖励。
- 每轮中，共享提议器 \(P\)（Claude Opus 4.6）读取分支内 harness–分数对、执行轨迹和指导 \(S_t^b\)，提出新 harness，并在 \(X_t^b\) 上评估。

### 2.3 动态开发子集更新

- 每个分支定义前沿 \(F_t^b\)：按当前开发子集平均奖励排名前 \(q\) 的 harness。
- 对每个开发案例 \(x\)，计算前沿覆盖投票：
  \[
  c_t^b(x)=\sum_{H\in F_t^b}\mathbb{1}[H\text{ solves }x]
  \]
- 更新规则：
  - 若所有分支的所有前沿 harness 都解决 \(x\)，则从所有子集中删除该案例。
  - 若分支 \(b\) 相对其他分支有足够优势：
    \[
    c_t^b(x)-\max_{b'\neq b}c_t^{b'}(x)\ge \Delta
    \]
    则该案例归分支 \(b\) 所有，并从其他分支删除。
  - 否则子集成员保持不变。
- 效果：保留分支具有相对优势的案例，形成不同搜索目标，且无需预定义任务类别。

### 2.4 分支专属提议指导更新

- 初始所有分支共享 \(S_0\)，但随着开发子集分化，共享指导不再适用。
- 每隔 \(C_s\) 轮，由同一提议器 \(P\) 根据当前指导与近期搜索记录更新 \(S_t^b\)。
- 更新指令要求：
  - 比较同一开发阶段的候选；
  - 区分重复证据与孤立成功/失败；
  - 记录有效修改、反复失败机制和未解决问题；
  - 形成下一阶段目标，同时保留探索空间。
- 结果：不同分支形成不同探索优先级，例如数学分支中一个侧重答案验证，另一个侧重推导构造。

### 2.5 开发信息驱动的路由

- 搜索结束后，每个分支选出一个开发集最优的 head \(\hat H_N^b\)。
- 由于不同分支开发子集不同，分数不可直接比较，因此训练路由器 \(R\)：
  - 使用仅被某一个最终 head 解决的开发案例作为标签；
  - 输入包括专家源码、head-exclusive 开发案例以及两个 head 的输出；
  - 用 GEPA 优化路由指令；
  - 新问题执行前选择专家，不使用专家输出或正确性反馈。

### 2.6 算法流程

- 初始化：在完整开发集上评估种子 harness，复制到各分支。
- 每轮并行：
  - 提议器基于分支历史、开发子集和指导提出新 harness；
  - 在分支开发子集上评估并存储记录；
  - 每隔 \(C_p\) 轮更新前沿并执行开发集剪枝；
  - 每隔 \(C_s\) 轮更新分支指导。
- 结束后：
  - 每分支选开发集最优 head；
  - 构建路由器；
  - 部署时先路由再执行。
