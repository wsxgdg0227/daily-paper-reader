## 摘要
高性能 GPU 内核对于现代机器学习系统至关重要，但自动生成既正确又高效的内核仍然具有挑战性。现有的基于 LLM 的方法面临两大局限：与模型当前能力相匹配的高质量训练数据稀缺，以及内核正确性与性能之间固有的权衡。为应对这些挑战，我们提出 KernelZero，一个协同演化框架，通过两个专门模型持续改进 GPU 内核生成：一个 Proposer（提议器）根据 API 集合生成 Torch 模块，一个 Coder（编码器）将其转换为 CUDA 或 Triton 内核。KernelZero 使用前沿驱动的模块生成机制，基于 Coder 当前的弱点持续生成与能力匹配的训练模块。它进一步引入正确性感知组相对策略优化（Correctness-Aware Group Relative Policy Optimization，CA-GRPO），仅在正确性足够可靠后才优化性能。通过交替优化 Proposer 和 Coder，KernelZero 形成自动课程，实现有针对性的、训练高效的能力提升。在实证中，KernelZero-7B 在 CUDA 上超越 Claude-4.5-Sonnet，在 Triton 上超越 DeepSeek-V4-Pro。在 KernelBench Level 1 和 2 上，其 CUDA pass@1 分别达到 75.8% 和 69.6%，pass@10 达到 100% 和 97%。在 Triton 上，pass@1 分别达到 77.2% 和 72.5%。

## Abstract
High-performance GPU kernels are essential to modern machine learning systems, yet automatically generating kernels that are both correct and efficient remains challenging. Existing LLM-based approaches face two major limitations: the scarcity of high-quality training data aligned with the model's current capabilities, and the inherent trade-off between kernel correctness and performance. To address these challenges, we propose KernelZero, a co-evolution framework that continuously improves GPU kernel generation through two specialized models: a Proposer that generates Torch modules from API sets and a Coder that translates them into CUDA or Triton kernels. KernelZero uses a frontier-driven module generation mechanism to continuously produce capability-aligned training modules based on the Coder's current weaknesses. It further introduces Correctness-Aware Group Relative Policy Optimization (CA-GRPO), which optimizes performance only after correctness becomes sufficiently reliable. By alternating the optimization of the Proposer and Coder, KernelZero forms an automatic curriculum that enables targeted and training-efficient capability improvement. Empirically, KernelZero-7B surpasses Claude-4.5-Sonnet on CUDA and DeepSeek-V4-Pro on Triton. On KernelBench Level 1 and 2, it achieves CUDA pass@1 scores of 75.8% and 69.6%, respectively, with pass@10 reaching 100% and 97%. On Triton, it achieves pass@1 scores of 77.2% and 72.5%, respectively.

## 一、核心问题与研究动机

- **背景**：高性能 GPU 内核是现代机器学习系统的关键基础设施，但手工开发成本极高，要求开发者同时掌握 CUDA、BangC、Triton 等领域特定语言以及计算机体系结构知识。
- **现状**：LLM 已被用于 GPU 内核生成（如 Kevin、Dr.Kernel、cudaLLM），但即使经过大规模 SFT 与 RL 训练，效果仍不理想。例如 cudaLLM 动用 128 张 H100 训练，在 KernelBench Level 1 上 pass@10 仅 81%。
- **两大根本挑战**：
  1. **能力对齐数据稀缺**：与模型当前能力匹配的高质量训练数据难以获取，导致训练难以收敛或成本极高。
  2. **正确性-性能权衡**：只优化正确性会得到保守、加速有限的内核；激进优化性能则显著增加错误风险。
- **研究问题**：如何以**有针对性**的方式训练模型，从而高效提升 GPU 内核生成性能？
- **整体含义**：论文主张用"持续协同演化"替代"一次性大规模训练"，让模型在每一轮迭代中动态识别并学习最贴合自身能力边界的样本，形成自动课程（automatic curriculum）。

## 二、方法论

### 2.1 总体框架

- 将内核生成建模为两个显式接口模型的协同演化：
  - **Proposer（提议器）**：输入 Torch API 集合 $a \in \mathcal{A}$，输出可运行的 Torch 模块 $m \sim \pi_P(\cdot|a;\theta_P)$。
  - **Coder（编码器）**：输入模块 $m$，输出 CUDA 或 Triton 内核 $k \sim \pi_C(\cdot|m;\theta_C)$。
- 形成两阶段映射 $a \xrightarrow{P} m \xrightarrow{C} k$，Proposer 探索算子组合空间，Coder 将其实现为高效底层代码。
- **交替优化**：两者轮流用各自的奖励（$r_P$ 或 $r_C$）通过 GRPO 更新，更新一方时固定另一方。

### 2.2 Proposer：生成前沿 Torch 模块

- **API 列表采样**：从真实 Torch 模块中构建 API 共现分布，采样 API 子集作为输入，兼顾真实性与多样性。
- **验证检查（三阶段）**：
  1. **AST 检查**：静态分析验证计算图与采样 API 集合语义一致。
  2. **可运行检查**：通过 `get_init_inputs` 与 `get_inputs` 构造输入并在 CUDA 设备上执行，丢弃编译或运行时报错的模块。
  3. **数值稳定性**：随机输入下过滤产生 NaN/Inf 的样本。
- **前沿奖励（Frontier Reward）**：设 Coder 对模块 $m$ 采样 $K$ 个内核的平均正确率为 $\bar{l}$，则
  $$R_p(m) = \begin{cases} 1 - 2|\bar{l} - 0.5|, & m \text{ 有效} \\ \rho, & m \text{ 无效} \end{cases}$$
  其中 $\rho<0$ 惩罚无效模块。奖励在正确率接近 0.5 时最大，鼓励生成既不过于简单也不过于困难的"能力边界"模块。对应算法称为 **FO-GRPO**。

### 2.3 Coder：生成高性能内核

- **编译器启发的冷启动蒸馏**：总结四条 GPU 优化原则，用于提示教师模型逐步推理后再产出内核：
  - **Tiling**（分块）：将张量划分为片上存储可容纳的块，提升数据复用、支持块/线程束规约。
  - **Fusion**（融合）：将生产者-消费者算子链合并为单一内核，减少中间张量、DRAM 流量与同步开销。
  - **Pipeline**（流水线）：分阶段执行，重叠内存搬运与计算以隐藏延迟。
  - **Reordering**（重排）：调整循环顺序与线程/数据映射，改善合并访存与局部性，缓解 bank 冲突与分支发散。
- **CA-GRPO（正确性感知组相对策略优化）**：
  - 对模块 $m$ 采样 $n$ 个候选内核，计算组级正确率 $\text{Acc}_G$。
  - 阈值函数 $T(G)=1$ 当 $\text{Acc}_G \geq \alpha$，否则为 0。
  - 对正确子集 $\mathcal{G}_c$ 定义归一化加速分：
    $$S_i^G = \frac{S(k_i) - \min(S(\mathcal{G}_c))}{\max(S(\mathcal{G}_c)) - \min(S(\mathcal{G}_c))}$$
    （当最大最小相等时置 0）。
  - 最终奖励：
    $$R_i^G = \begin{cases} 1 + T(G)\cdot\beta\cdot S_i^G, & \text{若 } \text{Corr}(m,k_i)=1 \\ 0, & \text{否则} \end{cases}$$
  - 关键设计：**只有组内正确率达标后才启用性能信号**，实现"先学正确、再学快"。
- **训练循环**：每轮 Proposer 更新 20 步（用 $R_p$），Coder 更新 20 步（用 $R_i^G$），共 4 轮。

## 三、实验设计

- **Benchmark**：KernelBench（250 个任务，三个难度级别）
  - Level 1：100 个单内核算子（如 Convolution）
  - Level 2：100 个融合模式（如 Matmul + Sigmoid）
  - 每个模型根据 PyTorch 参考实现以 one-shot 方式生成 CUDA 或 Triton 内核。
- **指标**：
  - `pass@k`（按 HumanEval 方式估计）：功能正确的比例。
  - `fast p@k`：内核既正确又相对 PyTorch 实现加速超过 $p$ 倍的比例（如 fast 2@1）。
  - 输出 token 数（含推理与最终代码），反映推理效率。
- **对比基线**：
  - **基础模型**：Claude-3.5/3.7/4.5-Sonnet、Gemini-2.5-Flash、GPT-oss-120B、GLM-5.1/5.2、Qwen3-32B/8B、Qwen2.5-Coder-32B/7B；Triton 侧额外对比 DeepSeek-V4-Pro。
  - **专用模型**：cudaLLM-8B、Kevin-32B（CUDA）；Dr.Kernel 8B/14B（Triton 三轮设置）。
- **消融实验**：
  - **Proposer 效果**：冻结 Step 40 后的 Proposer，对比持续更新的收益。
  - **正确性阈值 $\alpha$**：在 $\{0, 0.5, 0.9, 1.1\}$ 上评估（0 表示始终启用加速奖励，1.1 表示从不启用）。
  - **逐算子结果**：对 Tensor-MM、GroupNorm、Sum Reduce、Conv-BN-Scale、Conv3D Fusion、GEMM-BN-Swish 六个代表性算子报告最快正确内核的加速比。
- **自建评测服务器 Keck**：修复 KernelBench 的若干问题，包括单样本 GPU 隔离执行、模块参数一致性（`load_state_dict`）、统一数值校验（绝对/相对容差 $10^{-2}$）、后端特定实现约束（CUDA 不得调用 PyTorch 计算 API，Triton 必须为真实 `@triton.jit` 内核）、正确性门控的性能测量。

## 六、主要结论与发现

- **性能**：KernelZero-7B 在 CUDA 上超越 Claude-4.5-Sonnet，在 Triton 上超越 DeepSeek-V4-Pro，尽管参数量仅 7B。
  - CUDA：L1 pass@1 = 75.8%、pass@5 = 98.87%、pass@10 = 100%；L2 pass@1 = 69.6%、pass@5 = 93.70%、pass@10 = 97%。
  - Triton：L1 pass@1 = 77.2%、pass@5 = 97.41%、pass@10 = 99%；L2 pass@1 = 72.5%、pass@5 = 94.96%、pass@10 = 98%。
- **协同演化的收益**：持续更新 Proposer 相比冻结版本，CUDA L1/L2 的 pass@1 分别提升 0.9/5.2 个百分点，Triton 提升 2.3/4.2 个百分点；fast 1@1 也有一致提升，且 Level 2 收益更大。
- **正确性阈值的权衡**：$\alpha=1.1$（从不启用加速奖励）pass@1 最高（74.85%）但 fast 1.5@1 仅 9.75%；$\alpha=0.9$ 取得 73.15% pass@1 与最高 fast 1.5@1（11.00%）；综合最优为 $\alpha=0.5$。
- **后端差异**：Triton 的加速表现显著优于 CUDA（L1 fast 1@1 43.9% vs 17.6%；L2 65.4% vs 2.4%），原因是 Triton 提供瓦片级抽象便于表达 tiling/fusion，而生成的 CUDA 内核不调用外部高性能库，L2 中卷积/GEMM 的 PyTorch 参考直接调度到高度优化的 cuDNN/cuBLAS，独立内核难以超越。
- **Proposer 演化质量**：训练修复了算子

- **Proposer 演化质量**：训练修复了算子在 API 组合上的语义错误与数值不稳定问题，使生成模块逐步从简单单算子向复杂多算子融合迁移，同时保持在 Coder 正确率约 50% 的能力边界附近；案例研究显示 Step 60 相比 Base 检查点生成的模块结构更丰富、更接近真实深度学习工作负载（如 Conv+BN+激活的组合链），而非退化为孤立的简单算子。
- **课程有效性**：前沿奖励驱动的模块难度随训练轮次自然上升，验证了"自动课程"机制能够替代人工设计难度分层。
- **推理成本**：KernelZero-7B 的输出 token 数显著低于大型基线模型，说明其在保持高性能的同时具备更好的推理效率，验证了冷启动蒸馏与 RL 对推理冗长的抑制效果。

## 七、局限性与未来方向

- **评测范围有限**：实验仅基于 KernelBench 的 250 个任务，任务分布集中在算子级与简单融合模式，未覆盖真实端到端模型（如 Transformer 训练/推理全流程）中的复杂内核需求，泛化能力有待进一步验证。
- **模型规模单一**：Proposer 与 Coder 均从 Qwen2.5-Coder-7B 初始化，未验证该协同演化框架在 32B、70B 等更大底座上的可扩展性与边际收益，也未讨论规模定律在该任务上的表现。
- **奖励信号来源单一**：正确性与加速比均来自静态评测服务器 Keck，未引入编译器（如 NVCC/PTXAS）反馈、硬件性能计数器（如 NCU 的 SM 占用率、DRAM 带宽利用率）或实际运行时剖析数据，奖励信号与真实优化目标之间仍存在代理偏差。
- **数值判定宽松**：正确性容差统一设为 $10^{-2}$，对于累加、归约等对数值精度敏感的操作可能过于宽松，存在"数值上看似正确但实际不可用于生产"的风险。
- **训练成本仍不低**：每模型 4 轮 × 2 阶段共 80 步更新，累计约 30 小时 A100 时间并占用 8–12 张 GPU，对于资源有限的研究团队仍有门槛；论文未给出更小规模配置下的收益曲线。
- **潜在改进方向**：可考虑引入多后端协同（CUDA/Triton/TileLang 混合课程）、以性能剖析器驱动的细粒度奖励、以及 Proposer-Coder 联合而非交替优化的端到端训练范式。

## 八、总体评价与启发

- **方法贡献**：论文将 GPU 内核生成从"一次性大规模训练"重新表述为"能力对齐的持续协同演化"，提出 Proposer–Coder 双模型交替优化框架，配合前沿奖励（FO-GRPO）与正确性感知奖励（CA-GRPO），在方法论上兼具简洁性与针对性。
- **关键洞察**：
  1. **训练数据的难度应动态匹配模型当前能力**，而非静态采样——这一思想可迁移至代码生成、数学推理等更广泛的 RL 训练场景。
  2. **正确性与性能应分阶段优化**，先建立正确性门槛再启用性能信号，能有效缓解"追求加速导致正确率崩塌"的常见失败模式。
  3. **自建评测基础设施（Keck）是高性能内核研究的必要条件**，KernelBench 原生的干扰因素与随机性问题会显著影响结论可信度。
- **实证说服力**：7B 模型在 CUDA 上超越 Claude-4.5-Sonnet、在 Triton 上超越 DeepSeek-V4-Pro，且通过多组消融（Proposer 冻结、阈值四档、六算子逐项）系统验证了各组件贡献，结论具备较强说服力。
- **尚待回答的问题**：协同演化是否会陷入局部最优（如 Proposer 与 Coder 共同退化到简单算子）？前沿奖励在 Coder 能力快速变化时是否需要重新标定？这些在论文中讨论不足，是后续研究值得深入的方向。
