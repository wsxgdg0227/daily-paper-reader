Abstract
Large language models (LLMs) have demon-
strated strong performance in code generation,
where success depends on both recalling rel-
evant algorithmic knowledge and reasoning
about how to apply it. However, existing LLM
pipelines are opaque, with no explicit separa-
tion between these two components. We argue
that for well-known algorithms whose canon-
ical implementations are widely accessible in
pretraining corpora, code generation is better
measured as parametric code retrieval: repro-
ducing a named algorithm from internalised
knowledge rather than synthesizing a novel one.
We introduce ALGOREVAL, a benchmark of
599 problems spanning classical 77 algorithms
across 14 domains, 7 programming languages,
and 4 graph-input representations to evaluate
this capability in isolation, and assess 15 mod-
els (7B–34B parameters) in a zero-shot setting.
We find substantial variation in retrieval ac-
curacy across languages and input representa-
tions, even for widely documented algorithms
and show that prompt augmentation with re-
trieved code snippets or structured algorithmic
hints improve accuracy on complex algorithms,
while SFT achieves broader language gains and
GRPO achieves larger per-language gains on
specific languages. Together, our results es-
tablish parametric code retrieval as a distinct,
measurable capability and caution against de-
ploying AI-generated algorithmic code without
systematic validation.1

We focus on the “retrieval” aspect. The distinc-
tion has real stakes: an estimated 72% of devel-
opers now use AI coding tools on a daily basis,
and AI currently generates 42% of all committed
code.2 Yet, 66% report their top frustration is code
that is almost right, but not quite, which precisely
describes retrieval failure: the model knows the
algorithm but gets a detail wrong (Zhu et al., 2025).
In agentic coding pipelines, where models plan,
generate, and commit code without per-step hu-
man review, a retrieval failure in a graph algorithm
may not surface until a production incident exposes
the wrong output being computed silently (Sapkota
et al., 2025; Cemri et al., 2025). Knowing where
and how retrieval breaks is the minimum informa-
tion needed to decide when AI-generated algorith-
mic code can be trusted without verification.
Most code generation research frames the task
as synthesis: given a problem statement, construct
a solution. This is appropriate for novel problems,
but for well-known algorithms whose canonical
implementations appear across thousands of open-
source repositories and almost certainly in the pre-
training corpora of every model we evaluate. The
model need not invent anything; it must retrieve.

Conflating the two obscures a distinct failure mode:
a model may demonstrate impressive synthesis on
novel tasks while quietly failing to reproduce even
the most widely documented algorithms, or vice-
versa (Riddell et al., 2024; Matton et al., 2024).
We isolate this as parametric code retrieval: repro-
ducing a correct implementation of a named algo-
rithm in a specified language from parametric mem-
ory alone. Code constitutes roughly 13% of the
Dolma corpus (411 B of 3.1 T tokens) (Kocetkov
et al., 2022; Soldaini et al., 2024), with JavaScript
(486 GB), Java (271 GB), and C (222 GB) account-
ing for over half by volume, which are precisely
the language families our benchmark targets.
Contributions. We introduce ALGOREVAL,
a benchmark of 599 problems spanning 77 algo-
rithms, 7 programming languages, and 4 graph-
input representations, and evaluate fifteen models
zero-shot. We then ask whether retrieval failures
can be remediated: first via prompt augmentation
with retrieved code snippets or structured algorith-
mic hints, and then via GRPO (Group Relative
Policy Optimization) fine-tuning with execution-
based rewards compared against a SFT (Supervised
fine-tuning) baseline. Our main findings are three-
fold. First, retrieval accuracy varies widely across
models, and the variance is governed by surface
form (programming language and input representa-


tion) and not model size or code specialisation. The
dominant failure mode in Python and JavaScript is
wrong output: runnable code that silently returns
the wrong answer. Second, prompt augmentation
does not reliably improve retrieval in aggregate,
and actively hurts when parametric knowledge is
already present; executable snippets are more ef-
fective than abstract hints only on problems where
the model’s parametric trace is already thin. Third,
GRPO fine-tuning with execution-based rewards
converges faster than SFT and closes language gaps
that binary supervision cannot address, particularly
in Rust where partial-credit signals from compile
failures carry information that correct/incorrect la-
bels discard.

recovering a correct, executable implementation
of a named algorithm from an LLM’s parametric
memory, in a specified programming language and
input representation, without access to external doc-
uments or in-context examples.

Dataset Construction
We build the benchmark with 107 Python problems
drawn from RosettaCode3 and GeeksforGeeks4,
covering 77 distinct algorithms across 14 domains:
graph algorithms, sorting, dynamic programming,
string algorithms, number theory, image process-
ing, data structures, computational geometry, nu-
merical methods, compression, cryptography, back-
tracking, and parsing. Some algorithms contribute
to more than one problem, e.g., a weighted and
an unweighted variant, accounting for the gap be-
tween 107 problems and 77 algorithms. We select
algorithms that are extensively documented across
open-source repositories and therefore almost cer-
tainly present in any large pretraining corpus. This
is a deliberate design choice: we are not testing
generalisation to unseen problems, but the fidelity
of recall for algorithms a model has already been
exposed to. Ground truth for each problem is es-
tablished by executing a reference implementation
on the fixed test input tp and recording its standard
output as yp; a model passes if and only if its gen-
erated code reproduces yp exactly after whitespace

actly one primary domain based on its canonical

Each Python problem is adapted to six additional
languages (C++, Java, C, JavaScript, Rust, and Go)
by applying three transformations: (1) replacing
the target language name throughout the prompt,
(2) substituting the embedded Python test block
with an explicit expected-output specification, and
(3) rewriting Python-specific entry-point idioms to
language-appropriate forms (e.g., int main() for
C/C++, fn main() for Rust). This yields a multi-
lingual benchmark in which the same algorithmic
task is posed identically across all 7 languages,
isolating language-level retrieval differences from
differences in problem framing.

Related Work
4.1
Parametric Memory in LLMs.
Pretraining encodes factual and procedural knowl-
edge directly into model weights as parametric
memory (Petroni et al., 2019), which can be queried
at inference time without external retrieval. Prob-
ing studies on factual QA show that recall is re-
liable when inference-time surface forms closely
match training data, but degrades sharply under
paraphrase or format change (Roberts et al., 2020;
Gekhman et al., 2026). We study the same degra-
dation in code: the surface shift is a change in pro-
gramming language or input representation rather
than a change in natural-language phrasing, and the
failure mode is wrong output rather than a factual
error.
4.2
Code Generation Benchmarks
The dominant paradigm in code generation re-
search treats the task as synthesis: given a natural-
language specification, produce a correct program.
HumanEval (Chen et al., 2021) and MBPP (Austin
et al., 2021a) operationalise this with short func-
tional puzzles. APPS (Hendrycks et al., 2021)
scales difficulty to competitive programming. Live-
CodeBench (Jain et al., 2024) reduces contamina-
tion by time-gating problems after model training
cutoffs. All of these treat training-data overlap as
a confound to eliminate. However, Riddell et al.
(2024) found that only 3.6–20.8% of their reference
solutions turn up almost word-for-word in common
pretraining corpora such as the Pile (Gao et al.,
2020) and the Stack (Lozhkov et al., 2024). Either
way, these benchmarks do not probe whether the
model has seen the underlying algorithm before and


can reproduce it correctly in a given language and
input format. That framing is appropriate for novel
problems, but not for algorithms that are widely
documented, where correct behavior is explained
by retrieval: reconstructing a correct implementa-
tion from internalised parametric knowledge, ex-
pressing the algorithm’s structure, invariants, and
control flow correctly even in forms not seen ver-
batim. We take the opposite stance: overlap is the
precondition for our task, and the question worth
asking is not whether a model can produce code but
whether it faithfully reproduces correct implemen-
tations of algorithms it has already encountered.
Crucially, because existing benchmarks do not con-
trol for training exposure, a model’s pass rate on
a well-known algorithm conflates two fundamen-
tally different capabilities: retrieval, i.e., recalling
a correct implementation from parametric memory,
and understanding, i.e., deriving a solution through
reasoning (Maveli et al., 2026).
4.3
Retrieval-augmented generation (RAG)
RAG-based code generation assumes a parametric
knowledge deficit and supplies retrieved context to
fill it (Wang et al., 2025). The retrieved examples
add retrieval noise, misaligned context, and surface-
level code patterns that compete with, rather than
complement, what the model already encodes para-
metrically. Models perform significantly better on
the subset of benchmarks where similar solutions
were seen during training, and are more likely to
emit memorized training data when they have seen
it multiple times (Riddell et al., 2024). We there-
fore focus on parametric code recall: the model’s
capacity to retrieve correct algorithmic solutions
from weights alone, without retrieval augmenta-
tion.

Experimental Setup
5.1
Models
Programming language distribution in LLM pre-
training data varies dramatically by model type
and is rarely disclosed at the per-language level.
General-purpose models allocate a modest frac-
tion to code: LLaMA-1 (Touvron et al., 2023) re-
served only 4.5% of its 1.4T tokens for GitHub
content, while LLaMA-3 (Grattafiori et al., 2024)
scaled this to approximately 17% of 15T+ tokens.
Code-centric models invest far more: DeepSeek-
Coder (Guo et al., 2024) allocates 87% of its
2T tokens to code across 87 languages, and Star-
Coder2 (Lozhkov et al., 2024) trains almost entirely
on The Stack v2 (619 languages, ~4T tokens). This
variation matters for our benchmark: a model’s
pretraining code budget directly shapes which lan-
guages it has had sufficient exposure to for reliable
parametric retrieval.
We evaluate 15 models spanning three axes
of variation: (1) specialisation: general-purpose
instruction-tuned models versus code-specialised
ones; (2) scale: 7B to 34B parameters, and (3) in-
ference regime: standard decoding versus extended
chain-of-thought reasoning. Full model identifiers,
parameter counts, and licenses are listed in Ap-
pendix B.
5.2
Evaluation
Execution harness.
Each model-generated pro-
gram is executed in an isolated subprocess with
a 30-second wall-clock timeout.
Interpreted
languages (Python, JavaScript) are run directly,
whereas compiled languages (C, C++, Java, Rust,
Go) go through a mandatory compilation step first.
A compilation failure is recorded immediately as
a static failure without attempting execution. Stan-
dard output is compared against the ground-truth
string after whitespace normalisation; a submission
passes if and only if the strings match exactly. Fail-
ures are categorised into four mutually exclusive
types: static failure (parse or compile error), run-
time error (uncaught exception during execution),
timeout (execution exceeds 30 s), and wrong output
(clean execution but incorrect stdout).
Metrics.
Our primary metric is pass rate: the
fraction of problem instances on which a model’s
generated code passes, reported overall and strati-
fied by domain, language ℓ, and input representa-
tion r. Pass rate captures correctness but not consis-
tency: two models can both pass a problem while
producing structurally unrelated implementations.
To characterise solution diversity, we follow the
AlgoSim evaluation framework (Lee et al., 2025):
model predictions are pooled, grouped by problem
label, and evaluated for pairwise lexical similar-
ity across every pair of models that each produced
code for the same problem.
With the benchmark and evaluation harness in
place, we organise our experiments around three
questions. The first establishes where and how
retrieval fails: without a clear failure map, any pro-
posed remedy is unmotivated. The second asks
whether those failures can be patched at inference


time through prompt augmentation, which requires
no model changes but assumes that injecting exter-
nal context into a prompt where parametric knowl-
edge already exists is net-positive. The third asks
whether the gaps can instead be closed at the weight
level through execution-based fine-tuning, separat-
ing the contribution of reward signal (GRPO) from
the contribution of training on correct solutions
alone (SFT). In this paper, we mainly investigate
the following research questions through experi-
ments.
RQ1. How reliably do LLMs retrieve algorith-
mic code from parametric knowledge across
languages and input representations?
RQ2. Does augmenting LLM prompts with re-
trieved code snippets or structured algorithmic
hints improve parametric code retrieval accu-
racy, and which source better compensates for
failures on complex and esoteric algorithms?
RQ3. Does GRPO fine-tuning with execution-
based rewards reduce representation and lan-
guage accuracy gaps relative to SFT on algo-
rithmic code retrieval?
6
Analysis
We report results for each research question in turn,
moving from baseline measurement of retrieval
fidelity (RQ1) through inference-time intervention
via prompt augmentation (RQ2) to weight-level
adaptation via fine-tuning (RQ3).

spanning 37 algorithms, 80% of pairs share the
same underlying approach despite surface variation,
while 20% represent structurally distinct implemen-
tations of the same algorithm. This combination of
high surface diversity, predominantly shared algo-
rithmic structure, and zero verbatim matches is con-
sistent with parametric retrieval: models converge
on the same algorithm from memory but express it
independently rather than replaying a cached token
sequence. Figure 10 further shows that pass rate
and consensus recall are correlated but not iden-
tical: some models produce correct outputs that
deviate from the plurality answer, indicating in-
dependent retrieval rather than convergence on a
single cached response. A breakdown of AlgoSim
novel rate per model and language is provided in

6.3
RQ3: SFT vs. GRPO Fine-Tuning for
Closing Language and Representation
Gaps
Prompt augmentation treats retrieval failures as a
deployment-time problem, patching them case by
case. Fine-tuning with execution-based rewards
takes a different approach: adjusting the model’s
weights so that retrieval becomes more reliable
across languages and representations without re-
quiring external context. We apply GRPO (Shao
et al., 2024) to gpt-oss-20B using execution correct-
ness as the reward signal, and compare the resulting
checkpoint against both the base model and a SFT
baseline trained on the positive-reward subset of
the same training examples.
We fine-tune gpt-oss-20B using LoRA adapters
(r=16, α=32, dropout = 0.05) on all seven pro-
jection matrices, keeping approximately 0.5% of
parameters trainable. Both GRPO and SFT are
trained on the 56-algorithm training split (447 ex-
amples spanning all 7 languages and up to 3 input
representations per algorithm), with 22 algorithms
held out for evaluation. Training examples are orga-
nized into representative groups where all examples
sharing a canonical algorithm name (across lan-
guages and representations) constitute one group.
The reward function uses a four-tier ladder: exact
stdout match (r = 1.0), normalized match after
whitespace collapsing (r = 0.8), wrong output
with clean execution (r = 0.3), and any runtime
crash or static failure (r = 0.0–0.1). Advantages
are computed within each repr group via standard
GRPO normalization. The groups with zero reward
variance are skipped. The SFT baseline is trained
via rejection sampling on the 367 examples where
the base model already achieves reward 1.0, using
the same LoRA configuration, isolating the effect
of policy-gradient credit assignment from the ef-
fect of simply training on correct solutions. Full
hyperparameters appear in Appendix E.

Conclusion
We argue the question worth asking is not whether a
model can synthesise a solution but whether it reli-
ably reproduces one it has already internalised. The
most operationally significant failures are wrong-
output errors: syntactically valid, runnable code
that silently computes the wrong result, invisible
without a concrete test case, and present even in
the best-performing models. Retrieval failures are
partially remediable, but in complementary ways.
Prompt augmentation helps only where parametric
knowledge is genuinely absent. Execution-based
fine-tuning acts at the weight level: SFT achieves
broader and more consistent gains across lan-
guages (+3.9 pp overall), while GRPO’s execution-


based reward concentrates signal on specific lan-
guages, yielding the largest single-language gain
on JavaScript (+14.3 pp) but regressing on C++
(−9.5 pp).
Limitations
The results above are subject to three constraints
that bound what behavioral evaluation can establish
about parametric code retrieval.
A model may pass tp while silently failing on
edge cases such as empty graphs, disconnected
components, duplicate keys, or negative-weight
cycles, that the fixed input test case does not ex-
ercise. EvalPlus (Liu et al., 2023) demonstrated
that augmenting HumanEval with additional test
cases reduces pass rates substantially. A similar
augmentation of ALGOREVAL would tighten the
correctness criterion, but was not feasible at the
scale of 599 problems across 7 languages without
a verified oracle for each variant.
Our core framing assumes that all 77 algorithms
appear in the pretraining corpus of every model
we evaluate, and interprets failures as surface-form
brittleness rather than genuine knowledge absence.
This assumption is untestable: pretraining data
composition is rarely disclosed at per-algorithm or
per-language granularity. For some low-frequency
algorithms in low-resource languages (Go, Rust),
what we label a retrieval failure may instead re-
flect a genuine coverage gap in the pretraining data.
Without access to training data, the retrieval and
knowledge-absence failure modes cannot be sepa-
rated.
The paper frames correct model outputs as evi-
dence of parametric retrieval, but external behavior
alone cannot fully isolate retrieval from synthesis.
A clean separation would require either mechanis-
tic tracing of which training examples causally in-
fluence a given generation, or behavioral probes on
which a retrieved and a synthesized implementation
would make systematically different predictions,
neither is available to output-level evaluation.

Scale Experiment: A Behavioral Probe
for Retrieval vs. Synthesis
For each of 10 algorithms (kruskal, prim, bridges,
articulation points, boruvka, dijkstra, bellman-ford,
karger’s min cut, Stoer–Wagner, blossom), we sam-
ple G(n, p) graphs at 5 algorithm-specific values
of n (from n=50 for the O(V 3)/cut algorithms up
to n=8000 for near-linear ones), 8 samples per
(algo, n), with fresh networkx ground truth per
sample. We run every model that already passed
ALGOREVAL’s fixed-size correctness gate for that
algorithm (93 of 156 candidate pairs), in isolated,
resource-capped subprocesses.
For each (algo-
rithm, model), we fit a power law wall_time ∝nk
and compare the fitted exponent k to the text-
book exponent (e.g. O(E) →O(n2) in our dense
regime, where E ∼n2), allowing a tolerance of
±0.4. A second sparse regime (p(n) = 3 ln(n)/n,
E ∼n log n) covers the 7 algorithms with E-
dependent complexity: under dense sampling, a
correct O(E log V ) implementation and a hidden
O(V 2) one differ by only a log factor, but under
sparse sampling they differ by a full exponent, mak-
ing the two easy to tell apart.
Across both plots, the fitted runtime-vs-n curves
track the theoretical (textbook) complexity slope
rather than diverging from it. Most models are
reproducing the right asymptotic shape, not just the


right output.

conditions in Table 10, crossing name-correctness

Algorithmic-Fidelity Judging: Spec vs.
Code on External Benchmarks
It checks whether already-generated code on ex-
ternal benchmarks (MBPP, HumanEval, Live-
CodeBench) implements the algorithm its prompt
asked for. These benchmarks lack a single canoni-
cal algorithm name per problem, so a judge instead
categorizes the general technique/algorithm used.
A judge assigns each generation one category
from a closed list (18 categories for MBPP/Hu-
manEval, 24 for LiveCodeBench). The same judge
separately predicts the expected category from the
problem statement alone, standing in for a miss-
ing ground-truth label and joining spec-predicted
against code-observed category per problem gives a
fidelity signal. Two models (gemini-2.5-flash, gpt-
4.1-mini) are judged on 150 MBPP/HumanEval
and 75 LiveCodeBench problems.
We report the Pair match rate as a proxy for
algorithmic fidelity, which is the fraction of (prob-
lem, model) pairs where the code-judged category
equals the spec-predicted category.
The pair match rate is high on MBPP/Hu-
manEval (80.6%, 358/444) and lower on Live-
CodeBench (61.0%, 114/187). A second judge
(GPT-4.1, vs. the original gemini-pro-latest) shows
a clean self-preference effect: gemini-2.5-flash
scores best under the Gemini judge (82.2% MBPP,
77.5% LiveCodeBench) but worst under GPT-4.1
(69.9%, 53.7%), while gpt-4.1-mini scores best
under both.

Hopcroft-Karp bipartite maximum-cardinality matching and maximum
independent set for bipartite graphs.
D. Eppstein, April 2002.
"""
from .strong_connectivity import StronglyConnectedComponents
def matching(graph):
"""Find maximum cardinality matching of a bipartite graph (U,V,E).
The input format is a dictionary mapping members of U to lists
of their neighbors in V.
"""
# initialize greedy matching (redundant, but faster than full search)
matching = {}
for u in graph:
for v in graph[u]:
if v not in matching:
matching[v] = u
break
while True:
# structure residual graph into layers
preds = {}
unmatched = []
pred = {u: unmatched for u in graph}
for v in matching:
del pred[matching[v]]
layer = list(pred)
# repeatedly extend layering structure by another pair of layers
while layer and not unmatched:
newLayer = {}
for u in layer:
for v in graph[u]:
if v not in preds:
newLayer.setdefault(v, []).append(u)
layer = []
for v in newLayer:
preds[v] = newLayer[v]
if v in matching:
layer.append(matching[v])
pred[matching[v]] = v
else:
unmatched.append(v)
# did we finish layering without finding any alternating paths?
if not unmatched:
unlayered = {}
for u in graph:
for v in graph[u]:
if v not in preds:
unlayered[v] = None
return (matching, list(pred), list(unlayered))
# recursively search backward through layers to find alternating paths
def recurse(v):
if v in preds:
L = preds[v]
del preds[v]
for u in L:
if u in pred:
pu = pred[u]
del pred[u]
if pu is unmatched or recurse(pu):
