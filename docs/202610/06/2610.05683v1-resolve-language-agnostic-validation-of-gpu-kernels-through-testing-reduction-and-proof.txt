## Abstract 

AI systems can now write and optimize production GPU kernels, but validating them remains an important challenge. Evaluating the kernel on a few random inputs and check-ing that its outputs match a trusted reference kernel within numeric tolerances is not sufficient: races can cause non-deterministic behavior that fails to manifest in tests, and numeric tolerances can hide bugs and cause false positives even after extensive calibration. To address this challenge, we present RESOLVE, which combines testing and formal verification to build a compre-hensive kernel validation pipeline. It operates in three steps: First, it tests for nondeterminism using binary instrumen-tation that perturbs execution timing to expose races. Sec-ond, an agent rewrites the candidate and reference kernels to obtain "reduced-concurrency" versions that are simpler to analyze but still produce bitwise-identical outputs in all tests. Third, the reduced kernels are formally analyzed in the F*/Pulse framework and prove that they perform the same computation on real numbers. This sidesteps the need for numeric tolerances. We show that RESOLVE can validate a broad selection of kernels using KernelBench, and prove equivalence across fused GEMMs in three state-of-the-art frameworks and languages: CUTLASS, Triton, and Gluon. It also analyzes mega-kernels, notoriously difficult to vali-date, and finds four previously unreported issues, including two clear bugs. We show that agents can use RESOLVE to repair the issues, with minimal performance impact, high-lighting that agents can optimize aggressively when they can rigorously check their results. 

## 1 Introduction 

GPU kernels determine much of the performance of modern AI workloads. Recent systems have shown that AI agents can generate and optimize these kernels [24, 35, 50], produc-ing candidates far faster than humans can review them for correctness. Kernel generation is therefore creating a new validation bottleneck: an optimization that cannot be trusted cannot safely be deployed, regardless of its speed. The predominant method for validating GPU kernels is reference-based testing [24, 35]: execute a candidate and a trusted reference on representative inputs and compare their outputs. This approach is often effective for machine-learning kernels, whose behavior is determined largely by tensor shapes, data types, layouts, and other discrete config-urations that can be sampled systematically. Nevertheless, two challenges remain even with broad input coverage. First, concurrency bugs may manifest only under rare thread or warp schedules and therefore remain hidden across repeated executions. Second, valid optimizations may re-order floating-point operations and produce outputs that are not bitwise identical to the reference. Testing must conse-quently compare outputs using a numerical tolerance, but a permissive tolerance can conceal bugs while a restrictive one can reject valid optimizations. Formal verification can instead establish equivalence for all inputs covered by a specification [7, 28]. Its applicability, however, is limited by the verifier’s semantic coverage. Mod-ern kernels rely on warp intrinsics, asynchronous memory operations, tensor-core instructions, and synchronization patterns that existing verification frameworks do not fully model. Because GPU programming models and hardware features evolve faster than their formalizations, directly ver-ifying optimized production kernels remains impractical. This paper presents RESOLVE, a GPU-kernel validation framework that bridges the gap between the broad appli-cability of testing and the rigorous guarantees of formal verification. RESOLVE’s central idea is to separate concur-rency correctness from functional correctness , and to use a different validation technique for each. This decomposition exploits a key property of machine-learning kernels: they are generally intended to be deterministic, producing the same output for a given input regardless of thread schedule. This allows RESOLVE to focus on capturing a broad set of arXiv:2610.05683v1 [cs.PL] 5 Oct 2026 Vedadi Gargary et al.

RESOLVE then compares executions bit-for-bit. These comparisons distinguish two fail-ure modes. If repeated executions of the same kernel differ, RESOLVE reports schedule-dependent behavior. RESOLVE therefore uses testing where bitwise equality provides an exact per-execution oracle and formal verifica-tion where numerical testing requires an approximate one. Testing connects optimized binaries to proof-friendly repre-sentations, extending formal reasoning to kernels that use languages and hardware features outside the verifier’s se-mantic coverage. Agents construct the reductions, transla-tions, specifications, and proofs, but do not serve as cor-rectness oracles: their outputs must pass bitwise testing or formal proof checking. We evaluate RESOLVE on KernelBench kernels, complex state-of-the-art fused GEMM kernels written using Triton, Gluon, and CUTLASS, and three mega-kernels. Although every KernelBench candidate had passed the benchmark’s existing tolerance-based tests, RESOLVE identified two incor-rect candidates. We also design a mutation testing strategy to evaluate how effectively our concurrency testing finds synchronization faults. The fused GEMMs in particular use concurrency and hardware features outside Kuiper’s directly supported subset, and RESOLVE validated them regardless, demonstrating that reduction can extend formal reasoning to kernels that cannot be verified directly. Across the mega-kernels, RESOLVE found four previously unreported issues, including two clear bugs. Agents repaired them, and RE-SOLVE tested the repairs, which changed performance by less than 2% on three of the four. 

Contributions. In summary, we present RESOLVE, a workflow to validate GPU kernels. It consists of: 1. Efficient binary-level determinism testing (§3): timing perturbation on SASS, needing no source or compiler and covering any language or library. 2. Bitwise concurrency reduction (§4): an agent rewrites both programs with as little concurrency as possible, accepted only when the output is bitwise equivalent. 3. Automated equivalence proof (§5): agents write a specification from the trusted reference alone and a program for each side satisfying it, so an optimization can differ bitwise and still be accepted. 4. Given those reports, agents repaired the bugs, four with verified deterministic fixes, showing that better testing tools can make agentic kernel optimization more ambitious. 

## 2 GPU Background and Setup 

A GPU is built from many simple cores and gets its perfor-mance from running enormous numbers of threads. Recent GPUs also have fixed-function tensor cores that perform a small matrix multiply in a single instruction. A GPU function is called a kernel , and many thousands of threads run it at once. Threads are grouped into warps of 32 that advance together, warps into cooperative thread arrays (CTAs, also called blocks) whose threads share a fast on-chip scratchpad, and CTAs into a grid that covers the device. The newest hardware adds a cluster level between the CTA and the grid. RESOLVE: Language-Agnostic Validation of GPU Kernels Through Testing, Reduction, and Proof 

Memory follows the same levels: each thread has private 

registers , each CTA has shared memory that only its own threads can reach, and every thread can reach a large global memory . Launching a kernel runs one grid to completion. Most kernels are still written in CUDA, but a lot of perfor-mance work now happens in languages above it. Triton [44] lets a kernel be written over tiles and leaves the compiler to assign work to threads and to place data in shared memory. Gluon [45] sits on the same compiler but exposes layouts, memory movement and asynchrony, so the programmer con-trols what Triton decides. CUTLASS [32] is a C++ template library of hand-tuned building blocks for matrix multiply and its epilogues. Vendor libraries such as cuBLAS and cuDNN ship as binaries, with no source or PTX to inspect. The only common foundation is SASS , the relatively undocumented binary code for NVIDIA GPUs, unique to each architecture. Kernels have been getting larger. A single operation is usually limited by memory rather than arithmetic: it reads its inputs from global memory, computes, and writes the result back for the next operation to read again. Fusing several operations into one kernel removes those round trips. Fusion used to mean a matrix multiply with an activation attached to it. Now it means the whole MLP block of §6.3, the multi-layer perceptron that follows attention in every transformer layer of a modern LLM, or the mega-kernels of §6.4, which put an entire model in one launch. Two of those mega-kernels implement a mixture of experts , which replaces the MLP block with many copies of it and routes each token to a few. Fusing more work into one kernel puts more concurrency in it, and spreads that concurrency across more scopes. This paper is concerned with races : memory conflicts, at least one of them a write, unordered by synchronization. A race gives a different outcome depending on the scheduler. Races can oc-cur at every level of the hierarchy, and each level has its own way of ordering accesses: threads in a warp advance together, threads in a CTA can be ordered with __syncthreads() , and separate CTAs need a grid-wide barrier or atomics. The mem-ory scopes match, so shared memory can only be raced on from inside one CTA and global memory from anywhere. Asynchronous copies and TMA transfers add another bound-ary, between issuing a transfer and the point at which its result is safe to read. Reasoning about GPU programs almost always requires reasoning about floating-point computation, which does not behave like real arithmetic. Addition is not associative, so summing the same values in a different order changes the last bits, and any kernel that splits a reduction across threads is choosing an order. Fast-math flags widen the gap by letting the compiler reassociate, contract a multiply and an add into one fused operation, and replace a division by a reciprocal. Transcendental functions have no exact implementation, so an exponential ends up as a polynomial or a Taylor series, and two kernels can choose different ones. Tensor cores accumulate in their own precision and their own order, so a matrix multiply run on them does not agree bit for bit with the same multiply built out of ordinary fused multiply-adds. Two kernels that compute the same mathematical function may not produce the same bits. The kernels in this paper are tensor kernels, and we as-sume their shapes are fixed. ML kernels are tuned, and often recompiled, for the shapes they will actually see, so this is how they are written anyway. It also makes our testing tractable: with the shapes fixed, a kernel issues a fixed num-ber of memory accesses, so it can be traced in full and re-played on the same input under many schedules. 

2.1 RESOLVE Kernel Bench and Kernel Executors 

Throughout this work we need kernels to evaluate, and we draw on several corpora. For breadth and characterization we built one, the RESOLVE Kernel Bench (RKB), which pairs each of the 100 KernelBench Level 1 kernels [35] with an op-timized candidate. We generated the candidates with GPT-5.6 Sol and retried until each compiled and passed the tolerance tests shipped with the benchmark, so every candidate has already passed a conventional tolerance oracle. RESOLVE assumes each kernel comes with a kernel ex-ecutor. It runs the kernel a fixed number of times and hashes all of memory after each run, not just the output. That hash is what every comparison in RESOLVE is made on, between two runs of the same kernel and between a kernel and its reduced program. Hashing is only a way to save space: the comparisons are all equality tests, so we never need to keep a full copy of memory from every run. Inputs are tensors drawn from ten families of distributions, chosen per operation and seeded so a run can be replayed on the same input and any difference between runs is a property of the kernel. Uniform random data can miss branches and leave corner cases of floating-point arithmetic unexercised, so the families are built to cover both: degenerate, sparse and sentinel values, awkward magnitudes and cancellation, quantization boundaries, and the ties, indices, masks and lengths that steer control flow. We give their definitions in the artifact. Every kernel is run a fixed number of times on each input. 

## 3 Testing for Determinism 

RESOLVE requires the kernels it validates to be deterministic: on a given input, a kernel must produce the same output on every run. The determinism tester checks this, treating the kernel as a black box. Requiring determinism has two big advantages. First, it enables and improves the rest of our reduction pipeline, by simplifying subsequent reductions and boosting the effectiveness of random testing. Second, it can flag synchronization errors in kernels. For example, a mistakenly omitted barrier can cause nondeterminism. Vedadi Gargary et al.

Requiring determinism also has a potential disadvantage: we may reject kernels that are non-deterministic and yet cor-rect ( legitimate nondeterminism ). For example, a kernel may intentionally use a nondeterministic reduction order (say, based on atomicAdd ), leading to slightly different results due to the non-associativity of floating-point addition. Empirically, legitimate nondeterminism is rare for GPU kernels. Only one of the 100 kernels in RKB uses a floating-point atomicAdd ; the rest appeared deterministic on inspec-tion and under testing (§6.2), so the benefits outweigh the disadvantage. 

Determinism vs. Race-Freedom. The two often occur in tandem, but they are defined differently and neither implies the other. Data races are violations of synchronization rules 

agreed upon by a community, and there are many definitions rather than one universally accepted one. Evidence for a data race must include execution-internal details to show the violation. Nondeterminism is externally observable, and two executions that produce a different output on the same input suffice as evidence. 

3.1 Characterization 

RESOLVE looks for races by delaying memory operations and comparing the kernel’s full output bitwise against an unperturbed run. Delaying an access that races with another changes which of the two lands first, and the kernel can produce a different result. SuperCollider [43] applies the same idea to individual memory accesses, which it reaches through a compiler pass. The difficulty is knowing where to delay: a GPU kernel runs enormous numbers of threads over large tensors, and delaying at random took hours per kernel in our pilot runs. Conflicting memory accesses are not spread evenly, though: whole memory regions and levels of the thread hierarchy may admit none at all. Since determinism bugs do not occur without conflicts, there is no point in testing such accesses. RESOLVE therefore measures the kernel in three passes over the binary, counting, tracing, and perturbation (Figure 1), placing delays only where the trace shows a conflict is pos-sible. This brings the median time to test a kernel in RKB down to 88 seconds (§6.2).

Does the schedule change the output? The third pass inserts the delays: NVBit places a call before a selected mem-ory instruction, and that call stalls the issuing thread for up to a set number of cycles, with a configured probability so that not every execution is delayed. Perturbing a schedule to expose a concurrency bug is an old idea, and the search has to be bounded somehow: by systematic exploration [30], by randomized scheduling with a probabilistic guarantee [5], by directing it at reported races [39], or on GPUs by bounding the number of delays and directing them at conflicting atomics [10]. We bound ours by scope, using the trace to decide where a delay could matter, which keeps the binary as the only thing we need. RESOLVE is configured with a memory region, global or shared, and a scope, and delays only the instructions the trace placed there. An inter-block delay derives the stall from the CTA index; an intra-block delay derives it from the warp identifier. A conflict across CTAs is exposed by separating CTAs, not by reordering warps inside one. How many CTAs to perturb is a configuration knob here too. The cycle count and probability are parameters we fixed rather than results. Surprisingly, neither mattered: §6.2 shows detection did not change across the ranges we swept. RESOLVE compares the perturbed runs against an unper-turbed baseline, byte for byte on the same input, stops at the first difference, and reports that difference and nothing else. Turning it into a root cause is separate work. In §6.4 agents did that from these reports, and each proposed fix was validated by running the same test again. 

Limitations. RESOLVE does not perturb every scope, and the gaps follow from working at the binary level. We have no way to slow an asynchronous load through what NVBit ex-poses. We attempted to perturb intra-warp races and could not: every instrumentation site is bracketed by BSSY and 

BSYNC , the SASS instructions that synchronize and recon-verge warp control flow, so the independent thread scheduler never gets the chance to interleave differently. Conflicts be-tween CTAs that are never resident at the same time are also out of reach; SuperCollider shuffles block identifiers to bring such pairs together, which needs compiler access that we do not want to require. A clean campaign is not a proof of race freedom, but surviving it is strong, language-agnostic, black-box evidence that the kernel computes a deterministic function, which is what the rest of RESOLVE needs. 

## 4 Reduction 

Concurrency, more than size, is what puts a fully optimized GPU kernel out of reach of a verifier. The functional prop-erties of asynchronous copies, TMA, producer-consumer pipelines and the barriers coordinating them have not been formalized, especially the corner cases that arise when us-ing these synchronization constructs. Modeling each new construct as it arrives has not kept pace with the hardware. However, verification tools do work on much simpler pro-grams, so RESOLVE reduces the kernel to one of those. Reduction runs on a candidate that passed determinism testing (§3) and whose output differs from the reference. When their outputs agree bitwise on every test, RESOLVE stops there: the candidate has been tested to compute a func-tion, and that function matches the reference. Reduction could produce the same program from both sides, and the proof step would add nothing. This is not unusual, since 15 of the 100 pairs in RKB are bitwise identical (§6.2). An agent is instructed to rewrite each kernel using as little concurrency as possible: 

• Barriers, atomics, cooperative launches and warp prim-itives are rejected, including inside headers, macros, template expansions and inline PTX. 

• Multiple kernel launches are allowed. Splitting a large fused kernel into several simple ones is usually easier Vedadi Gargary et al. 

than flattening it into one, since we minimize concur-rency and not launches. 

• Repeated statements should become loops and shared code should become functions, since the later proof effort grows with bulk. Reduction usually reaches a single thread, but not always. The exact floating-point behavior of tensor cores is diffi-cult to model in one thread, especially across data types, and could evolve across architectures. We expect the future to bring more such instructions. Rather than reduce away from them, we allow the least concurrency the instruction requires, which for a tensor core is a single warp, and for the warpgroup instructions on Hopper is four. Modern verifica-tion tools such as Kuiper [28] provide semantics for these instructions over the reals, so the reduction can keep them rather than imitate them. The floor is set by the instruction, which is why the rule is as little concurrency as possible and not a single thread. A reduction is accepted only if it reproduces the output of the original, bitwise, on every tested input. There is no tolerance, no epsilon and no normalization in this compari-son. We have found modern agents, with the testing tooling available to them, very capable of producing reductions that pass. The result is now a simplified program that a verifier can reasonably handle. 

## 5 Proof 

After reduction, we are left with two simple programs, each bitwise equal to the original kernel they replace. Yet, their outputs still differ from each other. Such a difference may be benign and not indicative of a bug: algebraically sound changes like reassociating a reduction, distributing a product over a sum, or using fused-multiply-add instruction instead of doing the operations individually can change rounding behavior when using floating point numbers, and cause low-order bits to differ. In practice, many such rewrites are rou-tinely done by programmers when they believe they can increase performance, as long as some final numerical error check stays within bounds. This is unsatisfactory since there is no principled way to define acceptable error, or which of the two programs is more correct than the other (without using a higher-precision reference). We rely on testing too, but only for bitwise equality. The problem is the tolerance, not the testing: someone has to choose it, and that choice decides which bugs stay visible. In our approach, we aim to prove that the programs satisfy a common algebraic specification, where numerical error is ignored, and one can only reason symbolically about the result. That is, we do not intend to prove that the outputs on each side are “close enough” (in fact we do not even want to define what such a thing would mean) but instead prove, formally, that they both morally compute the same algebraic expression and, that if the precision of floats was infinite, they would match exactly and compute the exact same real number. This approach was introduced by Kuiper [28], where the authors introduce an abstract “approximation” relation ( ≈)between floating point numbers of any precision and real numbers. ## 6 Evaluation 

We evaluate RESOLVE on three sets of kernels, each fused more aggressively than the last, ending with production mega-kernels where it exposes real bugs and validates the agent-written fixes. (§6.2) On the KernelBench corpus [35] we demonstrate how RESOLVE operates on a breadth of simple kernels of the kind agents are commonly asked to optimize. We perform a mutation study to explore how hard concurrency errors are to catch, and we reduce and prove a subset of the corpus. (§6.3) We examine three implementations of a fused MLP kernel, critical to modern LLM implementations, span-ning three widely used performance-oriented languages: CUTLASS, Gluon and Triton. For all three kernels we test, reduce and prove the optimized variant against a PyTorch reference. (§6.4) We turn to mega-kernels, which fuse wider spans of a model into a single launch. The determinism tester exposes bugs in several of them, along with other behavior that diverges significantly from their refer-ence implementations, and for two we show an agent repairing the kernel with the fix tested by RESOLVE. The RESOLVE stages vary in how much time and tokens they consume. The determinism tester is cheap: it samples rather than tracing everything, prunes the scopes where a kernel can have no conflict, and works on the compiled bi-nary. That leaves it fast enough to run in a tight loop, or inside a full application wherever a deterministic output can be logged and checked (§6.4). Reduction, specification and proof are agent tasks and are much slower and more costly. In our context, this is acceptable, given that the primary goal of RESOLVE is to validate kernels as part of a larger auto-matic optimization system which can run without human interaction, not an interactive tool for hunting bugs. 

6.1 Setup 

All experiments run on a server with four NVIDIA H100 PCIe GPUs, sm_90 with CUDA 13.0, hosted on an AMD EPYC 9554 running Linux 6.8. Independent jobs take one GPU each, and no two experiments share a GPU. Agents appear throughout. They perform the reductions, write the specifications, write the Kuiper programs and check that each one reproduces the execution it stands for, along with tasks particular to each experiment, such as mutant generation in §6.2 and kernel repair in §6.4. Every agent runs through the Copilot CLI with reasoning effort set to max, on GPT-5.6. Our corpus is not rich enough to calibrate the determinism tester empirically, so we use settings that pilot experiments found practical: four unperturbed runs, delays of up to 5,000 cycles inserted with probability 0.8, a 200-million-record memory tracing cap, and eight randomly chosen CTAs for both tracing and perturbation. Section 6.2 shows that cap is large enough to identify the memory regions and scopes worth testing. Baselines are written in PyTorch and executed in eager mode. We assume they are deterministic, which informal runs of our determinism tester corroborate. All system and GPU calls are checked for errors.

An agent critic discards the attempts where the mutator had no site to apply to, such as a kernel with no barrier to remove or no shared destina-tion to alias, which accounts for 202. Of the 198 that remain, a further 55 fail to run and are excluded. This leaves 143 mutant kernels. The determinism tester flagged 92 of the 143 synchro-nization mutants. Testing one took 405 seconds on average, ranging from 88 to 4,587. A catch costs less than a clean run, because the tester stops at the first mismatch: the 92 it caught averaged 256 seconds and none took longer than 1,091. We reviewed all 51 misses with the help of an agent, and they fall into three groups. Three are mutants injected into code that never runs, so there is no fault to catch. Twenty-eight introduce a race that never changes the value the kernel finally writes. The mutated kernel is still deterministic, which is the property RESOLVE checks, so it has nothing to report, and these 28 are exactly the case §3 makes when it separates a data race from a nondeterministic result. The remaining 20 place their conflict inside a single warp, where no delay we can insert will separate two threads and we know of no perturbation an NVBit-based tool could apply to expose them. Every mutant that made a kernel nondeter-ministic and lay within reach of binary instrumentation was caught. Reaching inside the warp needs compiler support or a static analysis, and is future work. Per-mutant results are given in the artifact. Of the 92 we catch, 90 mismatch across repeated runs with no perturbation at all. Only two need a delay to expose them. 6.3 A Fused MLP Kernel 

The kernel fuses the up projection, the gate projection and the SwiGLU activation of an MLP block, the arrangement used by current models such as Qwen. Written the usual way this is three kernels, and the two projections must write their results to memory for the activation to read them back. Fus-ing the three removes four passes over those intermediates and makes the block run up to 2 .5× faster than the PyTorch implementation of the same block. Neither PyTorch’s com-piler nor TensorRT performs the fusion, because it has to cross two projections that use different weight matrices. At the time of writing, no compiler will automatically produce this kernel. Our reference is PyTorch in eager mode, where the three operations run as three kernels. Against it we place three ag-gressively optimized variants, one each in Triton [44], Gluon [45] and CUTLASS [32], each fusing the work into a single kernel and each written with the help of an agent. They are the fastest implementations of this operation we are aware of. We validate them at a representative size, a hidden dimen-sion of 8,192 and an FFN intermediate size of 29,568 against 4,096 rows of activations. None of the three matches the ref-erence bitwise, because the fusion reorders the reductions, and all three are intricate enough that correctness cannot be taken for granted. Gluon and Triton do match each other bitwise, so we carried only Gluon through specification and proof. As far as we are aware, these kernels are out of reach for existing rigorous validation, on both halves of the problem. For concurrency, Compute Sanitizer [34] runs on all three and reports nothing, which is the answer we expect and also all it can offer: a clean race report says neither that the kernel is deterministic nor that it computes the reference function. An agent optimizing a kernel should be able to move it from any one of these languages to another and still know it computes the same function, which is what RESOLVE gives it. 

6.4 Mega-Kernels 

A mega-kernel takes fusion further again. Where §6.3 fuses three operations into one kernel, these fuse much wider spans of a model, and they are the most aggressively fused GPU code we know of. We ran RESOLVE over three of them, each in its single-GPU configuration. 

• LUCE [11] fuses all 24 decoder layers of a hybrid DeltaNet and attention model into a single launch. 

• FlashMoE [2] fuses the routing and expert dispatch of a mixture-of-experts layer. 

• FastMoE [15] provides a native capacity-pruning ker-nel for mixture-of-experts routing. We also attempted Mirage [9], which compiles a model into a persistent mega-kernel. It hung when run under our determinism tester and we could not diagnose why, so we report nothing for it. Per-system configurations are given in the artifact. 

Testing mega-kernels. These kernels differ from every-thing above in one practical respect: they do not come with kernel executors. Each is embedded in a larger framework and is exercised only through that framework’s own tests. Our first pass therefore runs the determinism tester over those existing test suites, with an agent identifying outputs that should be deterministic and logging them at each stage of the pipeline. That the determinism tester can be pointed at code in this shape is a consequence of working at the binary. It is at its most convenient given a kernel executor, but NVBit will instrument nearly any NVIDIA binary, so the requirement reduces to identifying an output that should not change between runs and logging it. Nondeterministic outputs. All three mega-kernels be-haved nondeterministically. An agent could then work on each one with the determinism tester in hand, guessing at a cause, re-running the tester to check the guess, and narrow-ing the search by delta debugging [51]. Four root causes came out: two in LUCE, one in FlashMoE and one in FastMoE. LUCE’s two are plainly bugs. In the grid barrier, block 0 resets the arrival counters while other blocks may already be arriving, and __syncthreads() cannot order one block against another. The blog post that introduces the kernel mentions hitting grid synchronization problems during de-velopment [11], so a barrier problem is not a complete sur-prise. The second one looks unknown: several attention blocks write the same global scratch buffer, because the ad-dress they compute for it carries no block or head offset, and nothing we found mentions it. The barrier was also the only one that showed up reliably without perturbation. The other three needed inserted delays before they appeared consistently. The two routing causes are harder to classify. Both come from capacity. When an expert fills, routed tokens are dropped, and in both systems the tokens that get dropped depend on the order blocks arrive: FlashMoE reserves slots with atom-ics, and FastMoE prunes with atomicSub . Every reference implementation we know of routes deterministically and drops the same set of tokens once capacity binds. ## 7 Related Work 

Determinism and race freedom. Data-race freedom buys a simpler model to reason in, since a program without races behaves as though the machine were sequentially consis-tent [1]. Determinism buys something similar and has its own history, going back to determinacy races in Cilk [14] and to runtime checks that a program’s output does not depend on the schedule [6]. Type systems can guarantee determinism statically, on the CPU [4] and on the GPU [20]. Lipton reduction merges statements into coarser atomic blocks [13, 25]. Sequentialization goes further and emits an equivalent sequential program [18, 21]. These are complete guarantees, but require source code to be available. By con-trast, we run the binary under perturbation and watch the output; §6.2 lists the mutants that slip past. However our approach scales to binary kernel compiled from in Gluon or CUTLASS. 

Verified optimizers. Tools like CompCert and Exo pro-vide general correctness guarantees, one by verifying the compiler [22] and the other by building schedules only out of transformations already known to preserve semantics [17]. A long line of work checks that the output of the optimizer is equivalent to its input for each particular run, instead of trusting or verifying the tool. Translation validation checks a single compilation instead of the compiler [31, 37]. Alive2 takes two LLVM functions and determines refinement by encoding the problem to SMT [26]. This approach has also been used in superoptimizers to ensure correctness [38]. For tensor programs the same problem appears as graph substitutions, either verified up front [19] or allowed to be wrong and patched afterwards [48]. RESOLVE by contrast takes an even more radical approach: not only do we check each problem individually, we also pick a separate notion of equivalence for each problem (by deriv-ing a natural spec that both programs are verified against). 

GPU semantics. Formal models of GPU behavior tend to show up well after the hardware. A first memory con-sistency model was pinned down empirically in 2015 [3]. NVIDIA published a formal one four years after that [27]. Testing hardware against such models at scale still finds vio-lations [23]. Execution inside a warp has no official model, only a proposed operational semantics [8]. Forward progress between workgroups is undefined, and the candidate models had to be run on real hardware to see which ones held [42]. Named barriers got a model built to verify them [40]. Ten-sor core arithmetic has an SMT formalization, though not from NVIDIA [46]. Scoped data-race freedom is a cleaner foundation [16], but it only covers programs that respect the scopes, which an aggressively tuned kernel may not. None of this blocks RESOLVE’s determinism tester, since it does not require a formal model of each hardware feature. It only tests the general property that how long a memory access takes should not change the semantics of a program. Therefore we can verify kernels that use named barriers without even needing to know what named barriers are, let alone have a correct and practically usable formal semantics Vedadi Gargary et al. 

for them. Kuiper however still requires semantics for features that are used in the sequentialized kernels, and that blocks two kernels using certain thread-local operations (§6.2). 

## 8 Conclusion 

RESOLVE combines testing, reduction, and proof to validate optimized GPU kernels across languages and frameworks. Our evaluation evaluated 31 KernelBench Level 1 kernels, three fused MLP implementations in CUTLASS, Triton, and Gluon against a common PyTorch reference, and a mixture-of-experts kernel from an existing system. The determinism tester also caught 92 injected synchronization faults and exposed four previously unreported issues in production mega-kernels, including two clear bugs. These results show that the approach can both uncover errors in deployed code and support validation of optimizations beyond the verifier’s direct semantic coverage. As agents take on more of kernel development, they need validation they can trust, enough de-tail to debug what fails, and the freedom to write in whatever language is fastest at the time.
