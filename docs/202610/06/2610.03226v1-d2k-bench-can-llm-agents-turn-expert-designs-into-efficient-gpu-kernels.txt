D2K-BENCH: Can LLM Agents Turn Expert Designs into
Efficient GPU Kernels?
Daifeng Li1,2, Huiqiang Jiang2, Chengruidong Zhang2, Wei Wu3
Xudong Guo2, Jianhong Tu2, Jianwei Zhang2, Binhang Yuan1, Dayiheng Liu2
1HKUST, 2Alibaba Group, 3USTC
Abstract
GPU kernels generated by large language model (LLM) agents can remain less efficient than expert
implementations, but runtime alone does not reveal how the gap relates to design discovery and
implementation. We introduce D2K-BENCH, a diagnostic benchmark of 26 tasks and 85 workloads
that measures how effectively agents translate expert design guidance into efficient GPU kernels. The
guidance covers L1: high-level algorithmic insights, L2: dataflow design, and L3: low-level optimization
tricks, including dependencies among these levels. Pairwise runs with and without guidance share
task descriptions, workloads, tools, hardware, and a 350-turn budget. Complementary assessments
examine independently proposed designs and the design properties implemented in generated code.
Across five models on NVIDIA B200 GPUs, guidance raises correctness over 130 model–task pairs from
93.1% to 98.5% and increases the Performance Score over all 26 tasks from 1.46 to 1.95. For the three
frontier models with correct submissions on all 26 tasks in both runs (GPT-6-Astra, Claude-Opus-4.8,
and GPT-5.6-Sol), geometric mean speedup increases from 1.69× to 2.49×. Across all five models, the
mean combined implementation score increases from 57 to 70 out of 100. These results show the
value of expert design guidance while identifying design properties that remain unimplemented.

Introduction
In modern machine learning systems, GPU kernels usually execute the core computations of machine learning
workloads, and their efficiency significantly affects training and inference latency, throughput, and GPU
operating cost. Recently, large language model (LLM) agents have offered an effective way to automate GPU
kernel development through code generation, compilation, testing, profiling, and iterative optimization [1, 2].
Although these development loops can improve performance, the generated GPU kernels could still be less
efficient than expert implementations [3]. Concretely, the LLM-generated kernels and expert implementations
could differ in their algorithms, dataflow, and low-level optimization techniques. In this paper, we investigate
how effectively LLM agents can translate expert design guidance into efficient GPU kernel implementations.
Understanding the performance gap between LLM-generated kernels and expert implementations helps
target improvements in automated kernel development. The accurately identified gap can inform whether
agents need better support for discovering effective designs, implementing and tuning those designs, or both.
Algorithmic and dataflow choices can reduce computation and memory traffic, but their benefits depend on the
generated code preserving these savings while using GPU resources effectively. Recognizing a promising design
therefore does not ensure that an agent can achieve its performance potential. Useful diagnostics should
connect an agent’s design choices, their implementation in code, and measured runtime to identify limitations
that warrant further investigation. Without such evidence, additional tuning may leave an inefficient algorithm
or dataflow unchanged, while further design guidance may fail to resolve implementation limitations.

However, assessing how effectively agents translate expert design guidance into efficient kernels is difficult since
the execution time alone does not clearly reveal which design choices the generated code implements or how
well it implements them. An agent must identify an effective algorithm and dataflow, then implement those
choices through correct code, GPU execution mechanisms, and tuning. For example, FlashAttention combines
online normalization with tiled computation to avoid storing the full attention matrix [4]. Discovering this
design reveals an opportunity to reduce memory traffic; implementing the design further requires coordinated
computation and data movement, careful GPU resource management, and tile-size tuning. Runtime alone
cannot reveal where an agent falls short. Assessments of independently proposed designs and executable
source provide complementary evidence about design discovery and implementation.
Existing benchmarks evaluate kernel correctness and performance in different ways: KernelBench evaluates
speedup over PyTorch, SOL-ExecBench uses analytical hardware-performance estimates, and FastKernels
evaluates generated kernels against production implementations [1, 3, 5]. Prior work also studies optimization
guidance and generated code: KernelBench examines hardware knowledge and optimization examples, Hari
et al. [2] use Speed-of-Light guidance and LLM-based integrity review, and Shui et al. [6] compare expert-
assisted and autonomous kernel development. On the other hand, we focus on a diagnostic approach that
can connect task-specific design guidance, pairwise comparisons with and without guidance, and structured
assessments of independently proposed designs and generated code. This combination makes the assessed
design properties explicit and relates their implementation to correctness and runtime.
We introduce D2K-BENCH, a benchmark that connects performance comparisons with assessments of design
discovery and implementation. Expert design guidance and pairwise comparisons with and without guidance
make both guidance benefits and unimplemented design properties observable. We make the following
concrete contributions:
Contribution 1. We construct a targeted diagnostic benchmark of 26 tasks and 85 workloads, pairing task
descriptions with selected expert references and task-specific design guidance (Section 2). The guidance
covers L1: high-level algorithmic insights, L2: dataflow design, and L3: low-level optimization tricks, and records
dependencies among these levels. This structure captures algorithmic transformations, data representation
and movement, and GPU execution mechanisms within a common framework for guidance and assessment.
Contribution 2. We develop an evaluation protocol that compares kernel performance and design implementa-
tion with and without expert design guidance (Section 3). The runs in each pair use the same task description,
workloads, Triton implementation language, tools, and hardware; guidance provides explanations without
expert source code or prescribed tuning parameters. An LLM judge assesses independently proposed designs
and executable source evidence, with runtime hidden for source assessment and credit for correct alternative
designs. Source comparisons use all 26 tasks in both runs, providing a diagnostic of implemented properties
on these tasks and the shortfall that remains under guidance.
Contribution 3. We characterize the benefits and limits of expert design guidance across five models on NVIDIA
B200 GPUs (Section 4). Guidance raises correctness over 130 model–task pairs from 93.1% to 98.5%. The
Performance Score is computed over all 26 tasks for each model and increases from 1.46 to 1.95. For
GPT-6-Astra, Claude-Opus-4.8, and GPT-5.6-Sol, which have correct submissions on all 26 tasks in both
runs, geometric mean speedup increases from 1.69× to 2.49×. Across all five models, the mean combined
implementation score increases from 57 to 70 out of 100, while guided code still leaves assessed properties
unimplemented. Additional analyses examine cumulative guidance in a fixed level order and an illustrative
implementation. The evaluations separately assess agents’ independently proposed designs and their ability to
implement supplied expert designs in executable code, and relate these assessments to kernel performance.

Benchmark Design and Construction
We introduce how we select the benchmark tasks (Section 2.1), construct the inputs provided to agents
(Section 2.2), and derive expert design guidance for each task (Section 2.3).

2.1
Benchmark Task Selection
D2K-BENCH contains 26 GPU kernel optimization tasks. Each task includes at least two different configurations;
we use the term workload to refer to one task with a particular configuration. The benchmark includes 85
workloads in total. The tasks and workloads are carefully selected by experts from systems and specialized
implementations such as vLLM [7], SGLang [8], and FlashAttention [4]. We select tasks whose expert-written
implementations reduce computation or memory traffic through algorithmic transformations or dataflow
changes, with low-level kernel optimizations providing further performance gains. The resulting suite spans
common kernel development scenarios in LLM training and inference, including attention, mixture of experts,
and quantization. Appendix Table 3 summarizes the tasks by operator category along with the representative
expert design ideas in each group.
For each task, we include one expert implementation over the task’s corresponding workloads, i.e., the expert
implementation is used across all workloads for one task. We validate the outputs and track the state updates
against the PyTorch reference under the task’s numerical tolerances and verify that execution invokes the
selected B200 expert kernels.
2.2
Task Specification
For each task, we construct a set of shared task files that specify what the agent must implement and how
the task will be evaluated. These files include a task description, workload definitions, an input generator,
a PyTorch reference, implementation requirements, and a solution.py template with an unimplemented
run(...) entry point. The task description defines the required outputs, numerical tolerances, and state
updates; workload definitions specify tensor shapes, data types, and layouts. We derive the task description
and workloads from APIs, documentation, tests, and representative model settings. The implementation
requirements mandate custom kernels for the target operator and prohibit calls to the PyTorch reference or
existing implementations of that operator.

2.3
Expert Design Guidance
Expert design guidance connects algorithmic choices to their implementation. In the guided configuration,
this guidance is made available to the agent alongside the shared task files defined in Section 2.2. Expert code
supplies the design choices; corresponding technical documentation and comments clarify their intent. We
organize the guidance into three levels:
• L1: High-level algorithmic insights. Such guidance states the algorithmic transformation, why the proposed
algorithmic insight would preserve the operator’s required behavior, and the computation or data movement
it could optimize.
• L2: Dataflow design. The guidance specifies where variables should be produced, stored, and consumed,
together with their layouts and lifetimes. The guidance also identifies intermediate variables that can be
reused or avoided.
• L3: Low-level optimization tricks. The guidance explains how execution mechanisms implement the design,
such as optimizing pipelining to overlap data movement with computation and warp specialization to

The guidance records dependencies among the three levels to explain how the design choices work together.
These dependencies connect an algorithmic transformation to the data representation and movement it
requires, and then to the GPU execution mechanisms that preserve its benefits. They specify the cross-level
dependencies among algorithmic, dataflow, and low-level execution choices, including the required ordering
and state transitions.
Example expert guidance for Muon orthogonalization kernel. We provide the corresponding example of the expert
guidance for the Muon orthogonalization kernel. The Muon guidance replaces repeated updates of the large
rectangular matrix with composition on smaller square matrices (Figure 1(b)). At L1, the guidance defines
Pk = akI + bkRk + ckR2
k. In exact arithmetic, since Xk+1 = PkXk, steps 0 through j can be composed
into Q = Pj · · · P0. The resulting rectangular matrix is then computed as Xj+1 = QX0 in a single matrix
multiplication, avoiding explicit computation of the intermediate rectangular matrices X1, . . . , Xj. Meanwhile,
the Gram matrix is updated directly as Rk+1 = PkRkP⊤
k , rather than recomputed as Xk+1X⊤
k+1. This
algorithmic transformation preserves the result in exact arithmetic while replacing repeated rectangular-
matrix updates with composition on smaller square matrices. At L2, the dataflow keeps rectangular X fixed
throughout each composition segment, while square states R and Q are updated and reused across consecutive
polynomial steps. The updated rectangular matrix is materialized only at the segment boundary by applying Q
to X. Before step k=2, the fixed restart applies the composition of steps 0 and 1 to X, rounds to FP16, rebuilds
R = XX⊤to limit numerical drift, and initializes a fresh Q = a2I + b2R + c2R2 for steps 2 through 4. At L3,
the kernel execution schedule respects these data dependencies: square-state matrix-product kernels execute
within each segment, and rectangular products apply Q at restart and final boundaries after the corresponding

square-state updates are complete. To avoid redundant arithmetic, symmetric-product kernels compute one
triangle and reuse each tile’s accumulator for the original and transposed stores, writing diagonal tiles only
once.
For each task, we prepare two LLM-judge prompts: one assesses an independently generated written design,
and the other assesses generated implementation code. The written design is elicited in a separate agent run
described in Section 3.3. Both judge prompts combine the task description, task-specific design criteria, and
shared assessment instructions. These criteria form the design specification, describing the expert’s design
choices, the costs they remove, and the requirements for combining them correctly. The design-assessment
prompt includes the agent’s written design; the implementation-assessment prompt includes the three levels
of guidance, the expert implementation, and the candidate source code. The scoring procedure is described in
Section 3.3.
3
Evaluation Protocol
We describe the agentic evaluation pipeline with and without expert design guidance (Section 3.1), define the
measured performance score Sperf (Section 3.2), and define the LLM judge scores for independent designs,
JSdesign, and generated implementations, JSimpl (Section 3.3).
3.1
Agentic Evaluation Pipeline
For each model and task, we conduct paired agentic optimization runs with and without expert design
guidance. Each run follows the same pipeline: task initialization, iterative kernel optimization and evaluation,
and final submission selection. Figure 2 illustrates the agent loop and its interaction with the evaluator
sandbox.
Task initialization. Each agentic execution starts with an agent workspace containing the shared task files
defined in Section 2.2. The guided run additionally receives the expert design guidance from Section 2.3,
covering all three levels, together with instructions. This additional input is represented by the dashed branch
in Figure 2. Expert source code is unavailable to the agent in both runs. The two runs otherwise use the same
implementation language, tools, hardware, and optimization budget.
Iterative kernel optimization and evaluation. The agent develops candidate implementations by editing the
supplied solution.py template shown in Figure 1(a). The template specifies the task-specific signature of
run(...) and leaves the function body unimplemented; the agent implements this function to produce the
required outputs and state updates. The agent interacts with the execution sandbox through Model Context
Protocol (MCP) tools: read and write support file inspection and implementation editing, bash executes
compilation and profiling commands, and submit invokes the evaluator. On submission, the evaluator loads
the candidate file and calls run(...) with inputs prepared for each workload according to the task description.
The agent uses the returned correctness and timing feedback, together with profiling tools such as NVIDIA
Nsight Compute (ncu), to diagnose bottlenecks and revise its implementation. This process forms an iterative
loop of implementation, compilation, testing, profiling, and revision.
Final submission selection. Both runs use the same fixed turn limit and selection procedure. One agent
turn consists of a model response requesting one or more tool calls, execution of those calls, and return
of their results. A candidate is eligible for final selection only if the candidate passes the correctness and
implementation checks and has valid latency measurements on every workload of the task. For each eligible
candidate, we compute the geometric mean of its speedups across the task’s workloads, as defined in
Section 3.2. Among eligible candidates produced within the turn limit, we select the one with the highest
geometric mean speedup as the final submission.

Correctness and implementation validity. A task is scored as correct only if its submission satisfies both the
correctness criteria and implementation requirements on every workload. Violations of the implementation
requirements count as incorrect even when numerical outputs are correct. Correctness checks cover numerical
outputs, updates to mutable inputs, repeated execution on new inputs, and, where applicable, distributed
behavior. We check compliance with the custom-kernel requirements in Section 2.2 using abstract syntax tree
(AST) analysis, static keyword scans, and inspection of libraries linked during compilation. For distributed
tasks, we inspect communication traffic to verify that the required communication occurs. Manual review and
unit tests check compliance with the full task description, including all required outputs and state updates.
Execution latency timing. We measure GPU execution time for one call to the candidate run(...) entry point,
including its kernels and required communication. Input construction, compilation, and evaluator setup are
excluded from the timed region. The evaluator controls input preparation and state restoration to provide
equivalent inputs to all implementations. For distributed tasks, the reported latency is the maximum across
participating ranks. All implementations of a given workload use the same timing procedure. For tasks with
very short kernel execution times, such as decoding, we capture repeated calls to run(...) in a CUDA Graph
that takes at least one second to execute and replay the graph five times. For other tasks, we use CUDA events
to time batches of repeated calls to run(...), with each batch lasting at least one second. In both modes, the
reported latency is the arithmetic mean of repeated per-call measurements.

3.3
LLM Judge Scores for Designs and Implementations
Correctness and runtime alone are not able to completely reveal which design choices an agent implements
or can propose independently. We therefore use QWEN3.8-MAX-0902 as an LLM judge (Figure 2) to assess
generated code and independent design proposals against the expert-derived design specification in Section 2.3.
Implementation assessment. For each task and input configuration, the judge assesses the generated code at L1
(algorithmic insights), L2 (dataflow design), and L3 (low-level optimization), as defined in Section 2.3. Each
level is scored from 0 to 100 using five anchors: absent (0), isolated fragments (25), partial implementation
(50), substantial implementation (75), and complete implementation (100). Intermediate scores are permitted,
and every score must be supported by exact code passages demonstrating the implemented design choices.

satisfy the assessed design intent, even if they differ from the expert code. Functional correctness is evaluated

Experiments
Our experiments assess the benefits and limits of expert design guidance across five models and 26 kernel
tasks. We use a budget of 350 agent turns per task (see Appendix A.2 for the experimental setup). We aim to
answer three key research questions: RQ1. How does the comprehensive expert design guidance at all three levels
affect correctness and end-to-end kernel performance? (Section 4.1); RQ2. How closely do LLM judge scores align
with measured end-to-end kernel performance? (Section 4.2); and RQ3. How does guidance at L1, L2, and L3
affect kernel performance? (Section 4.3).
4.1
RQ1: Correctness and Performance Gains with Expert Guidance
Comprehensive guidance improves both correctness and Sperf in Table 1. Across 130 model–task pairs,
correctness increases from 93.1% to 98.5%. Overall Sperf increases from 1.46 to 1.95, a 33.9% improvement.
All five models improve their Sperf under guidance. The expert implementation achieves Sperf = 2.33 on the
same 26 tasks. GPT-6-Astra, Claude-Opus-4.8, and GPT-5.6-Sol are correct on every task in both configurations,
so their Sperf is the geometric mean speedup over all 26 tasks. Their geometric mean speedup increases from
1.69× to 2.49×. For GLM-5.3 and Kimi-K3, tasks without a correct submission or valid timing contribute 0.5.
Appendix A.3 reports the individual speedups of the three models that are correct on all 26 tasks.
Summarized Answer to RQ1. Comprehensive guidance improves both correctness and performance across all
five models: correctness rises from 93.1% to 98.5%, and Sperf over all 26 tasks rises from 1.46 to 1.95. For
the three models that are correct on every task, geometric mean speedup increases from 1.69× to 2.49×.
4.2
RQ2: Alignment of LLM Judge Scores with Measured Performance
We assess whether the LLM judge scores in Section 3.3 align with measured end-to-end kernel performance
despite the judge having no access to runtime measurements. Table 2 compares JSdesign for independently
proposed designs, JSimpl for final implementations, and the measured performance score Sperf. Each value
aggregates the same 26 tasks for a model; implementation and performance scores are reported separately
for each guidance configuration. Our key findings are: (i) Implementation scores align with performance and
guidance gains. In both configurations, JSimpl follows the broad model ordering of Sperf. Guidance also increases
both scores for every model. Thus, despite having no runtime access, the judge captures both performance
differences across models and the direction of improvement under guidance. (ii) Independent design scores
also reflect broad performance differences. Higher JSdesign is generally associated with stronger unguided
performance. Appendix C.3 presents a concrete Muon case illustrating the design and implementation
assessments.
Summarized Answer to RQ2. Runtime-blind implementation scores align with broad performance differences
and guidance gains. Independent design scores also reflect broad performance differences. This alignment
is approximate and demonstrated across model aggregates.

Related Work
GPU kernel generation benchmarks. GPU kernel generation benchmarks vary in task and hardware coverage
and in the reliability of their evaluation [9]. KernelBench [1] established the task of producing a correct GPU
kernel that runs faster than the PyTorch reference; TritonBench [10] focuses on Triton operators, MultiKernel-
Bench [11] spans GPUs, NPUs, and TPUs, and DataKernelBench [12] extends the domain to database queries.
Evaluation methods also differ. Robust-kbench [13] and KernelBench-Verified [14] strengthen verification and
hidden testing, while KernelBenchX [15] and AgentKernelArena [16] analyze correctness, hardware efficiency,
and agent generalization. SOL-ExecBench [5] evaluates kernel performance against analytically derived
9


hardware bounds [17]. FastKernels [3] emphasizes production interfaces, and RealisticTritonBench [18]
uses framework pull requests and end-to-end tests. FlashInfer-Bench [19] studies serving workloads, while
Atrex-Bench [20] samples operators and shapes from production inference traces.
Kernel optimization by LLM agents. Agentic systems optimize kernels through iterative feedback, reusable
knowledge, and hardware guidance. AutoKernel [21] and TritonForge [22] organize compilation, testing,
profiling, and revision, while Astra [23] and CUDAMaster [24] add multi-agent or hardware-aware workflows.
KernelSkill [25] provides reusable optimization knowledge. AccelOpt [26] and DRTriton [27] learn from
prior implementations or synthetic data, while Xe-Forge [28] stages search under hardware constraints.
KernelFoundry [29] and QiMeng-Kernel [30] use evolutionary search or hierarchical planning. Hari et al. [2]
allocate search effort using a compact domain-specific language and Speed-of-Light guidance, and Shui et al.
[6] show that expert directions can improve final implementations in a B200 contest harness. A complementary
line of work develops programming systems that make computation, data movement, and scheduling choices
explicit, including Halide [31], Fireiron [32], Triton [33], and TileLang [34].
6
Conclusion
We propose D2K-BENCH, a new benchmark that measures how effectively LLM agents translate expert design
guidance into efficient GPU kernels. The benchmark pairs 26 tasks and 85 workloads with guidance on
high-level algorithmic insights, dataflow design, and low-level optimization tricks. Its evaluation combines
pairwise performance comparisons with assessments of independently proposed designs and generated code.
Across five models on NVIDIA B200 GPUs, guidance raises correctness over 130 model–task pairs from 93.1%
to 98.5%. The Performance Score is computed over all 26 tasks for each model and increases from 1.46 to
1.95. Guidance also raises the mean combined implementation score from 57 to 70. Guidance improves
performance, but agents still leave assessed design properties unimplemented.

# Five-step polynomial orthogonalization map
## Interface
The returned tensor has the same shape and dtype as \(G\). The ‘steps‘
argument is retained for call compatibility and must equal 5.
## Semantics
This benchmark isolates the matrix orthogonalization primitive used inside an
orthogonalizing matrix optimizer. It does not include momentum, weight decay,
learning-rate scaling, distributed communication, or parameter mutation.
For every matrix in a tensor \(G\in\mathbb R^{[\ldots]\times M\times K}\),
normalize independently in fp32, store the iterate in fp16, and apply the five
coefficient triples below in order.
\[

{\|\operatorname{fp32}(G)\|_F+10^{-7}}
\right),

A_i=X_iX_i^\top,\qquad
X_{i+1}=a_iX_i+\left(b_iA_i+c_iA_i^2\right)X_i.
\]
Leading batch dimensions are independent.

## The angles to think along
These are the fields the schema requires. They are the angles because each one is a question
that can be answered wrongly.
### Cross-level rationale
A chain is one causal story from a cost to its removal, carried through all three levels. For
each chain state:
- **bottleneck** – what actually dominates, at the registered shapes, and not in general.
- **level_1_high_level_algorithmic_insights** – what changes in the mathematics.
- **level_2_dataflow_design** – what that change does to which values exist, where, and for how long.
- **level_3_low_level_optimization_tricks** – what the execution has to do to keep the benefit.
- **cost_reduction** – the specific cost that no longer exists. Name it, do not say "overhead".
21


- **conditions** – the required order, the partial states that are invalid, and
the evidence that the chain is complete. This is the field that decides whether the chain
is a design or a wish: if a chain can be half-adopted and still look adopted, say what
distinguishes them.
### Level 1 – High-level algorithmic insights
Changes to the algebra, computation domain, recurrence, reduction, representation, or
precision semantics. Per item:
- **algorithmic_change** – the change itself.
- **correctness_basis** – why the result is still exact, or under exactly which condition the
difference is admissible. "Within tolerance" is not a basis; the condition is.
- **performance_mechanism** – why this is faster, in terms of a resource.
- **dataflow_consequences** – what level 2 now has to be.
- **constraints** – what is left open to the implementation, deliberately.
### Level 2 – Dataflow design
Specify where values are produced, stored, and consumed; their layouts and lifetimes; and which
intermediate values are reused or avoided. Per design:
- **overview** – who owns what, and what the operator looks like as a whole.
- **parallelism_strategies** – the exploitable parallelism, and how much of it exists **at the
registered shapes**. If a decomposition exposes fewer concurrent units than the machine
has, that is a property of the design and belongs here with the arithmetic.
Each entry gives its **name**, **description**, and **available_parallelism**.
- **stages** – per stage: operation, outputs, data layout, owner and residency,
consumers and lifetime, and the performance condition
that must hold for the stage to be worth having.
- In **data_layout**, describe indexing, shape, packing, or thread/register mapping. Put dtype
and result completion in **outputs**, ownership and storage domain in **owner_and_residency**,
and handoff requirements in edge **readiness**. State explicitly when a layout is unspecified.
- **edges** – per edge: **from**, **to**, **value**, **storage_and_lifetime**, and **readiness**.
- **restrictions** – values that must never be materialized. Each entry costs
something: it forbids a structure. Only forbid what you would still forbid after measuring,
and if a prohibition depends on a shape or a device property, say so in the entry rather
than stating it unconditionally.
- **adoption_criteria** – how a reader decides, from an implementation, whether this design was
adopted. Each check should be decidable by looking at code, not by asking the author.
### Level 3 – Low-level optimization tricks
Execution mechanisms that realize the algorithm and dataflow design, such as software pipelining
that overlaps data movement with computation; warp or warp-group specialization and roles;
producer-consumer scheduling; load balancing; required ordering and synchronization; layout
transition instructions; and architecture-specific mechanisms. Do not repeat Level 2 value
placement, storage residency, layout, or lifetime descriptions as standalone Level 3 ideas. Per item:
- **supports** – which level 1 or level 2 element this exists to preserve.
- **challenge** – the thing that makes it hard.
- **strategy** – what the execution does.
- **pitfall** – what a straightforward implementation does instead, and what that
costs.
- **constraints** – what stays tunable. State what must be *measured* rather than assumed. If a
choice rests on a hardware rate, say which measurement would refute it.
## What is not credit
- Naming a mechanism without the condition under which it holds.
- A prohibition with no cost attached, or one that would forbid the fastest legal structure.
- A bottleneck claim that does not reference this operator’s shapes.
- A ‘conditions‘ entry that only restates the chain.

C
LLM Judge Prompts
The implementation assessment and independent design assessment in Section 3.3 use separate user message
templates. The prompt blocks in Appendices C.1 and C.2 place the short shared system message immediately
before the user template as part of the complete request rather than as a standalone appendix item. Brace-
delimited fields are filled by the release scorer before transmission. Both assessments assign continuous scores
in [0, 100] at L1, L2, and L3 and use the equal arithmetic mean of the three level scores. The corresponding
scores are JSdesign and JSimpl, as defined in Section 3.3 and computed by the release scorer.
C.1

experimental direction remain hidden from the judge.

C.3
Muon Design and Implementation Assessment Case
In this case, we examine the following question: How does the LLM judge assess the independent design proposal
and the two implementations? We analyze Claude-Opus-4.8’s independent Muon design proposal and its two
submitted implementations, then explain the rationale for the assigned scores using evidence from the design
and code. Our code repository contains the full proposal, both submitted solutions, and the complete judge
outputs with code citations.
Independent design assessment. The proposal elicited without expert guidance retains the five-step recurrence
of the PyTorch reference in Section 2.2: the proposed method forms an M × M Gram matrix and writes
a new rectangular X after every coefficient step. The proposal also calls for computing one triangle of
symmetric square products and mirroring the off-diagonal tiles. Unlike the expert guidance in Section 2.3, the
proposal neither composes the polynomial actions in Q nor applies the fixed restart before coefficient 2; the
repeated rectangular updates therefore remain. The proposal’s cost argument counts a rectangular Horner
multiplication absent from the supplied PyTorch reference and uses 0.26 for the row-to-column ratio, which is
0.37–0.39 for the three registered workloads.
Implementation assessment. Without design guidance, the submitted code follows the PyTorch reference’s
stepwise recurrence from Section 2.2: the code forms a Gram matrix, computes a square polynomial action,
and writes a new rectangular iterate for every coefficient triple (source lines 210–214):
for (a_c, b_c, c_c) in _COEFFICIENTS:
_xxt_tma[sym_grid](X, A, M, K, B, RM)
_aa_tma[sym_grid](A, Bmat, M, B, b_c, c_c, RM)
_bx_tma[bx_grid](Bmat, X, Xn, M, K, a_c, B, RM, NUM_SMS=_NUM_SMS)
X, Xn = Xn, X
The square kernels exploit symmetry, but the loop leaves the cross-step rectangular dataflow unchanged. With
design guidance, the submitted code follows the main expert design in Section 2.3: the code composes the
polynomial actions in a square operator Q while advancing the Gram state, then applies Q to the rectangular
input once at the end (source lines 315–325):
X0 = normalize(G)
# [B, M, K] fp16
A = bmm_sym(X0, X0, transB=True)
# X0 @ X0^T -> [B, M, M] (symmetric)
Q = None
for i, (a, b, c) in enumerate(_COEFFICIENTS):
A2 = bmm_sym(A, A)
# symmetric
P = poly(A, A2, a, b, c)
Q = P if Q is None else bmm_sym(P, Q)
# Q symmetric (product of commuting sym P’s)
if i < 4:
T = bmm_sym(P, A)
# P@A symmetric (P is a polynomial in A)
A = bmm_sym(T, P)
# (P@A)@P symmetric
X = bmm(Q, X0, out_dtype=out_dtype)
# [B, M, K], cast fused into epilogue
The guided implementation follows the square composition strategy but omits the expert’s fixed restart before
coefficient 2. Here A is the square Gram state R of Section 2.3, and Q is the composed action Q. The guided
implementation uses the left Gram, which is the smaller side for the registered Muon workloads. The guided
implementation’s square kernel publishes an off-diagonal tile and its transpose from the same accumulator
(source lines 208–215):
# store (m, n)

# store transpose at (n, m) when off-diagonal
