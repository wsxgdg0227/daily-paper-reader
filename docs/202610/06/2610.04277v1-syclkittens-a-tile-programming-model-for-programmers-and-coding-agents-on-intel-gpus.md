## 摘要
新的 AI 加速器在能使其快速运行的 kernel 出现之前就已问世，因为要达到 kernel 峰值性能，需要操作数流水线和数据搬运技术方面架构特定的专业知识。如今，编程智能体可以自行编写、编译和调优 kernel，因此它们能够极大加速 kernel 的开发与优化。智能体产出的结果取决于赋予它们的接口。这些接口既可能暴露机器的原始能力，也可能编码了高效利用其硬件特性的已知有效方法。我们通过三个编码模型在三个 kernel 上的受控实验，测试了这两类接口在 Intel GPU 上的性能影响。使用原生 SYCL 和执行反馈时，所测试的三个模型中最强的 Opus 4.8 编写的单 GPU GEMM kernel 仅达到 Intel 调优过的 oneDNN 库的 57.5%。我们提出 SyclKittens，一种面向 Intel GPU 的硬件感知 Tile 编程模型，它编码了这些已知有效方法，因此其操作会将操作数置于矩阵引擎布局中、通过 L1 缓存预取，并通过将 GPU 堆栈连接为节点的 fabric 进行通信。在相同智能体、任务和反馈预算下，使用 SyclKittens 时，该智能体达到 82.1%，表明编码的方法能将硬件能力转化为性能。工作负载特定的策略仍可编程，工程师和智能体在 SyclKittens 中共同细化这些调度，构建出一个 kernel 套件，在多种 GEMM 形状上几何平均达到 oneDNN 的约 96%。该套件在单 GPU 上运行 Llama-3.1-8B 推理比 torch.compile 快 1.59 倍，在 Intel oneCCL 上比匹配的多 GPU 解码路径快达 2.91 倍。SyclKittens 开源，地址为 https://github.com/intel/SyclKittens。

## Abstract
New AI accelerators arrive before the kernels that make them fast, because peak kernel performance requires architecture-specific expertise in operand pipelines and data-movement techniques. Coding agents can now write, compile, and tune kernels on their own, so they could greatly accelerate kernel development and optimization. What agents produce depends on the interfaces they are given. These interfaces may expose a machine's raw capabilities or encode the known-good methods for exploiting its hardware features efficiently. We test the performance impact of these two interfaces on Intel GPUs through controlled experiments with three coding models on three kernels. With raw SYCL and execution feedback, Opus 4.8, the strongest of the three models tested, writes a single-GPU GEMM kernel reaching only 57.5% of Intel's tuned oneDNN library. We present SyclKittens, a hardware-aware tile programming model for Intel GPUs that encodes these known-good methods, so its operations place operands in matrix-engine layouts, prefetch through the L1 cache, and communicate over the fabric that links GPU stacks into a node. With SyclKittens under the same agent, task, and feedback budget, the agent reaches 82.1%, showing that encoded methods turn hardware capabilities into performance. Workload-specific policies stay programmable, and engineers and agents jointly refine these schedules in SyclKittens to build a kernel suite that reaches ~96% of oneDNN in geometric mean across GEMM shapes. The suite runs Llama-3.1-8B inference 1.59x faster than torch$.$compile on one GPU and up to 2.91x faster than a matched multi-GPU decode path on Intel's oneCCL. SyclKittens is open source and available at https://github.com/intel/SyclKittens.

# SyclKittens 论文深度总结

## 1. 核心问题与整体含义（研究动机与背景）

- **加速器先于 kernel 生态**：新的 AI 加速器往往在能发挥其性能的高效 kernel 出现之前就已发布。达到峰值性能需要操作数流水线、寄存器布局、数据搬运等方面的架构特定专业知识，这类知识目前主要由人工专家掌握。
- **编程智能体的机遇与依赖**：编码智能体已能自主编写、编译、基准测试并迭代改进单 GPU 与多 GPU kernel。但智能体产出什么，取决于被赋予的**接口**——接口可能只暴露机器原始能力（capability），也可能编码了高效利用硬件的**已知有效方法**（method）。
- **Intel GPU 生态缺口**：NVIDIA 有 ThunderKittens，AMD 有 HipKittens，多 GPU 有 ParallelKittens；Intel 侧此前只有把 ThunderKittens 直接移植到 SYCL 的探索性工作，缺少硬件感知的 tile 编程模型。
- **核心研究问题**：一个 tile 编程模型能否让 Intel GPU 的架构方法对**程序员和编码智能体**都可复用，同时保留工作负载特定的策略控制？
- **核心论断**：把架构的"方法"作为一等操作编码进接口，把"策略"留给用户，能把硬件能力转化为实际性能。

## 2. 方法论：核心思想与关键技术

### 2.1 三层抽象（Figure 1a / Figure 8）

| 层次 | 含义 | 归属 |
|---|---|---|
| Capability | 硅片暴露的原始能力（XMX/DPAS 指令、2-D block load、L1、MDFI/XeLink） | 硬件 |
| Method | 如何用好它的已知有效方法（矩阵引擎布局、L1 预取、协作式部分 tile） | **SyclKittens 编码** |
| Policy | 工作负载策略（tile 形状、预取距离与所有权、形状相关调度、stack/package 放置） | **程序员与智能体选择** |

### 2.2 实现形态与接口

- Header-only C++ tile 编程模型，后端 lowering 到 SYCL / SPIR-V；保留 C++ 控制流与直接 intrinsic 访问。
- 核心类型：`rt<T,M,N,layout,shape>` 寄存器 tile（row/column-major + 静态物理 base tile，支持 16×16 / 32×32 / 矩形）；`Global Layout (GL)` 把设备指针与逻辑 batch/depth/row/col 维度绑定；`Parallel Global Layout (PGL)` 将其扩展到多设备坐标空间。
- 分布式布局、peer memory、GPU 常驻同步把同一编程模型延伸到节点级。

### 2.3 三类 Intel 特定操作

**（1）矩阵操作数布局与打包**

- 把逻辑 tile 映射为沿 SIMD 方向的线性向量，固定使用 XMX 唯一接受的 **16-lane subgroup**，避免从 NVIDIA 32-lane warp 映射继承的 32→16 重排。
- BF16 下 32 元素行正好匹配一条 **64 B L1 cache line**；32×32 base tile 使每条 cache line 被立即完整消费，L1 事务数减半（消融：37.4% → 68.2%）。
- 对 column-major 右矩阵操作数 B，`load_transform` lowering 到硬件 `LoadTransformINTEL`，**融合 global 2-D block load 与 VNNI 打包**，省去软件 shuffle（实测 8192³ 从 106 → 147 TFLOP/s，+39%）。
- 与 ThunderKittens/HipKittens 不同，Intel Max GPU **没有 SLM 矩阵操作数加载**（无 `ldmatrix` 等价物），从 SLM 取 16×16 BF16 B 操作数需约 64 次普通读；因此选择 L1 直取路径。

**（2）协作式缓存预取**

- 把操作数投递拆为 **prefetch 阶段**（`prefetch_load` 发 2-D block 预取 hint，预热 L1，不写寄存器）与 **demand 阶段**（后续 2-D block load 载入寄存器），无需 SLM 暂存缓冲。
- `prefetch_load_coop` 接受子 tile 偏移，暴露 workgroup 内所有权：每个计算 subgroup 认领**不相交**的共享操作数区域，每个共享 cache 区域只被预热一次（partial-tile de-duplication）。
- 预取距离由 schedule 决定（平方形状多为 2，矩形多为 1–3），内核选择 unroll、snake traversal 等策略。

**（3）拓扑感知 GPU 通信**

- `make_pgl` 合并各设备 GL 与 peer 指针，`pgl.dev_ptrs[peer]` 让普通 load/store 直接访问远程 HBM；所有 GPU 共享一个 SYCL context。
- 同步协议：写方用 system-scope **release** atomic 发布完成，读方用 system-scope **acquire** atomic 等待；`signal` / `wait` / `barrier_all` 实现，无需返回 host。
- `topo::group_pvc` 把相邻 stack 归为 GPU package，`topo::plan_all_gather` 分配传输所有权。
- **层次化 gather**：每个源 shard 只跨一次 XeLink 送到每个远程 package 的一个 landing stack，再由该 stack 经 **MDFI**（同 package 内更高带宽链路）复制给伙伴 stack，从而把 XeLink 出口流量减半。

### 2.4 GEMM 主循环要点（附录 D）

- 每 subgroup 持有 32×64 fp32 累加器，K 维按 BK=32 流式；A 行主序、B 列主序（VNNI），经 2-D block load 进寄存器，直接 `mma_AB` 做 DPAS 收缩，并预取未来 A/B 面板。
- 特点：**无需 producer-consumer warp 分工、无 SLM 多级缓冲轮转、无每步 barrier**（对比 ThunderKittens 每 K 步 semaphore、HipKittens 每条矩阵指令两次 workgroup barrier）。
- 附加策略：snake-curve workgroup swizzle、32-way K 循环展开、bf16 输出就地降精度存储、split-K/Stream-K（针对小 M,N 大 K 的 decode 形状）。

## 3. 实验设计

### 3.1 任务与场景

- **单 GPU GEMM**：4096³ BF16 输入输出、FP32 累加。
- **分布式 GEMM**：12 GPU、行分片 6144³（及 12288³），A 行分片、B 复制，每 GPU 返回完整 C。
- **Causal GQA**：B=1, H=32, H_KV=8, N=2048, D=128。
- **kernel 套件**：27 个 GEMM 形状（13 平方 + 14 矩形，来自 Llama-3/BERT 风格推理工作负载），加因果 MHA、GQA、RMSNorm/LayerNorm/RoPE、split-K GEMV、多 GPU collectives、ring attention、融合分布式 kernel。
- **端到端**：Llama-3.1-8B 单 GPU（24 形状：B∈{1,2,4,8} × N∈{256…8192}）与整节点多 GPU decode（含 2D TP×CP 布局，至 256K 上下文）。

### 3.2 智能体受控实验设计

- **模型**：Opus 4.8、Sonnet 5、Haiku 4.5（同厂商大/中/小档），Claude Code 2.1.214 定制 harness。
- **三种编程上下文**：Raw SYCL（仅 Intel 文档）/ SyclKittens（加头文件与 API 文档，不含目标 kernel 实现）/ SyclKittens + examples（再加 NVIDIA/AMD 或其它算子的 kernel 源码，但**不含 Intel 目标 kernel 实现**）。
- **协议**：single-shot（不可编译执行）、cold-iterative（≤20 次 evaluator 调用）、warm-iterative（从合格 single-shot 源作为 checkpoint 0 继续）；每 model-context 3 个独立起点；最终用 5 个 held-out seeds 评分。
- **控制**：所有上下文允许直接 SYCL/SPIR-V intrinsic，禁止 oneAPI `joint_matrix`；GQA 全部条件禁用 ESIMD、使用字节相同的 raw-pointer harness；排除 Triton-XPU 作为上下文（会同时改变代码生成器与接口）。
