## ABSTRACT 

Open-ended scientific discovery often requires repeatedly proposing and evaluating candidate solutions. LLM-based systems can support this process by generating and refining executable solutions from verifier feedback. Methods such as TTT-Discover use test-time training (TTT) to update the solution-generating LLM from verifier feedback, adapting its generation policy to improve subsequent proposals on the target problem. However, this becomes expensive when reliable execution requires a large model, since training must maintain gradients, optimizer states, and policy statistics while repeatedly generating long, structured outputs. It also complicates credit assignment: outcome-level verifier feedback must jointly eval-uate the high-level strategy and its low-level implementation. In this work, we introduce Guidance-TTT , which separates these roles. A compact guidance model 

is trained at test time to propose high-level strategic changes, while a frozen ex-ecution model implements them as complete executable solutions. At each step, the system selects a promising previously discovered solution, proposes a change, executes and verifies it, and updates only the guidance model using an adaptive group-relative RL objective. This concentrates test-time learning on short strategic decisions while retaining the implementation capability of a substantially stronger model without adapting it. Without web access, Guidance-TTT produces strong solutions across four distinct domains: combinatorial optimization (Polyomino Packing), heuristic programming (AHC058), machine learning (Lasso), and GPU kernel optimization (TriMul). Across these tasks, it outperforms the best solutions reported in prior work while remaining competitive with state-of-the-art results on public online leaderboards. ## 1 INTRODUCTION 

Scientific discovery can be enhanced by LLMs that iteratively propose, evaluate, and refine candidate solutions (Romera-Paredes et al., 2024; Novikov et al., 2025; Qu et al., 2026). Many existing systems keep the LLM frozen and use verifier feedback to select promising candidates and condition subsequent generations through the prompt (Romera-Paredes et al., 2024; Novikov et al., 2025). This supports inference-time search and in-context adaptation without changing model parameters. Test-time training (TTT) additionally updates model parameters using verifier feedback to adapt the generation policy to the current problem (Wang et al., 2025; Yuksekgonul et al., 2026). Existing discovery-oriented TTT methods train the same LLM that generates the complete candidate solution (Surina et al., 2025; Wang et al., 2025; Yuksekgonul et al., 2026). This coupling creates two challenges. First, reliable solution generation often requires a large model, making direct test-time adaptation expensive in memory and computation (Hu et al., 2022; Yuksekgonul et al., 2026). Second, verifier feedback is applied to the complete output, so a single outcome-level reward must assign credit across both high-level strategy and low-level implementation (Setlur et al., 2025; Samanta et al., 2026). Consequently, a promising strategy may receive poor feedback simply because its implementation fails. These limitations motivate separating strategic guidance from solution implementation: test-time adaptation focuses on deciding what to change, while a capable executor handles how to realize it. This division also reflects how human experts often solve difficult problems through a small number of critical strategic decisions rather than by reconsidering every implementation detail. We therefore introduce Guidance-TTT (Figure 1), with the full workflow shown in Figure 3. A compact guidance model is trained at test time to propose high-level, parent-conditioned changes, while a stronger execution model remains frozen and implements them as complete candidate solutions. Only the guidance model is updated, reducing adaptation cost and focusing test-time learning on strategic decisions while preserving the implementation capability of the frozen executor. We refer to this as learning in thought space , where the learned actions are explicit natural-language proposals rather than complete programs or latent representations. After each execution, the system stores the resulting candidate together with compact summaries describing the solution and its change from the parent. The guidance model conditions on these summaries and the verifier score, while the execution model receives the exact parent solution together with the proposed guidance. Across four tasks, we train only 8B or 14B guidance while keeping GLM-5.2 frozen, without web access (Table 2). Polyomino reaches 91.89, exceeding four-agent, web-enabled CORAL’s 89.40 by 2.49 points. Our Lasso solver is approximately 1.40 × faster than SimpleTES under the same correctness tolerance. On AHC058, we obtain 850.08M AtCoder points versus SimpleTES’s 2Preprint. Under review. 849.33M. On TriMul, we reach 1129 μs, close to the public rank-1 reference of 1128 μs. In a separate Polyomino comparison using GPT-OSS-120B for execution, adapting only 8B guidance costs about 58% less than directly adapting the 120B model, with comparable scores of 83.19 and 83.72, respectively (Section 4.3). We make two contributions: 1. We introduce Guidance-TTT , a test-time RL framework that decouples strategic adaptation from solution generation: a compact guidance model learns parent-conditioned changes in thought space, while a stronger execution model remains frozen. We demonstrate its performance across four modern tasks ranging from algorithm design to kernel design. 2. We analyze how guidance learning affects discovery through controlled ablations, model-scale comparisons, search trajectories, and failure-mode studies, revealing the benefits of learning in thought space. 

## 2 RELATED WORK 

LLM self-evolution. A growing line of work improves LLM-generated solutions through iterative inference-time search without updating model parameters. FunSearch alternates program generation, selection, and evaluation to discover mathematical constructions and heuristics (Romera-Paredes et al., 2024). AlphaEvolve extends this paradigm with a general-purpose coding model and an evolutionary program database (Novikov et al., 2025). CORAL further distributes open-ended discovery across multiple fixed frontier LLMs using shared memory and asynchronous evolution (Qu et al., 2026). These methods demonstrate that archive reuse, verifier feedback, and repeated refinement can drive substantial improvement while keeping the underlying models fixed. 

Test-time training. Classical test-time training adapts a model using a learning problem constructed from each test instance (Sun et al., 2020; 2023). Recent LLM methods extend this idea to reasoning and open-ended discovery by updating model parameters during inference. ThetaEvolve augments a program database with optional test-time RL (Wang et al., 2025) and TTT-Discover introduces an entropic objective with PUCT-based reuse for max-seeking discovery (Yuksekgonul et al., 2026). Role specialization in LLM systems. Prior work has explored decomposing LLM systems into specialized roles that coordinate through natural-language communication (Wu et al., 2023). More recent work explicitly separates ideation from execution. Si et al. (2026) develop an automated executor that implements LLM-generated research ideas and evaluates them through large-scale experiments, allowing the ideation process to be grounded in execution feedback. Guidance-TTT learns parent-conditioned guidance from verifier feedback at test time, rather than only assigning ideation and execution to separate models.

Each candidate C ∈ C d is a complete solution, and its reward is R = Vd(C). 3.2 WHAT SHOULD BE LEARNED AT TEST TIME ?LLM-based methods for scientific discovery differ in what they learn from verifier feedback. In self-evolution without parameter updates, a fixed solution LLM generates the complete child from the task and its selected parent. Feedback changes which solutions are retained or selected for later refinement, but it does not change the model (Romera-Paredes et al., 2024; Novikov et al., 2025). TTT-Discover and related discovery-oriented methods (Surina et al., 2025; Wang et al., 2025; Yuksekgonul et al., 2026) instead use evaluated rollouts to update the same LLM that generates complete candidate solutions. The model must decide what change to attempt and implement that change in a complete solution. This is expensive when reliable generation requires a large model, and outcome-level feedback combines the quality of the strategy with the quality of its implementation. These limitations motivate separating strategic adaptation from solution implementation. Guidance-TTT therefore updates only a compact guidance model that proposes high-level changes, while a 4Preprint. Under review. separate execution model remains frozen and applies them to the exact parent solution. This focuses test-time learning on strategic decisions while avoiding the cost of adapting a much larger solution generator. We next describe the Guidance-TTT loop, including parent selection, guidance generation, execution, verification, and the test-time update. Algorithm 1 summarizes the Guidance-TTT loop, and Figure 3 shows the information exchanged in one iteration. Each eligible solution is stored in the archive together with compact summaries and its verifier score. Given a selected parent, the guidance model conditions on its summaries and score to sample K

high-level modifications. The frozen execution model applies each modification to the exact parent solution, producing K child candidates that are evaluated by the verifier. Their rewards form a sibling group used to update only the guidance policy. We select parents from the solution archive using PUCT sampling rule (Yuksekgonul et al., 2026). 4.1 EXPERIMENTAL SETUP 

Seeds are generated by one-shot execution-model calls; discovery is entirely offline, without web access or inheriting existing solution code. 

Polyomino Packing. We use FrontierCS problem 0 (Mang et al., 2025), where each candidate is a C++17 solver for packing irregular pieces across 70 cases. Performance is measured by aggregated packed-cell density on a 0–100 scale, with higher being better. 

TriMul GPU kernel. TriMul is the outgoing Triangle Multiplicative Update kernel from AlphaFold3 (Abramson et al., 2024), following the TTT-Discover GPU benchmark (Yuksekgonul et al., 2026). Candidates are Triton-based Python kernels that must pass correctness tests before timing. We report geometric-mean latency over seven benchmark cases using repeated fixed-kernel evaluations, with lower being better. Public ranks refer to the cited GPUMode leaderboard snapshot (GPU MODE, 2026). We include ranks 1, 4, and 5; ranks 2 and 3 are excluded because they use compiled CUDA/C++ extensions rather than Triton kernels. Details are in Appendix A.2. 

Lasso regularization path. Candidates are double-precision C++ solvers for the full Gaussian Lasso path. Valid solutions must match the scikit-learn reference objective within 10 −6. We evaluate fixed solvers repeatedly and report the reciprocal of geometric-mean solve time, with higher being better. The TTT-Discover Lasso reference is from our own evaluation. 

AHC058: Apple Production Planning. AHC058 is a 500-turn planning task in which the solver allocates resources across four machine levels to maximize apple production. Performance is measured by the task score, with higher being better; final results use the submitted solution’s AtCoder score. 

Comparison methods. We compare with TTT-Discover, CORAL, OpenEvolve, and task-specific references. The verified TTT-Discover runs use GPT-OSS-120B. The GLM-5.2 CORAL Polyomino run uses a 12 h budget, and OpenEvolve uses GLM-5.2 for 500 iterations. For Polyomino, we also include CORAL’s offline Opus 4.6 result and the FrontierCS human best. Guidance-TTT achieves stronger final solutions than the prior-work references across all four tasks, without web access or adapting the execution model. The gains are particularly pronounced on Polyomino and Lasso: Polyomino reaches 91.89, surpassing both web-enabled four-agent CORAL (89.40) and the released human reference (89.10), while Lasso improves over SimpleTES from 0.1243 to 0.1739, a 39.8% gain under the same correctness tolerance. On the already strong AHC058 and TriMul benchmarks, our official AHC058 submission reaches 850.08M points, exceeding SimpleTES (849.33M) and TTT-Discover (848.41M), while our TriMul kernel achieves 1129 μs geometric-mean latency, slightly outperforming K-Search (1131 μs) and approaching the eligible public rank-1 result (1128 μs). Appendix A tests whether these gains persist beyond the primary evaluation settings. On Lasso, the solvers discovered by Guidance-TTT with GLM-5.2 execution pass all 15 held-out real and stress-test cases, compared with 13/15 for SimpleTES. On TriMul, the discovered kernel transfers unchanged across Triton versions and remains the fastest evaluated automated method on Triton 3.4.0 and 3.6.0. We additionally report alternative execution-model results for Polyomino. 4.2.2 SOLUTION ANALYSIS 

Across all four tasks, Guidance-TTT exhibits a common pattern: it preserves a strong algorithmic backbone while introducing targeted structural changes to how search, computation, or adaptation is allocated (Figure 4). These comparisons are post hoc: Guidance-TTT does not directly evolve the referenced human or prior solutions. Rather, we compare the independently discovered solutions with strong existing approaches to characterize the structural changes associated with their gains. For Polyomino, the discovered solver independently recovers a geometry-aware skyline construction similar to the human solver, while adding a simulated-annealing refinement stage over piece priorities and board width. For Lasso, it combines a homotopy-style path method with segment-tree-based screening, avoiding repeated scans over the full inactive set. For AHC058, it introduces phase-dependent scheduling and cascade-aware valuation, allowing investment priorities to adapt as the production state evolves. Ablation results. The matched 8B controls isolate three design choices in Guidance-TTT: whether to learn the guidance policy, where to apply test-time adaptation, and how much parent context to expose to guidance. First, freezing the guidance model while retaining the same guidance–execution hierarchy reduces the Polyomino score from 91.89 to 84.85 and increases TriMul latency from 1225 .58 to 1256 .62 μs. Therefore, the hierarchical decomposition alone is not sufficient, updating the guidance policy provides additional gains on both tasks. Second, applying the same 8B adaptation budget directly to a model that generates complete solutions performs substantially worse, reaching 41.63 on Polyomino 8Preprint. Under review. and 9664 .91 μs on TriMul. This comparison suggests that concentrating test-time learning on strategic guidance is markedly more effective than asking the adapted model to both choose and implement complete solution changes. Third, adding a second parent’s summary and score (G-Top2) has opposite effects across the two tasks: it degrades Polyomino to 82.12 but improves TriMul to 1166 .82 μs. This contrast suggests that additional cross-parent context is useful only when proposed changes transfer cleanly across nearby solution states. Practical advantage: reducing adaptation cost by freezing the large executor. As an additional large-executor comparison on Polyomino, Guidance-TTT with a frozen GPT-OSS-120B executor reaches 83.19, close to the 83.72 obtained by TTT-Discover when directly adapting the same 120B model. Guidance-TTT trains only Qwen3-8B guidance with 8 × 16 samples for 30 updates, whereas TTT-Discover trains GPT-OSS-120B with 8 × 64 samples for 50 updates. Under the hardware and service configurations used in these runs, the observed cost is approximately $120 for Guidance-TTT versus $283 for the TTT-Discover trace, a reduction of roughly 58%. This result illustrates the practical cost advantage of keeping a large execution model frozen while retaining similar solution quality. Full executor comparisons are reported in Appendix A.3. 4.4 ANALYSIS : S CALING GUIDANCE IMPROVES PERFORMANCE ON SATURATED TASKS 

In this section, we analyze why scaling guidance improves discovery on saturated tasks. On both AHC058 and TriMul, 14B guidance improves over the 8B runs and reaches state-of-the-art perfor-mance. We compare the resulting solutions and diagnostic probes to identify what the larger guidance model does differently and how this translates into better results. Full trajectories and matched comparisons are reported in Appendix B.1. The 8B and 14B runs recover similar high-level mechanisms, but 14B applies them with finer special-ization. On TriMul, it adapts the fusion strategy to channel size rather than using a common pipeline. On AHC058, it combines state-dependent valuation with beam-based initialization and coordinated cross-level moves. These solutions indicate that larger guidance better organizes techniques around the current solution state. To examine their understanding, we asked two models to explain the SOTA code generated by Guidance-TTT with 14B model and answer related questions. Both recognized the main mechanisms. ## 5 CONCLUSION 

We introduced Guidance-TTT , a test-time RL framework that separates strategic adaptation from solution implementation. Rather than updating the model that generates complete solutions, Guidance-TTT learns a compact guidance policy in thought space , while a stronger execution model remains frozen. Across four distinct discovery domains, this simple separation produces solutions that outperform the strongest prior-work references while remaining competitive with public leaderboard results. Controlled comparisons further show that learning strategic guidance can be substantially more effective than either freezing the guidance policy or directly adapting a solution-generating model, while avoiding the cost of training the large execution model. Guidance-TTT suggests that test-time adaptation can learn to guide a frozen executor. Future work includes richer guidance representations, improved credit assignment between guidance and execution, and more diversity-aware search.

To further examine the interpretation in Section 4.4, we probed Qwen3-8B and Qwen3-14B with a fixed set of prompts, drawing three samples per prompt and model. The probes asked the models to propose improvements, explain excerpts from the 14B solutions, and solve related cases with or without a mechanism hint. In total, we collected 84 responses: 48 with reasoning disabled and 36 with reasoning enabled. For the reasoning-enabled runs, we used temperature 0.6, top-p = 0 .95 , and an 8192-token completion limit. With reasoning enabled, both models passed all explicit code-condition checks on AHC058 (15/15) and TriMul (18/18). A difference emerged, however, in the quality of the TriMul explanations. Among the three 8B responses, only one correctly described the relevant branch conditions without introducing additional restrictions, whereas all three 14B responses did so correctly. The other two 8B responses incorrectly imposed extra divisibility requirements. In particular, the persistent contraction fallback requires only N mod 128 ̸ = 0 , not the additional condition that N be indivisible by 64 or 32. Because this fallback is inactive on the standard benchmark shapes, these errors cannot directly account for the observed performance gap. They nevertheless suggest that the larger guidance model more reliably captures and articulates the underlying mechanism, consistent with the interpretation that increased guidance capacity improves strategic reasoning rather than merely code-condition compliance. 160 . Two 8B responses claim that a greedy procedure accepting only individually improving moves can reach the joint upgrade. In fact, neither first move would be accepted, so the higher-reward combination is unreachable under that search rule. All three 14B responses identify this constraint correctly. Together, these examples probe complementary aspects of mechanism-level reasoning: faithfully eval-uating an objective, translating structural observations into valid execution rules, and distinguishing the value of a decision from whether that decision is reachable under the specified search dynamics. B.2 PARENT ATTACHMENT AND TRANSFERABILITY 

In Guidance-TTT, each guidance is anchored to one selected parent: the guidance model observes its summaries and score, while the execution model modifies its exact solution. G-Top2 adds information from a second PUCT-selected solution to the guidance context, but leaves the executable state attached to the original parent. Any mechanism borrowed from the alternative must therefore remain compatible with the selected parent’s implementation. The two tasks respond differently to this intervention. On Polyomino, G-Top2 reduces validity to 33.83% and useful yield to 7.71%, indicating that packing mechanisms depend strongly on the surrounding ordering, state, and repair logic. On TriMul, validity remains close to the selected-parent setting, useful yield increases from 8.70% to 9.17%, and the run reaches 1166 .82 μs during search. This contrast is consistent with the task-structure interpretation in Section B.1: TriMul modifications may transfer more readily across nearby solutions, whereas Polyomino changes may depend more on their parent state. The single-trajectory comparison does not establish this mechanism causally. B.3 FAILURE MODES 

The Polyomino and TriMul trajectories reveal two recurring failure modes. First, verifier reward evaluates the realized program rather than guidance alone. Therefore, execution failures can produce misleading learning signals to the guidance model. Second, the interaction between policy updates and parent selection can concentrate later exploration within a small number of successful lineages. The Lasso and AHC058 histories contain counterparts of both structures: related proposals with different implementation outcomes, and parent-relative improvements that do not advance the global best. 

Credit ambiguity. Credit ambiguity arises when a zero reward does not reveal whether the failure comes from the guidance or from its realization. Since the verifier scores only the final program, it cannot separate poor guidance from a failed implementation of a sound one. The precondition for this ambiguity—execution failure—is common in our training logs: 404 of 3,840 Polyomino candidates are invalid (10.5%), all at compile or parse time, and 1,390 of 3,840 on TriMul (36.2%), mostly correctness failures. The Polyomino failures are the cleaner evidence here: they occur before any behaviour is observed, whereas a correctness failure does not separate a botched realization from a wrong idea. ## C METHOD DETAILS 

C.1 BUDGET AND PARENT GROUPS 

We use U for the number of guidance updates and N for the number of search candidates. Each update contains B parent groups and K rollouts per group, giving N = U BK . The default U = 30 ,

B = 8 , and K = 16 therefore give 3,840 candidate attempts. Seed generation and its validation precede this budget; subsequent fixed-solution evaluations are also separate. A failed candidate still consumes one search attempt. Parent selection returns an ordered list (p1, . . . , p B ), not a set of necessarily distinct solutions. Parents are selected from the archive visible before the current update; newly generated children become available at the next update. The selector prefers nodes outside the ancestor–descendant lineages already selected in the same batch. If all eligible nodes are blocked, it falls back to the highest-ranked node. Thus a single seed can supply all B groups at initialization, and repeated parents remain possible later. Each group has its own identifier even when parents repeat. For group b, the guidance policy samples K actions conditioned on the same parent state. Each action is executed once to produce one candidate, which is then evaluated. These K candidates form the sibling group for the advantage estimator; we do not execute one shared guidance K times. Independent samples need not produce distinct guidance text or code. C.2 TRAINING RECORDS AND SEARCH ARCHIVE 

Every completed attempt retains its parent link, guidance, generated code, summaries, verifier status, and reward in the rollout record. The search archive is a separate, filtered collection used for parent selection. Admission requires a valid verifier status and an available score; duplicate programs are filtered. Compilation errors, crashes, and timeouts do not create eligible parents. For AHC058, all 150 instances must be accepted, even though an invalid candidate can receive partial training reward. Training therefore uses the recorded sibling rewards, not only the children admitted to the archive. TriMul’s two-child rule retains the two highest-valued eligible children per parent for future selection. It does not reduce a group from 16 training rollouts to two. After a batch, the implementation applies child filtering, deduplication, and the configured archive-capacity limit. Ancestors required to preserve lineage links may remain as structural nodes without being selectable. Pruning the search archive does not delete the full rollout records or their evaluation feedback. C.3 TASK SCORES AND REWARDS 

All training rewards are oriented so that larger is better. For valid candidates, the mappings are: • Polyomino: R = s, where s is the aggregate packing score on the 0–100 scale. • Lasso: R = 1 /t geo , where tgeo is geometric-mean solve time in milliseconds across the search cases, subject to the objective-accuracy checks. • TriMul: R = 1500 /ℓ geo , where ℓgeo is geometric-mean latency in microseconds. Tables report latency rather than this reciprocal reward. • AHC058: R = ¯ s/ (3 × 10 6), where ¯s is the evaluator’s arithmetic-mean raw score over 150 instances. Training-trajectory totals are 150¯ s; official AtCoder scores are reported separately. Invalid Polyomino, Lasso, and TriMul programs receive zero reward. AHC058 can retain a partial reward from its evaluator, but only fully accepted candidates contribute archive bests. These task mappings are distinct from the within-group transformation used to obtain learning advantages. The Discover-compatible PUCT implementation uses the raw score oriented for maximization: the packing score, Lasso inverse time, and AHC mean score, or negative latency for TriMul. This search value is denoted v(i) in the main text. In particular, TriMul’s PUCT value and its reciprocal RL reward have the same ordering but are not numerically interchangeable. 23 Preprint. ## E DISCOVERED SOLUTION CODE 

The listings retain the parts of each discovered solution that implement the design choices discussed below. They omit input handling, bookkeeping, repeated launch code, and helper functions that do not affect the mechanisms described here. The accompanying code repository contains the full implementations; the excerpts are lightly condensed for typesetting. E.1 RELATIONSHIP TO PRIOR SOLVERS 

Polyomino packing. At a high level, the discovered solver is not a complete departure from prior packing methods, but a substantial extension of the constructive approach used by the released FrontierCS human solver (Mang et al., 2025). Both solvers use skyline geometry and search over orientations and widths. The human solver selects the next piece from a bounded candidate pool during construction; our solver additionally revises piece priorities and width through simulated annealing over reconstructed packings. The main difference from the strongest alternative configurations is a second-stage refinement procedure . Guidance-TTT augments the constructive packer with simulated annealing (Kirkpatrick et al., 1983) and timed restarts, allowing improvement beyond the initial packing. While the strongest frozen and direct-search baselines recover similar constructive backbones, they do not retain this refinement stage. The resulting solver therefore follows a clear two-stage design: construction followed by refinement. 

TriMul GPU kernel. The discovered kernel shares the hybrid Triton–cuBLAS structure used by K-Search (Cao et al., 2026); this is a comparison of final designs, not inherited source code. K-Search combines Triton kernels with cuBLAS for the main computation, whereas our kernel further specializes the pipeline across channel regimes and sequence shapes. In particular, it uses separate front ends for C = 128 and C = 384 , and dispatches the contraction between cuBLAS and a persistent Triton kernel depending on the input shape. The resulting design preserves a strong hybrid backbone while refining individual stages through more specialized execution paths. E.2 POLYOMINO PACKING
