## 摘要
现代高性能 GPU 计算将张量划分为分块，以利用数据复用和并行性。单个分块计算会比整个张量计算更早完成，从而为计算与通信的重叠创造了机会。然而，计算与通信进展之间的不匹配会限制这些机会。当没有数据就绪时，通信会停顿；当数据突发到达时，通信可能滞后。通信还可能通过消耗共享资源拖慢计算，抵消重叠带来的收益。我们提出 Entwine，它协调分块计算顺序、细粒度通信和 SM 资源分配，以最小化整体完成时间。Entwine 重新排序分块计算，以更规律的节奏产生用于通信的数据。Entwine 将这一调度与基于 SM 的细粒度通信相结合，以低延迟和低开销处理分块结果。由于通信内核也会消耗 SM 资源，Entwine 协调它们的分配，以在通信进展与计算减速之间取得平衡。在具有代表性的张量并行 LLM 工作负载上，Entwine 相比 cuBLAS+NCCL 实现了 1.232 倍的几何平均加速（最高 1.433 倍），并在几何平均上比最先进的重叠基线高出 3.1-9.8%。我们将在论文发表后开源我们的实现。

## Abstract
Modern high-performance GPU computations partition tensors into tiles to exploit data reuse and parallelism. Individual tile computations complete earlier than the full tensor computation, creating opportunities to overlap computation and communication. However, a mismatch between computation and communication progress can limit these opportunities. Communication stalls when no data is ready, and may lag when data arrives in bursts. Communication can also slow computation by consuming shared resources, offsetting the benefits of overlap.   We present Entwine, which coordinates tile computation order, fine-grained communication, and SM resource allocation to minimize overall completion time. Entwine reorders tile computation to produce data for communication at a more regular pace. Entwine couples this schedule with fine-grained SM-based communication to process tile results with low latency and low overhead. Since the communication kernel also consumes SM resources, Entwine coordinates their allocation to balance communication progress against computation slowdown. Across representative tensor-parallel LLM workloads, Entwine achieves a geomean speedup of 1.232x (up to 1.433x) over cuBLAS+NCCL, and outperforms state-of-the-art overlap baselines by 3.1-9.8% in geomean. We will open-source our implementation upon publication.

# Entwine 论文总结

## 1. 核心问题与研究背景

- **背景**：大语言模型需跨多 GPU 分布式部署，张量并行（tensor parallelism）把单层计算切分到各设备，但引入了交换/合并中间结果的通信开销（典型为行并行 GEMM 后接 ReduceScatter），该开销可占执行时间的相当比例。
- **机会**：高性能 GEMM 内核按 tile（分块）计算输出，各 tile 完成时间不同，因此理论上可在剩余输出仍在计算时就推进通信，实现计算—通信重叠。
- **核心问题（两个耦合挑战）**：
  - **挑战一：通信就绪 tile 的供给不稳定**。若按输出分区连续遍历，生产者会连续计算属于本地分区的 tile，这段时间不产生跨 GPU 传输数据，形成"供给间隙（supply gap）"；同时若通信按更大的组（如整个 wave group / 分区）触发，早完成的 tile 必须等待无关输出，缩短可重叠窗口。
  - **挑战二：重叠收益必须超过计算减速代价**。改变产出顺序会降低数据复用，并发传输/规约会争抢 SM 资源与内存带宽，都可能拖慢后续 tile 生产。
- **量化动机**：在评估负载上，顺序执行（cuBLAS+NCCL）使通信暴露占端到端时延的 **11.0%–40.2%，中位数 23.3%**。
- **已有工作局限**：CoCoNet 将通信块与 GEMM 流水化；FlashOverlap 以 wave/wave group 为单位释放给库集合通信（需等待组内无关输出）；FLUX 通过 GEMM epilogue 融合做 tile 级传输，但把通信并行度耦合到 GEMM 执行结构；Comet 用专用 block 划分计算/通信，但为整个执行期固定资源划分，无法匹配执行中动态变化的供需平衡。
- **整体含义**：需要**联合**决定"何时产出、以何种粒度通信、如何分配 SM 资源"，且以**端到端时延**而非 GEMM 吞吐或通信尾延迟为优化目标。

## 2. 方法论

### 2.1 核心思想
以 GEMM–ReduceScatter 为具体实例，同时协调三件事：**交错式 tile 产出顺序**、**独立的 tile 级细粒度通信**、**共享 SM 池 + 通信预算**。用离线 profiling 以端到端时延为准则联合选取 GEMM 配置与通信并发度。

### 2.2 关键技术细节

- **交错产出（Interleaved production）**
  - 逻辑块序循环遍历输出分区，使"本地消费的 tile"与"需跨 GPU 传输的 tile"交替出现，让通信数据以更均匀的节奏产出。
  - 映射公式（W 个 GPU、分区等宽且块对齐，p 为逻辑块序号从 0 起）：
    - 目标 rank `d = p mod W`
    - 分区内块索引 `ℓ = ⌊p / W⌋`
  - 所有 rank 使用同一映射，保证同一 tile 的各 rank 贡献位于对应逻辑位置，目的端的任务顺序可跟随统一的产出顺序。
  - 注：只规定逻辑顺序，物理完成时刻仍受 GPU 调度影响。

- **独立 tile 通信（Independent tile communication）**
  - 每个通信任务只规约**一个输出 tile**，仅依赖各 rank 的一个生产者块；不需要等待目的分区其余输出。
  - 协议：生产者完成输出 store 后按 tile 发布完成信号 `F[r,d,t]`；消费者先等待所有 W 个 rank 的信号，再规约该 tile。用 release store / acquire load + CTA barrier 保证"读发生在所有相关写之后"。
  - 通信粒度与 GEMM 块形状解耦：一个 GEMM 块可覆盖多个 tile 以复用数据，这些 tile 仍各自保留独立的规约任务。

- **任务顺序匹配（Matching task order）**
  - 一个通信内核处理本地输出分区的全部 tile 规约；分区内按生产者遍历顺序编号 0..Q-1。
  - 若有 x 个消费者块，块 j 处理 tile `j, j+x, j+2x, ...`；块内串行、块间独立推进，无需为每个 tile 单独启动内核。
  - 减小 x 只是让每块序列更长，**不会**合并相邻 tile 的依赖。

- **资源共享与通信预算**
  - 每个 GPU 上并发运行一个计算内核和一个通信内核，**共享同一 SM 池**，不固定保留 SM；块退出后资源可被任一内核的待处理工作获取。
  - **通信预算 x** = 通信内核 grid size（上限为分区 tile 数）；线程数 b ∈ {128, 256, 512}。x 与 b 共同决定通信与 GEMM 竞争的资源量。
  - 通信块在等待输入期间**保持占用 SM 资源**，因此预算必须为计算留出产能（默认 reducer grid 上限低于设备 SM 数）。
  - GEMM 在默认优先级流、规约在高优先级流；硬件调度器决定块准入，运行中的块不被打断。

- **端到端优化准则**
  - 全局通信尾 = 最后一个计算内核结束到全部通信完成的区间。增大并发可缩短尾部但延长计算窗口。
  - 离线 profiling 对每种矩阵形状与 rank 数枚举 GEMM 内核、reducer grid size 与线程数，**选择并发执行下端到端时延最低的组合**（而非单独最优化 GEMM 吞吐或通信尾）。

- **带宽分析（解释配置选择）**
  - 远端读取量：`V_comm = (W-1)/W · M·N·s`
  - GEMM 时延：`T_G(x,K) = 2MNK / Φ(x,K)`（Φ 为并发下实测吞吐，已含通信导致的减速）
  - 所需平均带宽：`B_req(x,K) = (W-1)/W · s·Φ(x,K) / (2K)`
  - 推论：M、N 显式相消，但形状仍通过吞吐影响需求；K 增大只增计算不增通信量，所需带宽下降；**所需带宽降低也可能只是因为 GEMM 变慢**，故配置选择必须看端到端时延。平均带宽相同不代表性能相同——晚到的输入留给重叠的计算窗口更短。

- **实现要点**
  - CUTLASS GEMM + CUDA 规约内核，面向 NVIDIA SM80、单 NVLink 可 peer 访问域。
  - 对称 CUDA IPC 堆存放部分输出与发布标志，偏移一致；reducer 直接读对端显存；分配跨调用复用，每次调用前重置标志并同步。
  - 自定义 CUTLASS thread-block swizzle 实现交错遍历；epilogue visitor 发布完成信号（系统作用域 release store）。
  - 规约单元为 128×128 tile；生产者块为 128×128 或 128×256（数据复用不同）。
  - 两个内核在独立 CUDA stream 上于公共 start event 后启动，用 CUDA Graphs 降低重复主机启动开销。
  - FP16 打包对以跨线程 strided 循环处理；两 rank 时合并为向量读写。
