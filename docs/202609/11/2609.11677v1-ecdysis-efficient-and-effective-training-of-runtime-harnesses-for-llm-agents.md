## 摘要
自演化的运行时harness能够显著提升大语言模型（LLM）智能体的能力，并为优化智能体执行提供了一种有前景的范式。现有的harness演化方法通常依赖迭代搜索，基于来自任务实例的执行反馈反复评估和修订候选harness。尽管该范式能够实现持续的harness优化，但由于重复的智能体执行和代码修改，它会带来大量时间开销，并且可能对已观测任务和特定失败模式过拟合，导致对未见任务的泛化能力下降。我们将缺乏有原则的失败诊断视为harness演化的一个关键瓶颈：观察到的失败可能反映模型特有的缺陷，也可能反映系统性的harness缺陷，而直接针对单个失败进行优化可能导致不必要的模型特定适配。因此，我们提出Ecdysis，一个高效且有效的框架，它区分模型特定适配与harness层面修复，并通过识别反复出现的跨任务失败模式，将适配偏向系统性的harness缺陷。Ecdysis采用批级跨实例失败聚合范式，联合分析来自多个任务实例的失败证据，并进一步引入失败驱动的协同精化（Failure-Driven Collaborative Refinement），以诊断失败原因并迭代细化harness修改规范。通过将跨实例失败分析与多角色诊断相结合，Ecdysis能够以更低的训练时间实现更有效的harness演化。实验表明，与现有harness演化方法相比，Ecdysis在harness训练上实现了最高1.84倍的加速，同时将所得harness的推理准确率提高了18.56%。

## Abstract
Self-evolving runtime harnesses can substantially improve the capabilities of large language model (LLM) agents and provide a promising paradigm for optimizing agent execution. Existing harness evolution methods typically rely on iterative search, repeatedly evaluating and revising candidate harnesses based on execution feedback from task instances. While this paradigm enables continuous harness optimization, it incurs substantial time overhead due to repeated agent executions and code modifications, and may overfit to observed tasks and specific failure patterns, resulting in degraded generalization to unseen tasks. We identify the lack of principled failure diagnosis as a key bottleneck in harness evolution: an observed failure can reflect either model-specific deficiencies or systematic harness deficiencies, and directly optimizing against individual failures can lead to unnecessary model-specific accommodation. We therefore propose Ecdysis, an efficient and effective framework that distinguishes model-specific accommodation from harness-level repair and biases adaptation toward systematic harness deficiencies by identifying recurring cross-task failure patterns. Ecdysis adopts a batch-level cross-instance failure aggregation paradigm to jointly analyze failure evidence from multiple task instances and further introduces Failure-Driven Collaborative Refinement to diagnose failure causes and iteratively refine harness modification specifications. By combining cross-instance failure analysis with multi-role diagnosis, Ecdysis enables more effective harness evolution with lower training time. Experiments show that Ecdysis achieves up to a 1.84x speedup in harness training compared with existing harness evolution methods, while improving the reasoning accuracy of the resulting harnesses by 18.56%.

- **核心瓶颈**：现有 harness 演化通常采用“实例级、迭代搜索”的方式，即每次失败都触发候选修改、执行验证和代码修订，导致训练时间和 API 成本高。同时，单个失败可能来自模型自身缺陷，也可能来自 harness 的系统性缺陷；若不加区分地针对每个失败修改 harness，会产生“模型特定适配”，过拟合当前模型和训练任务，损害对未见任务和其他模型的泛化。
- **论文主张**：缺乏有原则的失败诊断是 harness 演化的关键瓶颈。Ecdysis 的核心含义是：不应把每个失败都当作直接修改信号，而应识别**跨任务反复出现的失败模式**，将其作为 harness 层面系统性修复的证据，从而减少模型特定适配，提升演化效率与泛化性。

## 2. 方法论

### 2.1 核心思想

- 将失败驱动演化从“单个失败 → 单次修改”转变为“批级跨实例失败聚合 → 结构化诊断 → 候选修改”。
- 用跨任务复发模式作为归纳偏置：如果某失败机制在多个独立任务中重复出现，它更可能是 harness 的系统性缺陷，而非当前模型的偶发或特定缺陷。
- 区分两类更新：
  - **模型特定适配**：适应当前任务模型的行为特点。
  - **harness 层面修复**：修复交互机制、状态管理、工具调用等系统性问题。
- 论文用如下分解描述一轮 harness 更新：
  - \(\Delta H = t\Delta H_{\text{model}} + (1-t)\Delta H_{\text{harness}}\)，其中 \(t \in [0,1]\) 表示模型特定适配决策的比例。Ecdysis 试图降低 \(t\)，使更新偏向 harness 修复。

### 2.2 算法流程

论文 Algorithm 1 的流程可概括为：

1. 输入：固定任务模型 \(\theta\)、运行环境 \(E\)、训练任务集 \(D_{\text{train}}\)、初始 harness \(H_{\text{base}}\)、失败阈值 \(\lambda\)、演化轮数 \(R\)、精化次数 \(K\)。
2. 初始化 \(H_0 = H_{\text{base}}\)。
3. 对每一轮 \(i=1,\dots,R\)：
   - 用当前 harness \(H_{i-1}\) 执行训练任务，收集轨迹 \(T_i\)。
   - 对轨迹 \(\tau\) 计算任务分数 \(S(\tau)\)，定义失败信号 \(f_\lambda(\tau)=I[S(\tau)<\lambda]\)。
   - 聚合失败轨迹，形成结构化失败证据集 \(B_i\)。若为空，保留原 harness 并进入下一轮。
   - 将失败证据分组为失败模式 \(G_i\)。
   - 进入 FDCR：Analyst、Critic、Engineer 三个角色在共享 transcript 中迭代 \(K\) 轮，从互补角度诊断失败原因并细化修改提案。
   - Moderator 综合失败证据和讨论记录，生成结构化 harness 修改规范 \(q_i\)。
   - 编码智能体根据 \(q_i\) 修改 \(H_{i-1}\)，得到候选 harness \(H_i^c\)。
   - 若候选在训练集整体分数上严格提升，即 \(J_{\text{train}}(H_i^c) > J_{\text{train}}(H_{i-1})\)，则接受；否则回滚。
4. 训练结束后冻结最终 harness \(H_F=H_R\)。

### 2.3 关键机制

- **批级失败聚合**：每轮只对非空失败证据调用一次编码智能体，而不是每个失败调用一次。论文给出：
  - \(N_{\text{round}} = \sum_{i=1}^R I(n_i>0) \le \sum_{i=1}^R n_i = N_{\text{serial}}\)，其中 \(n_i=|B_i|\)。
- **FDCR 多角色诊断**：
  - Analyst：识别潜在 harness 缺陷并提出最小、针对性修改。
  - Critic：评估提案是否过宽、是否阻断合法行为、是否违反运行契约、是否导致回归。
  - Engineer：追踪共识与分歧，提出后续需澄清的问题。
  - Moderator：保守仲裁，合并提案、解决分歧，优先处理跨任务复发问题。
- **诊断与实现分离**：FDCR 负责诊断和形成规范，编码智能体负责实际代码修改。
