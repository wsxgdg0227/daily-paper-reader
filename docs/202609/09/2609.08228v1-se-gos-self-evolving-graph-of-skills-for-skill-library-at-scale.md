## 摘要
现代LLM代理越来越依赖于可复用技能，然而随着技能库扩展至数千条目，有效检索成为瓶颈。技能图（GoS）通过利用依赖感知的图结构实现可扩展的技能检索来解决这一挑战，而SkillDAG进一步表明技能图可以在线积累基于执行支持的图结构。然而，这些方法未解决是否可以从历史执行轨迹中系统性地提炼出更好的检索图，使其泛化到未见任务。我们提出自进化技能图（SE-GoS），一种无需训练的框架，从执行轨迹进化现有GoS图，同时保留原始检索流程。SE-GoS执行三种互补更新：拓扑进化，从执行证据中发现和剪枝技能关系；边权重进化，基于历史有效性强化检索相关关系；描述进化，利用执行反馈优化面向检索的技能描述。在SkillsBench上的三个LLM中，SE-GoS在降低输入token（相对于完整技能加载）的同时持续提升任务奖励，且提升幅度因模型系列而异。在一个代表性设置中，一轮进化将奖励从52.4%提升至59.4%，同时相对于完整技能加载减少约三分之一的输入token，且所得图可迁移至不相交的保留测试分割，相较于静态GoS基线有5.4个百分点的提升。这些结果表明，无需模型训练、无需改变检索算法或修改技能内容，即可从执行经验中改进技能图，将静态检索图转变为不断进化的检索基础设施。

## Abstract
Modern LLM agents increasingly rely on reusable skills, yet as skill libraries scale to thousands of entries, effective retrieval becomes a bottleneck. Graph-of-Skills (GoS) addresses this challenge by exploiting dependency-aware graph structure for scalable skill retrieval, while SkillDAG further demonstrates that skill graphs can accumulate execution-backed structure online. However, these approaches leave open whether historical execution traces can be systematically distilled into a better retrieval graph that generalizes to unseen tasks. We present Self-Evolving Graph-of-Skills (SE-GoS), a training-free framework that evolves an existing GoS graph from execution traces while preserving the original retrieval pipeline. SE-GoS performs three complementary updates: topology evolution that discovers and prunes skill relationships from execution evidence, edge-weight evolution that reinforces retrieval-relevant relationships based on historical effectiveness, and description evolution that optimizes retrieval-facing skill descriptions using execution feedback. Across three LLMs on SkillsBench, SE-GoS consistently improves task reward while reducing input tokens relative to full skill loading, with gains varying across model families. In a representative setting, one evolution round improves reward from 52.4\% to 59.4\% while reducing input tokens by approximately one-third relative to full skill loading, and the resulting graph transfers to a disjoint held-out split with a 5.4-point improvement over the static GoS baseline. These results show that skill graphs can be improved from execution experience without model training, changes to the retrieval algorithm, or modifications to skill content, turning a static retrieval graph into an evolving retrieval infrastructure.

## 1. 核心问题与研究动机

- **背景**：LLM 代理在复杂技术任务中需要调用外部工具与可复用技能。随着技能库从数十条增长到数千条，瓶颈从“决定是否使用技能”转变为“从库中检索出足够完成任务的有界子集”。
- **现有方法的缺陷**：
  - **全量加载**所有技能进入上下文，token 开销线性增长，且模型在过载上下文中会忽视关键技能；
  - **基于向量的检索**忽略技能之间的功能依赖关系，常出现“前置条件鸿沟”（prerequisite gap），即语义匹配最强的高级求解器缺少其依赖的低层解析器或工具；
  - **Graph-of-Skills (GoS)** 的静态技能图虽然能利用依赖感知的结构做预算化检索，但**图一旦构建就不再更新**，无法从执行反馈中自我纠正错误的关系、缺失的连接或失配的描述。
- **本文提出的核心问题**：历史执行轨迹能否被系统性地提炼为更好的检索图，从而泛化到未见过的任务？答案应是肯定的——每条执行记录中已蕴含“哪些技能被检索到、哪些真正被使用、任务是否成功”这一免费信号。

## 2. 方法论

### 2.1 核心思想

- SE-GoS 是一个 **无需训练（training-free）** 的框架，在不修改技能内容（SKILL.md）、不训练任何参数、不改变检索算法的前提下，仅通过**改动检索所依赖的图结构和元数据**，使静态 GoS 图从执行轨迹中自进化。
- 关键洞察：PPR（Personalized PageRank）直接读取边权重，因此重新连线/加权图即可改变检索行为；图与节点元数据是唯一被 SE-GoS 修改的对象，而检索流程本身是固定消费者（fixed consumer）。

### 2.2 三类互补的演化更新

1. **拓扑演化（Topology Update）** —— 改变图离散结构，增删边及边的类型：
   - **workflow 边（工作流关系）**：成功轨迹中，检索到的种子技能 u 与实际使用的技能 v 共现，则添加有向边 u→v，权重与共现次数挂钩（w = min(0.9, 0.6 + 0.05·(c_uv − 1))）；
   - **dependency 边（依赖关系）**：成功轨迹中 u 先于 v 被使用，且 u 的输出与 v 的输入之间存在满足 GoS 离线阈值（ζ=0.6）的 schema 重叠，则添加依赖边；轨迹的时序状态对 schema 预测进行认证；
   - **avoid 边（规避关系）**：两技能在失败轨迹中共同出现达到阈值且从未在成功轨迹中共现，则添加零权重的 avoid 边；扩散过程不经过零权重边，只在 bundle 组合阶段用于剔除冲突候选；
   - **软剪枝（soft pruning）**：对“频繁被检索但从未被实际使用”的技能，将其所有入边权重乘 0.5，低于下限的边直接删除。

2. **边权重演化（Edge-weight Update）** —— 更新连续权重：
   - 强化规则：对成功轨迹中每个被实际使用的技能 v，强化所有指向 v 的入边权重，公式为 w^(t+1)(u→v) = w^(t)(u→v) + η·r_t·I[v∈U_t]；
   - 失败轨迹不贡献正向信用；任务成功奖励 r_t 对增量幅度进行缩放。

3. **描述演化（Node/Description Update）** —— 优化面向检索的技能描述，针对“被使用但在低排名位置出现的技能”：
   - 借鉴 ProTeGi 的文本梯度下降思想，实现单轮、技能局部的变体：LLM 批评者 ∇ 生成自然语言梯度（描述为何与查询错配）→ LLM 编辑者 δ 反向修订描述（≤50 token 预算）→ 改写模型生成 p 个释义变体做蒙特卡洛探索 → 用离线评估器 E(q,s;d) 对候选描述按提升目标技能的排名打分，选择最优；
   - 仅对失败试验（r_t < r_succ = 0.9）中被实际使用但排序低于阈值 n_rank = 3 的技能发起更新，成本 O(|Q_s|·(1+p)) 次 LLM 调用，与技能库大小无关；
   - 默认开启“no-eviction guard”，防止新的描述改写把真正用过的技能挤出 top-K。

3 各类更新分别作用于图的边集合、边权重和节点文本三个互补维度，不会相互覆写；三类更新按依赖顺序执行：拓扑 → 边权重 → 节点描述。

### 2.4 冷启动与泛化设计

为公平分离 LLM 先验与演化增益，SE-GoS 的冷启动图是一个**确定性、无语义模型（token overlap）的纯语义相似图**（k=1，863 条语义边），不含 GoS 的完整类型边集。演化更新从执行轨迹中补充 workflow、dependency、avoid 结构，而不是依靠 LLM 对技能相关性的先验判断。

## 6. 主要结论与发现

1. 在 deepseek-v4-flash-0731 + SkillsBench 主实验中，静态 GoS 已经从 52.4% 的奖励占优（高于 Vanilla 46.2% 与 Vector 38.7%）；SE-GoS 一轮演化后达到 **59.4%**（相对静态 +7.0 分），同时将每次尝试输入 token 降至 **3.45M**（约比全量加载节省 32%）。
2. 在 minimax-m2.7 和 gpt-5.2-codex 两个骨架上，SE-GoS 均优于静态 GoS 和 SkillDAG（38.1% vs. GoS 34.4% vs. SkillDAG 36.6%；ALFWorld 上在 gpt-5.2-codex 上与 SkillDAG 平手 93.6%）。
3. Held-out 分割上（evolve on 50/test on 37），SE-GoS 相对静态 GoS 有 **+5.4 分**的提升，token 基本不变，说明获得的提升是**可迁移结构，而非记忆化的轨迹拟合**。
4. 多轮演化并非越多越好：第 1 轮奖励 59.4%、第 2 轮 59.8%、第 3 轮降至 54.0%，伴随边数膨胀到 1,502，出现过拟合；因此演化应是一次性部署步骤而非训练循环。
5. 组件消融：单独作用均为正改进——edge（+4.9）> topology（+1.7）> node（+1.2）；成对组合中包含 edge 的单元提升最大（+6.4~+6.7）。主效果排序为 edge（+4.7）> topology（+1.4）≈ node（+1.3）。leave-one-out 一致显示缺少 edge-weight 更新时奖励损失最明显。

## 7. 优点

- **方法设计上的技术创新**：利用 PPR 对边权重直接读取的特点，只改动“图”本身就能改变检索行为，整个检索流程不需要任何改动；三类更新分别作用于离散边集、连续权重和文本描述三个互补轴，互不冲突。
- **无需训练、审计性强**：所有更新可解释、可逆，边权重构成可审计的、跨代理共享的成功执行记录；不需要修改任何技能内容，不需要嵌入服务，也不改变推理时检索代码。
- **结构信号来自执行而非 LLM 先验**：workflow、dependency、avoid 边都来自真实执行轨迹的行为观测，而避免使用不能被观测证据支持的 alternative 关系，该方法论边界清晰且论证有力。
- **有效处理了模型训练前的冷启动/部署设置问题**：实验基座是极轻的纯词法 token-overlap 图 + 词法种子加 PPR，不附带任何 LLM 依赖，反而更能观测到演化本身的增益。
- **消融和统计审计严谨**：提供 23 因子消融、噪声分辨率校准、held-out 分割、检索接口消融，与相似系统（SkillDAG）的对比也做了协议降级说明。
- **结论与工程部署链接紧密**：演化是一次性离线步骤、成本固定且可用窗口化的方式投入生产，对实际部署友好。

## 8. 不足与局限

- **单轮为主、多轮过拟合**：主结果只报告一次演化；重复更新到第三轮奖励出现倒退（54.0%），工程上长期部署时的演化窗口机制与过拟合惩罚尚未深入刻画。
- **轨迹依赖的“已用技能集”提取**：U_t 提取依赖对工具调用轨迹的目录路径扫描，间接调用或脚本内调用可能漏算；提取误差会传播给 topology 与 edge 更新。
- **统计分辨度有限**：作者自己给出 ±6~7 分噪声带，单个增加的显著性集中在包含边权重更新的配对单元；单组件单独撬动的增益大部分处于噪音带内，不能精确分辨。
- **评估范围受限**：仅在 1,000 标签技能的 SkillsBench 和 ALFWorld dev split、三种骨干模型上验证；未做 200/500/2,000 规模下的变化，也未必能外推到其他模型家族与任务领域。
- **SkillDAG 对比不严格同等**：SkillDAG 在本文协议下测得而非按其官方原文引用；同类对比仍存在一定标准差异（它官方流程自带嵌入服务 + LLM 冷启动）。
- **资源信息缺失**：未提供 GPU 型号、数量、显存、训练/推理时长等细节，不利于复现与资源估算。
- **通用建议**：在全文给了一个实例（技能图是比模型和技能内容更适合吸收经验的检索面上层），但这只是某个 LLM + 某种库规模下的结果，需要更多下游场景验证。
