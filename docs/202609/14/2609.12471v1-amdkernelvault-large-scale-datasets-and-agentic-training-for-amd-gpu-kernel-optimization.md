## 摘要
我们介绍了 AMDKernelVault，一个面向近期 AMD CDNA GPU 的开放 HIP 与 Triton 内核语料库及训练框架。现有基于 LLM 的内核智能体大多以 CUDA/NVIDIA 为中心，且通常依赖反复调用前沿 LLM 来进行生成、反思和优化。为弥补这一空白，我们开发了 HIPKernelGen 和 TritonKernelGen，这两条智能体驱动的流水线可将 PyTorch 参考实现转换为 HIP 或 Triton 内核，在 ROCm 下编译并验证候选内核，并在 AMD 硬件上对其进行延迟剖析。该语料库包含 62,153 个经过执行验证的 HIP 内核样本、2,377 条基于生产环境的 ROCm Libraries 问答条目，以及 39,893 个 Triton 内核。我们进一步通过监督微调和执行感知强化学习训练 Qwen3-8B，以展示该语料库的效用。在固定评估预算下，它在 PyTorch-to-HIP（34.0% Pass@1）、TritonBench-G（33.2% Corr@3）和 ROCmBench（41.94% Corr@3）上取得了所比较模型中最高的正确率，但并未在编译或速度指标上全面领先。语料库和文档可在 https://huggingface.co/datasets/amd/AIG-Datasets 获取，相关训练与内核生成代码可在 https://github.com/AMD-AGI/hip_kernel_llm_lab 获取。

## Abstract
We introduce AMDKernelVault, an open HIP and Triton kernel corpus and training framework for recent AMD CDNA GPUs. Existing LLM-based kernel agents are largely CUDA/NVIDIA-centric and often depend on repeated frontier-LLM calls for generation, reflection, and optimization. To address this gap, we develop HIPKernelGen and TritonKernelGen, agent-driven pipelines that transform PyTorch references into HIP or Triton kernels, compile and validate candidates under ROCm, and latency-profile them on AMD hardware. The corpus contains 62,153 execution-verified HIP kernel samples, 2,377 production-grounded ROCm Libraries QA entries, and 39,893 Triton kernels. We further train Qwen3-8B with supervised fine-tuning and execution-aware reinforcement learning as a demonstration of the corpus's utility. Under fixed evaluation budgets, it achieves the highest correctness among the compared models on PyTorch-to-HIP (34.0% Pass@1), TritonBench-G (33.2% Corr@3), and ROCmBench (41.94% Corr@3), but does not uniformly lead compilation or speed metrics. The corpus and documentation are available at https://huggingface.co/datasets/amd/AIG-Datasets, and the associated training and kernel-generation code is available at https://github.com/AMD-AGI/hip_kernel_llm_lab.

## 1. 核心问题与整体含义

- **研究动机**：现有基于 LLM 的 GPU 内核智能体（如 Kevin、AutoTriton、GEAK 等）几乎全部以 **CUDA/NVIDIA 为中心**，其数据、工具链与评测基准难以迁移到 AMD 生态。
- **关键空白**：AMD 的 HIP/ROCm 生态缺乏**大规模、执行验证**的内核数据，且同时覆盖原生 HIP 与 Triton 两个后端。
- **为何不能简单翻译**：HIP 与 CUDA 虽抽象相似，但高性能 AMD 内核依赖 ROCm 编译行为、wavefront 执行、LDS 使用、内存合并、矩阵核支持及 Triton 后端约束；`hipify` 只保留 API 结构，可能残留 NVIDIA 形状的分块常量、warp-size 假设与内存布局，导致编译失败或性能低下。
- **整体含义**：论文主张 AMD 内核数据必须经过**原生编译 + 执行级正确性验证 + ROCm 延迟测量**，并据此构建开源语料库与可本地部署的紧凑内核模型，以减少对前沿 LLM 反复调用的依赖。

## 2. 方法论

### 2.1 统一智能体框架（generate–evaluate–reflect）

- **Stage 1：PyTorch 参考标准化**——将目标算子/模块转为函数式 PyTorch 参考，保证可靠调用、一致接口语义与执行验证；Torch Inductor 生成的内核仅用于交叉校验，不替代参考正确性。
- **Stage 2：后端特定内核合成**——HIP/Triton 智能体生成候选内核，每个候选需经编译、对 PyTorch 参考的执行级正确性检查、延迟剖析；失败则触发 reflector 引导的再生成，直到满足正确性标准或达到尝试上限。
- **两条实例化流水线**：
  - `HIPKernelGen`：面向 AMD HIP，主要用 GPT-5（2025 年 8–12 月采集），经 `hipcc` 编译，通过 `torch.utils.cpp_extension` 绑定执行。
  - `TritonKernelGen`：使用 GPT-oss-120B、DeepSeek-R1、Qwen2.5-32B 多样化实现与推理轨迹，经 Triton 3.3.0 编译执行，约 10 个正确性配置 + 3 个性能配置（形状、步幅、FP32/FP16/BF16、边界情况）。

### 2.2 正确性判定与测试构造

- HIP 默认容差：`torch.allclose(rtol=1e-4, atol=1e-4, equal_nan=True)`；Triton 回退容差：`rtol=1e-4, atol=1e-3, equal_nan=False`；无固定 dtype/算子专用规则。
- 测试输入继承自 CUDA-Agent-Ops-6K、GPUMode、AI-CUDA-Engineer-Archive，并用经校验的 LLM 生成用例补充形状、步幅、dtype 与边界覆盖。
- 对 Triton→Triton，扩展 TritonBench 风格测试的 ROCm 兼容用例，**丢弃仅通过输入/形状特化检查的候选**；LLM 生成的测试本身不作为监督，仅作为执行验证循环中的额外探针。

### 2.3 语料来源与构成

- **六个源数据**：CUDA-Agent-Ops-6K（6,000 合成算子任务）、GPUMODE-KernelBook（约 18,000 PyTorch 模块 + Torch Inductor Triton）、AI-CUDA-Engineer-Archive（250+ KernelBench 基准）、Stack-v2-dedup-Triton（13K 候选筛出 2,269 对）、TritonBench-8k、ROCm Libraries（rocBLAS/rocSOLVER）。
- **语料规模**：
  - HIP/ROCm 合计 **64,530**：HIP-CudaAgent 5,388、HIP-GPUMode 22,397（5,910 唯一任务，平均 3.8 变体/条目）、HIP2HIP 34,368（31,155 单轮 + 3,213 多轮）、ROCm Libraries QA 2,377。
  - 其中**执行验证的 HIP 内核样本为 62,153**；另有一个 14,282 条目的 HIP-AICUDA 子集单独发布、本文未使用。
  - Triton 合计 **39,893**：Triton-Stack 2,269、Triton-Bench 7,713、Triton-GPUMode 18,000、Triton-AICE 11,911。

### 2.4 生产级 ROCm QA 监督

- **接口分解**：从用户接口出发，沿调用图遍历，识别设备端内核、主机端启动逻辑、参数准备与紧耦合辅助工具。
- **范围控制**：用项目特定 allowlist/disallowlist 过滤日志、调试、测试与辅助代码，避免递归爆炸与无关上下文。
- **内核中心 QA 生成**：问题聚焦计算语义、索引到张量映射、内存访问模式、同步与归约策略、启动配置、正确性约束，答案锚定检索到的真实代码。
- 产出：rocSOLVER 519 条（226 实现 + 293 QA），rocBLAS 1,858 条（1,169 实现 + 689 QA），共 2,377 条。

### 2.5 难度分级

- Level 1（独立单函数内核）、Level 2（融合算子或单文件实现）、Level 3（多文件、跨模块依赖）。
- Triton 语料：L1 11,824（29.6%）、L2 24,765（62.1%）、L3 3,304（8.3%）；ROCm QA 分布类似。

### 2.6 紧凑内核 LLM 训练（Qwen3-8B）

- **两阶段配方**：先 SFT 冷启动（学内核语法、绑定约定、内存访问惯用法），再执行感知 RL。
- **四类任务**：PyTorch→HIP、HIP→HIP、Text→Triton、Triton→Triton。
- **三指标**：编译通过、正确性通过（对 PyTorch 参考数值等价）、加速比；Comp@k/Corr@k 报 k 轮迭代后结果，Pass@k 报 k 次采样至少一次正确的概率，Speed@10 取最佳 10 个正确样本的平均加速。
- **奖励设计**：`r = r_compile + r_correct + r_perf`，其中 `r_compile = 0.4`、`r_correct = 1.0`、`r_perf = min(0.375·(log₂ s)², 1.5)`（s≥1），总奖励 ∈ [0, 2.9]。编译部分学分在低成功率区提供梯度信号，性能项有界以抑制延迟噪声。
- **GRPO 变体**：HIP 用单轮 GRPO；Triton 用多轮 on-policy reflection GRPO（T=3，γ=0.6，轮次权重 w₁=1.0、w₂=0.6、w₃=0.36，归一化后约 51% 权重给第一轮）。
- **关键技巧**：**禁用方差归一化**，改用 `Âᵢ = rᵢ − r̄`。论文理论分析指出，二值奖励 + 标准归一化在 ~6% 初始成功率、G=8 时约 **60.6%** 的组出现零优势，导致梯度消失。
- **SFT 细节**：全参数微调而非 PEFT/LoRA（初步实验表明适配器不足）；Triton 样本含 CoT 式规划再输出内核。
- **课程学习**：Triton RL 采用"难度衰减"三阶段（L1 5.3K → L1子集+L2+L3 16.5K → L2子集+L3+变体 4K），逐步减少简单样本。

## 3. 实验设计

- **评测任务与基准**：
  - PyTorch→HIP：200 个 KernelBench Level-1/2 任务（Pass@1）。
  - HIP→HIP 优化：100 个留出模块。
  - Triton：TritonBench-G（184 内核）与 ROCmBench（31 个 AMD 特定内核）。
- **统一协议**：Triton 全部对比使用相同的 **GEAK OptimAgent-v2** 配置（`num_offsprings=1`、`max_iteration=3`、相同 generator/reflector/optimizer 角色分配、无 profiler 反馈），仅更换模型 checkpoint。
- **对比方法**：GPT-5、Gemini 2.5 Pro、Claude Sonnet 4，以及 Qwen3-8B 的 base / +SFT / +SFT+RL 三档。
- **训练/测试分离**：评测用例按来源与任务标识符排除出训练集；但作者明确指出，由于生成内核可能以不同代码实现语义相似算子，**精确匹配过滤无法排除所有功能性近重复**，因此结果解释为"基准特定"而非"无重叠泛化"。
- **复现设置**：Triton 固定 3.3.0；语料验证与剖析用 MI325/MI350，推理用 MI355X；warm-up 25 ms、测量 100 ms；报 GPU-event 中位延迟，每次测量前 flush L2，测量循环后同步，不丢弃任何计时观测。
