## 摘要
现代LLM智能体在持久化工作区中运行，其累积的历史记录可能超过GPU KV容量和模型的原生上下文窗口。现有系统通常将较旧的上下文压缩为摘要，或稍后以文本形式检索，这要么丢失细粒度的执行证据，要么重复预填充模型已处理过的内容。我们提出了KVMem，一种KV上下文虚拟化系统，它将溢出的工作区历史记录作为分页KV状态，跨GPU内存、主机内存和NVMe保存。KVMem使用轻量级、模型原生的注意力空间索引来选择相关的历史块，并物化一个受模型原生上下文窗口限制的、依赖于查询的执行视图。在长达一百万token历史的长上下文智能体基准上的广泛评估，包括LongMemEval、MemoryAgentBench和AgentLongBench，表明KVMem通常比基于压缩的方法（处理上下文溢出的事实标准）实现更高的任务效用和更高的推理效率。在使用Qwen3.8-27B的DeepSWE长上下文测试中，KVMem将任务成功率从仅使用压缩上下文管理的43.8%提高到48.4%。在我们的本地部署评估中，KVMem在配备24 GB RTX 5090 Laptop GPU的现成笔记本电脑上运行Qwen3.6/3.8-27B NVFP4与MTP，虚拟化高达1M token的智能体工作区——这是模型原生256K-token上下文窗口的四倍。在单会话设置中，KVMem生成约50 tokens/s，为本地智能体执行提供交互式响应。更广泛地说，通过将可寻址工作区大小与LLM的原生上下文窗口解耦，KVMem为长时间运行的智能体提供了一条实用路径，使其工作区可以增长到超出该窗口。

## Abstract
Modern LLM agents operate in persistent workspaces whose accumulated history can exceed both GPU KV capacity and the model's native context window. Existing systems typically compact older context into summaries or retrieve it later as text, either losing fine-grained execution evidence or repeatedly prefilling content that the model has already processed. We present KVMem, a KV-context virtualization system that preserves overflowed workspace history as paged KV state across GPU memory, host memory, and NVMe. KVMem uses lightweight, model-native attention-space indexes to select relevant historical blocks and materializes a query-dependent execution view bounded by the model's native context window. Extensive evaluations on long-context agent benchmarks spanning histories up to one million tokens, including LongMemEval, MemoryAgentBench, and AgentLongBench, show that KVMem generally achieves higher task utility and greater inference efficiency than compaction-based approaches, the de facto standard for handling context overflow. In the DeepSWE long-context test with Qwen3.8-27B, KVMem improves task success from 43.8% with compaction-only context management to 48.4%.   In our local-deployment evaluation, KVMem runs Qwen3.6/3.8-27B NVFP4 with MTP on an off-the-shelf laptop equipped with a 24\,GB RTX 5090 Laptop GPU, virtualizing agent workspaces of up to 1M tokens-four times the model's native 256K-token context window. In a single-session setting, KVMem generates $\sim$50 tokens/s, providing interactive responsiveness for local agent execution. More broadly, by decoupling addressable workspace size from the LLM's native context window, KVMem provides a practical path toward long-running agents whose workspaces can grow beyond that window.

## 1. 核心问题与整体含义（研究动机和背景）

现代LLM智能体（Agent）运行在持久化工作区（workspace）中，工作区会累积用户指令、文件内容、工具输出、执行日志等大量历史上下文。随着智能体长时间运行，这些历史记录可能超出两个关键限制：

- **GPU KV缓存容量限制**：模型权重、运行时缓冲、推测解码状态和KV缓存争抢同一GPU显存，导致实际可用上下文远小于模型标称的最大窗口。例如在24GB显卡上，vLLM仅能支持约10K token上下文。
- **模型原生上下文窗口限制**：例如Qwen3.6-27B原生窗口为256K token，而长上下文智能体基准中轨迹可能达到数十万到数百万token。

现有系统处理上下文溢出的主流方式是**压缩（compaction）**：将较早的执行历史压缩为摘要。部分系统还辅以**文本检索**（如MemGPT、Mem0、MemoryOS等），将历史文本片段重新插入提示词。但这类文本中心的抽象存在两个耦合问题：

1. **保真度问题**：压缩必须在未来相关性未知的情况下决定保留哪些信息，可能丢失之后任务关键的低显著性细节（如文件中的某句话、工具输出中的某个值）。
2. **效率问题**：被压缩的历史文本一旦被检索回来，模型必须**重新预填充**这些已经处理过的token，产生重复计算开销。

论文指出，这些损失不是上下文溢出的必然结果——模型处理历史时已经算出了KV状态，问题只在于如何保存和选择性恢复。核心洞察是：借鉴虚拟内存思想，将智能体**可寻址的KV工作区大小与GPU上物理驻留的KV状态大小解耦**，用更大的后备存储保存溢出历史，并在需要时按需物化。

## 2. 方法论

### 2.1 核心思想
提出KVMem——一个KV上下文虚拟化系统：
- 将溢出历史保存为**分页KV块**，分布在GPU内存、主机内存和NVMe存储。
- 在每个智能体步骤，用**模型自身的注意力空间索引**选择相关历史KV块。
- 将选中的块物化成一个**有界、查询相关的执行视图**，视图大小不超过模型原生上下文窗口和GPU KV预算。

### 2.2 关键技术设计

KVMem由三个机制协同构成：

**(1) 步级内存调度（Step-Level Memory Scheduling）**
- 通过分析OpenHands SWE-bench Lite轨迹中的注意力分布，发现同一智能体步骤内相邻窗口的注意力KL散度仅0.070 bits，而跨越步骤边界的KL散度平均为2.59 bits（高37.3倍）。
- 因此KVMem**仅在每个智能体步骤边界**更新历史工作集，具体时序为：新步骤的预填充完成之后、解码开始之前进行一次工作集更新；解码期间工作集保持不变，新生成的KV追加在视图尾部。

**(2) 查询条件KV检索（Query-Conditioned KV Retrieval）**

采用**Mean-K紧凑块索引**，从模型的K向量中提取逐层逐头的均值作为块表示。

- 构造索引时先去除RoPE位置信息，得到与位置无关的K向量。
- 对每个历史块b，其第l层第g个KV head的Mean-K表示定义为：
  `\bar{k}_{l,b,g} = (1/|b|) Σ_{i∈b} \tilde{k}_{l,i,g}`
- 块大小为32个token，索引显著小于完整KV。
- 查询时的相关度评分：将查询Q向量（也去除位置信息）与每个块的Mean-K向量做缩放点积，然后在候选块集合上进行softmax归一化，最后跨查询token和层/头求平均得到块相关度：
  `R_b = Σ_m mean_{l,h} softmax_{b'∈C}( q^T_{l,m,h} \bar{k}_{l,b',g(h)} / √d )_b`
- 索引整体存放在主机内存中，GPU上仅驻留有界tile，以支持数百万token工作区的可扩展检索。

**(3) 分层KV管理（Tiered KV Management）**
- 区分**仓库视图（repository view）**和**执行视图（execution view）**。仓库视图记录每个块的存储位置；执行视图通过页表将非连续物理页映射到紧凑的逻辑顺序，避免复制到稠密缓存。
- **位置一致性**：RoPE编码的K只在其原始位置有效。KVMem以**不含位置信息的raw K**作为源，对选中的块在新的紧凑位置上重新施加RoPE（re-RoPE）；V不依赖位置可直接复制。对已在GPU上的块，若位置变化则做有界次数的delta re-RoPE，达到上限后从raw K重建以控制低精度累积误差。
- **主动换出（Proactive Stage-out）**：在预填充分块完成后异步将已完成块的KV复制到主机/ NVMe，使换出操作不阻塞后续换入。
- **检索感知的分层复用**：计算连续工作集的交集、新增和淘汰块，只加载GPU中不存在的块；被频繁召回但从GPU淘汰的块优先保留在主机内存；考虑最近性和累计召回频率来决定主机内存准入/淘汰。
- **打包与流水线重物化**：将多个非连续的块打包成连续主机缓冲批量传输；用双缓冲和CUDA事件实现CPU gather、H2D传输、GPU scatter和re-RoPE三个阶段在不同批次间重叠。

整体流程：
每个新步骤先执行当前查询的预填充（收集检索所需信号），计算Mean-K索引增量更新，然后进行工作集重选和KV物化，最后在组装好的执行视图上重新预填充当前查询（利用检查点避免重放旧上下文），再开始解码。

### 2.3 推理引擎
由于现有引擎（vLLM、SGLang、LMCache等）不支持这种动态查询相关视图的持久化、跨层检索和位置重映射，作者实现了原生C++/CUDA推理引擎**QW3**作为KVMem的执行基座，支持连续批处理、前缀复用、多token预测（MTP）等。

- **Full Context**：完整历史在模型可容纳范围内时的参考设置。

## 6. 主要结论与发现

- **效用优势**：KVMem在受控基准上普遍优于Sliding Window和Compact-only。在LongMemEval-S上达到85.6% (Full Context 86.6%)；AgentLongBench ≤256K时达到60.87%，甚至略高于Full Context的59.54%。MemoryAgentBench >256K时40.99%，高于Compact+RAG的34.80%。AgentLongBench 1M时50.0%，比Compact+RAG高8个百分点。
- **效率大幅提升**：KVMem前回答延迟仅0.38–1.81秒，而Compact+RAG需要26.63–416.38秒（包含摘要生成），即使排除摘要成本仍要10.63–39.24秒。KVMem将压缩后恢复延迟降低**11.4–53.8倍**。
- **消费级硬件可行性**：在24GB RTX 5090 Laptop上支持**1M token虚拟工作区**（4倍于模型原生256K窗口，12.5倍于GPU驻留80K执行视图），单会话生成速度约**50 tokens/s**。
- **服务器平台可扩展性**：可将Qwen3.6-27B工作区扩展到**10M token**，GPU内存保持约34GB不变，TTFT从0.43秒（256K）增至1.60秒（10M），解码吞吐稳定在75–85 tok/s。
- **DeepSWE长期任务提升**：Qwen3.8-27B + KVMem Pass@1从43.8%提高到48.4%，Pass@4从81.3%提高到93.8%（15/16任务在4次运行中至少成功一次）；预填充时间降低55.1%，请求墙钟时间降低15.4%，解码token数降低18.7%。
- 直接复用历史KV并恢复，避免了重复预填充，同时保留了比文本压缩更高的任务细节保真度。

## 7. 优点

1. **概念创新突出**：将KV缓存上升为可寻址、可分页的资源，解耦工作区逻辑大小与GPU物理容量，类比虚拟内存是巧妙且系统的视角。
2. **动机清晰且验证扎实**：通过注意力KL散度观察和top-k覆盖统计，为"何时召回"和"选取少量强相关块"的设计提供数据支撑。
3. **完整系统实现**：不只是仿真，实现了原生推理引擎QW3，能与实际执行路径整合。
4. **兼顾保真和效率**：避免了压缩的信息丢失和文本检索的重复预填充，在百万token规模展现出实用延迟。
5. **消费级硬件演示**：以RTX 5090 Laptop GPU运行27B模型并支持1M工作区，具有很强的实践说服力。
6. **模型迁移验证**：不修改任何机制切换Qwen3.6→Qwen3.8，在DeepSWE上仍获改进，证明设计通用性。
7. **客观的局限讨论**：承认KV复用非严格等价于重算、面对检索遗漏风险、存储开销大及黑盒API不可用性等。

## 8. 不足与局限

1. **实验偏差风险**：DeepSWE仅使用规范顺序下前16个任务，规模较小；测试量级上总共128条本地轨迹，对于软件工程基准可能代表性有限。
2. **缺少消融和敏感性分析**：没有系统评估块大小（32 vs 64 vs 128）、Mean-K vs 更复杂的多向量索引、调度策略选择、re-RoPE重建阈值以及各优化组件（主动换出、分层复用、流水线打包）的单独贡献。
3. **检索可能遗漏关键信息**：每一步只物化被选中的历史子集，若检索索引无法捕获某些任务关键但表观不相关的块，则会损失效用；论文未尽最大检索预算/视图大小扰动分析。
4. **KV复用并非数学等价**：尽管采用re-RoPE和查询重预填充，历史KV仍是在旧因果上下文中计算的；当上下文被重构时，可能存在轻微状态偏差，实验未评估极端场景下（如冲突信息）可能的风险。
5. **存储开销大**：KV状态比文本大很多，10M token工作区需约324GB NVMe + 64GB主机内存 + 34GB GPU，这限制了超大工作区在更小设备的可用性；索引本身也随工作区线性增长。
6. **无法适配黑盒API**：需要底层控制KV分配、检索、RoPE和存储传输，不能直接应用于基于API的LLM服务。
7. **并发多用户情况未评估**：系统当前面向单会话agent；多工作区在共享GPU/存储下的调度与资源竞争是新问题。
8. **缺少对照方法的成本敏感性分析**：例如增大压缩摘要预算、不同RAG块检索数量、长文本重排等对KVMem相对优势的影响未探讨。
9. **尚未在实际多用户生产部署中验证**，服务层经济和集成方式停留在设想层面。
