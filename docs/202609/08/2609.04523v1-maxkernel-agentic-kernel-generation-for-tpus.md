## 摘要
为加速器设计和编写高性能自定义内核是一项复杂的任务，需要深厚的硬件级专业知识。大语言模型（LLM）可以结合实时编译器反馈，构建用于内核生成的智能体系统。在这项工作中，我们提出了MaxKernel，一个多智能体系统，实现了三种不同的TPU内核开发范式：（1）一种人在回环（HITL）智能体，用于协作式、逐步设计；（2）一种自主（Auto）智能体，执行全自动、基于指标/跟踪的优化循环；（3）一种基于图的自主动态搜索，扩展自主智能体以对设计空间进行全局探索。所有三种范式都利用共享的专用子智能体池来负责规划、实现、自我调试、测试和硬件性能分析。我们在JaxBench上评估了MaxKernel，这是一个包含50个多样化TPU内核任务的综合基准测试套件，并评估了来自最先进开源模型的复杂真实工作负载。我们证明MaxKernel持续生成高度优化的实现，匹配专家手工调优基线，并在基准测试中提供显著的性能。我们的智能体已开源，可在https://github.com/AI-Hypercomputer/accelerator-agents/tree/main/MaxKernel获取。

## Abstract
Designing and authoring high-performance custom kernels for accelerators is a complex task that requires deep hardware-level expertise. Large Language Models (LLM) can be leveraged together with real-time compiler feedback to build agentic systems for kernel generation. In this work, we present MaxKernel, a multi-agent system that implements three distinct paradigms for TPU kernel development: (1) a Human-in-the-Loop (HITL) agent for collaborative, step-by-step design; (2) an Autonomous (Auto) agent that executes a fully automated, metric/trace-driven optimization loop; and (3) a Graph-Based Autonomous Search that scales the Auto agent for global exploration of the design space. All three paradigms leverage a shared pool of specialized sub-agents to handle planning, implementation, self-debugging, testing, and hardware profiling. We evaluate MaxKernel on JaxBench, a comprehensive suite of 50 diverse kernel tasks for TPUs, alongside complex, real-world workloads from state-of-the-art open-source models. We demonstrate that MaxKernel consistently generates highly optimized implementations, matching expert hand-tuned baselines and delivering significant performance across the benchmark. Our agent is open-sourced and available https://github.com/AI-Hypercomputer/accelerator-agents/tree/main/MaxKernel.

### 1. 核心问题与总体含义（研究动机与背景）

为深度学习加速器（尤其是 TPU）编写高性能自定义内核是一项对硬件专业知识要求极高的任务。程序员需要手动管理复杂的内存层次结构（如 HBM 与 VMEM）、编排 DMA 流水线、推导多维分块（tiling）策略等，同时还要面对底层编译器晦涩难懂的错误信息。即便借助 LLM 进行代码生成，零样本或少量样本的方法也常常因缺乏硬件反馈而失败。传统编译器调优方法（Halide、TVM、Ansor）虽有探索，但也需要大量领域知识或昂贵的演化搜索。

**核心动机**：构建一个将 LLM 与实时编译器反馈、硬件性能追踪（profiling）工具结合的智能体系统，使其能自动生成、调试并优化 TPU 内核，从而大幅降低人力成本，并探索智能体在高性能计算中是否能够达到甚至超越人类专家的水平。

### 2. 方法论：核心思想、关键技术细节与算法流程

**核心思想**：将复杂的内核开发任务，分解为一系列专化子任务，交由多个专用于代理（sub-agents）完成，并通过三种不同的编排范式来适应从人工深度控制到全自动大规模搜索的不同场景。

**2.1 专用子代理（Specialized Sub-agents）**

- **生成与修复代理**：
  - **Planning Agent**：基于硬件规格与参考代码编写高层优化方案。
  - **Implementation Agent**：将优化方案翻译为合法的 Pallas 代码，循环尝试编译，读取编译器反馈并修复代码。
- **测试与验证代理**：
  - **Test Synthesis Agent**：基于参考代码构建测试套件。
  - **Execution Agent**：在目标硬件上安全运行测试，验证数值正确性。
- **Autotuning Agent**：系统化探索超参数空间（如 block sizes、tile dimensions）寻找最优配置。
- **Profiling Agent**：利用 XProf 工具捕获硬件轨迹，分析执行延迟、内存带宽利用率和计算密度，识别瓶颈，为下一步优化提供反馈。

**2.2 知识库（Knowledge Store）与 RAG**

- 使用 RAG 管道按需检索外部知识库（Pallas、Mosaic、XLA 等框架文档与性能手册）。
- **关键设计**：知识库中**排除**了任何人工调优内核代码，以测试智能体在不依赖人类基线的前提下，能否独立发现 TPU 的优化技巧。

**2.3 三种编排范式**

- **Human-in-the-Loop (HITL)**：采用“一个代理执行，然后停止等待”的路由方式。用户可在任意子代理完成后审查中间产物，提供反馈并修正路径，适合复杂且需专家直觉介入的设计。
- **Autonomous Loop (Auto)**：全自动闭环流水线，执行序列为：
  - **准备阶段**：基于参考代码生成并冻结综合测试套件（防止“奖励作弊”）。
  - **计划与代码生成**：迭代进入 Plan Generation → Implementation → Compilation Validation。
  - **验证与测试**：检查编译性、数值等价性和基线性能。
  - **优化与性能分析**：自动调优 + XProf 追踪，将性能结果反馈给下一轮规划。
  - 关键机制包括：**修复失败快速短路（重新规划）**、**Best-of-N 状态滚回（保留历史最优）**、**路径硬约束（防止文件状态混乱）**。
- **Graph-Based Autonomous Search**：将 Auto 代理封装进**搜索图**框架中：
  - **SearchGraph**：每个节点代表一个内核状态（代码+方案+指标）。
  - 支持不同类型的搜索算法：
    - **并行搜索（Parallel Search）**：并发启动多条独立 Auto 轨迹，不互相竞争，分配大量迭代预算，深度成熟代码修改。
    - **束搜索（Beam Search)**：维护 top-k 候选前沿，每个候选进行较浅探索，然后剪枝低绩效轨迹。支持从中断中通过持久图形状态优雅恢复。

### 3. 实验设计与 Benchmark

**3.1 基准与数据集**

- **JaxBench**：包含 50 种 TPU 内核工作负载的基准套件。

  - 33 种来自 KernelBench 的融合操作符。
- 涵盖众多的运算，如密集/稀疏线性代数、复杂损失、各类归一化与高速融合操作。
- **SOTA OSS 模型实际工作负载**：包括 MLA v1、Qwen3-Next Gated DeltaNet、DeepSeek-V4 Sparse Attention、Mamba v2（SSD）、Ragged Page Attention v3 等。

**3.2 硬件与框架**

- 评估在 **TPU v6e** 硬件上进行。
- 性能测量通过 **XProf** 进行精确的片端测量，排除了主机端 JAX 调度和编译开销。

- 数值正确性用 jnp.allclose，atol=rtol=10⁻²（部分调整为10⁻¹）。

**3.3 对比方法**

- **Best-of-N（Zero-Shot）**：100次独立零样本生成，选最快正确样本。
- **MaxKernel Auto**：单轨迹迭代优化，限 5 次迭代，执行5次独立运行以报告性能中位数。
- **MaxKernel Parallel**：5 个并发 Auto 轨迹，选最快正确内核。
- **MaxKernel Beam**：束宽 3、最大深度 3、每节点 2 个分支，内评估循环限制 2 次迭代。

### 6. 主要结论与发现

- **零样本方法失效**：Best-of-N（100次）编译率仅 10/50，平均加速 1.08×，证明无反馈式生成无法处理 TPU 内核。
- **迭代闭环有效但单轨迹不稳**：Auto 中位数几何加速 1.39×，正确率 48/50，但 5 次独立运行结果差异较大，易陷入局部最优。
- **搜索显著提升鲁棒性**：
  - Parallel 搜索：**50/50 编译、50/50 正确**，平均加速 **1.58×**，fast₁ 达 34/50 。
  - Beam 搜索：50/50 正确，平均加速 1.49×，fast₁ 为 31/50。
- **可匹敌/超越人类专家**：在 8 个有专家参考的任务上，Parallel 平均加速 **2.32×**，Beam 1.78×，均高于专家手写的 2.02×；7/8 工作负载上超过了专家，例如 Paged Attention 达 6.74×（超专家 2.41× 的两倍以上）。
- **真实模型收益显著**，典型数据：DSv4 的 prefill 加速达 7.85×、Qwen3-Next 训练步骤加速 4.70×、MLA v1 延迟降低 8.68%。
- 搜索策略之间存在明显权衡：Parallel 深化单一路径，适合需多步调试的复杂改动；Beam 广度优先，但在浅预算下会惩罚需要深度调试的优化思路。

### 7. 优点

- **模块化多智能体架构**：清晰的职责分工（规划、实现、测试、调优、分析），极好的可组合性，可适配不同交互程度的用户场景。
- **多范式灵活设计**：从全人工到全自动再到大搜索空间，三种模式具有共享基础但覆盖不同需求，图搜索把内核优化抽象为通用的搜索图。
- **“测试套件冻结”防止奖励作弊**：这是 LLM 自动编程中很重要的方法论贡献。
- **严格性能纪律**：只采用 XProf 真实硬件计时排除调度和编译噪声，不用模拟器数据。
- **成绩透明且优秀**：公开了完整的 50 任务容差表（附表 A），主要结论全部来自真实 TPU 运行，且开放了代码社区使用的开源链路。

### 8. 不足与局限

- **单一硬件生态限制**：仅验证了 TPU（JAX/Pallas）与 XProf，结论是否能迁移到 NVIDIA GPU（CUDA/Triton）、AWS Tranium、MTIA 等尚未验证，虽然作者声称方法普遍适用但实验上没有给出跨平台验证。
- **LLM 依赖**：仅使用了单一的 Gemini 3.1 Pro 模型，不同 LLM 的泛化性、稳定性（agent 的推理能力差异）未做消融；同时对上下文长度、错误信息的解读能力有很强依赖。
- **成本与延迟**：并没有披露 Graph-based 搜索模式的时间和算力开销，这在实践中影响很多工程决策。
- **专家基线缺乏透明度**：8 个“熟练工参考”由谁编写、开发工时、是否受到 Pallas API 版本限制等细节不够充分，对比可能有偏差。
- **部分结果方差大**：Auto 模式多次运行离散程度较大（0.19~0.42 的加速区间跨度），说明系统的稳定性还在开发之中。Beam 搜索有空间降低并行度提升的可能性但作者用相同配置并未找到。
- **搜索评估偏静态**：对图搜索的分析主要通过把节点按时间排序画进展曲线，没有将搜索时间成本、中止时间和优化质量的帕累托面做量化分析。
