## 摘要
LLM 智能体通过反复组合候选内核并在真实 GPU 上测量其运行时长，来自动化 GPU 内核优化。现有系统通过为整个智能体会话或基准测试命令保留一块 GPU 来保证测量保真度。然而，这会导致利用率低下，因为只有一小部分命令执行过程需要独占 GPU 访问。共享 GPU 可以回收这部分闲置容量，但会引入资源竞争，从而损害测量保真度并误导智能体的搜索。我们提出 KREX，一种具有区域粒度独占性的并发内核智能体基准测试运行时。KREX 允许智能体在基准测试命令中标记涉及时序敏感操作的关键区域。该运行时随后在标记区域内强制独占，并允许区域外并发执行，从而在保持测量保真度的同时实现高吞吐量。为在区域内强制独占，KREX 会阻止新的竞争性 GPU 提交，并在冻结同级进程和隔离 CPU 核之前排空未完成的工作，从而同时保护 GPU 执行和驱动测量的宿主线程。为最大化区域外并发，KREX 在持久化上下文进程中复用 GPU 上下文，以避免重复的、节点范围的串行化上下文创建。我们在 NVIDIA 和 AMD GPU 上评估 KREX。与命令粒度独占基线相比，KREX 将基准测试吞吐量提升至多 3.4 倍，同时对于长于 10 ms、1 ms 和 0.1 ms 的内核，p95 计时膨胀可忽略不计，分别为 0.30%、1.58% 和 3.90%。

## Abstract
LLM agents automate GPU kernel optimization by repeatedly composing candidates and measuring their duration on real GPUs. Existing systems preserve measurement fidelity by reserving a GPU for an entire agent session or benchmarking command. However, this results in poor utilization because only a small fraction of command execution requires exclusive GPU access. Sharing GPUs could recover this idle capacity, but introduces contention that compromises measurement fidelity and misdirects the agent's search.   We present KREX, a runtime for concurrent kernel agent benchmarking with region-granular exclusivity. KREX lets agents mark critical regions involving timing-sensitive operations within a benchmarking command. The runtime then enforces exclusivity within marked regions and allows concurrent execution outside them, achieving high throughput while preserving measurement fidelity. To enforce in-region exclusivity, KREX blocks new competing GPU submissions and drains outstanding work before freezing sibling processes and isolating CPU cores, protecting both GPU execution and the host threads that drive measurements. To maximize off-region concurrency, KREX reuses GPU contexts in persistent context processes to avoid repeated, node-wide serialized context creation. We evaluate KREX on NVIDIA and AMD GPUs. Compared with command-granular exclusivity baselines, KREX delivers up to $3.4\times$ the benchmarking throughput with a negligible p95 timing inflation of $0.30\%$, $1.58\%$, and $3.90\%$ for kernels longer than 10 ms, 1 ms, and 0.1 ms, respectively.

- **共享 GPU 的代价**：MPS、MIG、时间片等现成共享机制是为吞吐和隔离设计的，无法直接用于保真测量——要么扰动计时，要么改变被测硬件（如 MIG 会改变硬件形态）。图 2a 显示，8 个命令/GPU 无保护共享时，报告的内核耗时被膨胀至独占时的 **1.5×–3.2×**；图 2b 显示竞争会导致候选内核**排序反转**（如 49.0 μs 的最佳候选在竞争下变为 53.9 μs，劣于对手的 49.3 μs），直接误导智能体搜索方向。
- **关键洞察**：命令中只有**计时区域**对竞争敏感，其余部分（导入框架、编译、输入生成、正确性校验）无需独占。因此应引入更细粒度的 **E3 区域粒度独占**：区域内独占、区域外共享，从而同时实现高利用率与高保真度。

## 2. 方法论：核心思想与关键技术细节

### 核心思想
KREX 是一个多租户运行时，接受带有显式标记关键区域的基准测试命令。在标记区域内强制**GPU 与 CPU 双重独占**；无命令处于区域时，同一 GPU 上的命令可并发执行。核心由两大机制构成：**区域内独占（In-region Exclusivity）** 与 **区域外并发（Off-region Concurrency）**。

### 关键技术细节

**（1）区域标记（Region Marking）**
- 通过一行上下文管理器 `region.critical()` 标记，支持两种模式：
  - 智能体自写完整程序并标记区域；
  - 固定基准脚手架中由脚手架作者预先标记（智能体仅提交内核，不能修改评测流程）。
- 设计理由：区域边界必须覆盖完整的测量语义（如包含预热循环、排除正确性检查），而代码本身无法表达“作者的测量意图”，因此要求显式标记（类比 Linux 的 `madvise`/`posix_fadvise` 将下层无法推断的意图上抛）。

**（2）区域内独占（8 步协议，见图 4）**
- **GPU 独占**：
  1. 上下文进程从该 GPU 的 coordinator 获取区域锁，一次仅允许一个租户；
  2. 原子认领共享内存门（gate），记录持有者身份与唯一 epoch；
  3. 关闭门后，唤醒各兄弟上下文进程中的 drainer 线程；
  4. 各进程维护**在途计数器（in-flight counter）**，提交前先自增再检查门；若门被他人持有则回退并挂起（不消耗 CPU）；
  5. drainer 捕获 epoch，等待计数器归零，并同步该进程拥有的所有上下文（含候选创建的次级上下文），完成后发布 epoch 确认；
  6. 持有者轮询确认，仅当所有兄弟均确认当前 epoch 且计数器为零才继续。
- **CPU 独占**：
  7. GPU 工作排空后，冻结兄弟进程树（利用 **per-tenant freezer cgroup**，可覆盖尚未注册的进程，如正在 `import torch` 的客户端）；
  8. 每个 GPU 分配**独立的物理 CPU 核切片**（本地 NUMA 节点），租户被限制在切片内；进入区域时，将持有者的提交线程**绑定到预留核**，并用 L2 大小缓冲区的 memset **刷新 L2 缓存**。
- **区域退出**：先等待区域内 GPU 调用完成主机侧提交 → 解冻兄弟 → 再重新开门释放区域锁（顺序严格，防止解冻延迟破坏下一持有者的冻结）。持有者死亡时由 dispatcher 接管清理，并以 epoch 绑定防止恢复路径与正常退出竞争。

**（3）区域外并发（Off-Region Concurrency）**
- **持久上下文池**：每块 GPU 在启动时创建固定数量的上下文进程，长期存活并顺序服务多个候选命令。客户端进程仍为每命令独立，通过 dispatcher 在候选边界配对（仅需控制面往返，不创建上下文）。这消除了每命令数百毫秒、且会**阻塞全节点所有 GPU** 的驱动级锁串行化开销。
- **驱动 API 拦截与转发**：客户端进程内的 shim 拦截驱动 API（含动态解析入口），通过共享内存 RPC 转发到配对的上下文进程；不支持的调用显式失败而非绕过池。
- **保真度优化三机制**：
  1. **最小共享内存传输**：单生产者单消费者环形缓冲区，内核启动仅需一条定长环形条目；
  2. **异步转发**：内核启动采用 fire-and-forget，转发与 GPU 执行重叠；计时事件与同步操作采用请求-应答；
  3. **自旋-停靠等待策略**：短暂自旋等待环形条目，超时才 futex 停靠，避免频繁唤醒带来的微秒级开销。
- **清理与故障恢复**：候选结束后释放其资源、保留上下文与内容寻址库缓存，并同步设备做健康检查；若出现粘性启动错误、未完成图捕获等，dispatcher 淘汰并替换上下文进程；后台检查处理超时或异常终止的客户端。

**（4）异构支持（R4）**
- NVIDIA：门实现在上下文进程的 RPC 分发循环中；计数器跟踪**主机提交**。
- AMD：可在池化路径或租户进程内由 ROCm 工具库实现（patch runtime dispatch table）；计数器跟踪**设备完成**（轮询线程递减）；租户仅在初始化后才加入 freezer cgroup（避免初始化期冻结失败）。

## 6. 主要结论与发现

- **吞吐量**：H20 上 KREX 达 **54.8 cmds/min**，为 native（16.0）的 **3.4×**、KREX-serial（17.5）的 3.1×；MI308X 上达 **50.4 cmds/min**，为 native（19.4）的 **2.6×**。KREX-serial 在 H20 上比 native 高约 9%，说明上下文复用本身即消除重复初始化开销。
- **保真度**：KREX 的 p95 膨胀为 **H20 2.5%、MI308X 2.4%**，远优于 ungated 的 154% / 150%，接近 native（0.9% / 3.2%）。对 >10 ms、1 ms、0.1 ms 内核，p95 膨胀分别为 **0.30%、1.58%、3.90%**。
- **候选排序**：KREX 的成对翻转率在各耗时差分组中均**保持在 native repeat 的 3 个百分点以内**；每轨迹 Kendall's τ_b 中位数：KREX **0.857**、native repeat 0.820、ungated 仅 0.432。
- **消融发现**：GPU 保护贡献了大部分保真度改善；叠加 CPU 保护进一步降低膨胀并在此配置下提升吞吐。H20 并发 16 时启用 MPS 使吞吐从 44.2 升至 54.8 cmds/min（+24%），而 P 仅从 2.23% 升至 2.45%。并发度是吞吐-保真度权衡的关键旋钮；MI308X 上并发

度较低（4）时，MPS 影响有限，说明 MPS 收益依赖并发度而非平台本身。

- **区域占比与收益的关系**：图 6 显示计时区域平均仅占命令墙钟时间的 8.5%，正是这一低占比解释了为何区域粒度独占能同时获得高吞吐（区域外大量并发）与高保真（区域内严格独占）。
- **异构验证**：AMD MI308X 上同样的机制（门 + 设备完成计数器 + freezer cgroup）取得与 NVIDIA 相当的效果，说明该设计不依赖单一厂商的运行时特性。

## 7. 局限与批判性分析

- **依赖显式标记**：KREX 要求命令显式标注关键区域。若智能体或脚手架作者标注不当（漏标预热、误标正确性检查、区域过窄或过宽），保真度与并发收益都会退化。论文将这一责任交给上层，属于设计权衡而非缺陷，但对第三方/不可信提交者的正确性缺乏自动校验或推断机制。
- **未覆盖计时之外的干扰源**：论文聚焦竞争对计时的扰动，但共享还可能通过**功耗/热节流、频率抖动、内存带宽争用**间接影响测量。图 2a 中 ungated 的膨胀已包含这些效应，但作者未单独分离各物理成因，故"区域内独占即可恢复保真"的因果链条在极端负载下仍有不确定性。
- **公平性配置差异**：`ungated` 未启用 MPS 而 `KREX` 启用，虽作者给出理由，但严格来说这不是完全对称的对比；读者应把 MPS 视为 KREX 默认栈的一部分而非独立变量（消融图 11 已部分回应此点）。
- **短内核保真度边界**：<0.1 ms 内核即便 native 重复也有 7.6%–12.1% 波动，KREX 在 0.1 ms 档的 p95 膨胀达 3.90%。这说明对极短内核，**测量噪声本身**可能成为主导误差，KREX 无法、也不应承诺消除固有抖动。
- **故障恢复与安全边界**：依赖 freezer cgroup、驱动 API 拦截与上下文池淘汰来处理僵死客户端，机制复杂；论文报告了清理路径，但对**恶意或持续对抗性**提交者（例如故意长期占用区域锁、伪造 epoch）的防护未充分展开，生产环境中可能需额外配额与超时策略。
- **迁移性**：结论基于 H20 与 MI308X 两代数据中心 GPU 与特定驱动版本；对消费级 GPU、多卡 NVLink 拓扑、以及未来引入的硬件分区（如更细粒度 MIG 演进）是否仍成立，需进一步验证。

## 8. 主要贡献与定位

- **概念贡献**：提出 **E3 区域粒度独占**，把"独占"从会话/命令粒度细化到"关键计时区域"粒度，并论证这是同时满足高利用率与高保真度的正确抽象层次。
- **系统贡献**：给出可落地的多租户运行时 KREX，包含 GPU 门协议（epoch + 在途计数器 + 兄弟同步）、CPU 冻结与核绑定 + L2 刷新、持久上下文池、驱动 API 转发与保真优化，以及跨 NVIDIA/AMD 的异构实现。
- **实证贡献**：在 20,000+ 真实智能体命令、3 个智能体、3 个基准套件、16+16 块 GPU 上量化收益——吞吐 2.6×–3.4×，p95 膨胀降至 ~2.5%，候选排序保真度接近 native repeat。
- **实践意义**：直接针对生产中"30 万条/日、峰值排队 4.8×"的容量瓶颈，把闲置 GPU 时间（实测仅 3.4% 利用率）转化为有效算力，对内核智能体规模化部署具有现实价值。

## 9. 一句话总结

KREX 通过"区域内独占、区域外并发"的细粒度多租户设计，在几乎不牺牲测量保真度（p95 膨胀 ~2.5%）的前提下，把内核基准测试吞吐提升到命令粒度独占的 2.6×–3.4×，为大规模内核智能体的测量基础设施提供了一条务实且可移植的路径。
