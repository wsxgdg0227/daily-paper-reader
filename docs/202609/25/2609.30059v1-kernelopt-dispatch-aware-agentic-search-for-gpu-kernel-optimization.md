## 摘要
深度学习推理和训练性能在很大程度上取决于 GPU 内核效率。PyTorch Inductor 等现代编译器能够从高层模型代码自动生成 GPU 内核，但常常大幅落后于专家手写的实现。近期基于 LLM 的内核优化器能够为独立内核缩小这一差距，但它们将编译后的模型视为黑盒，通常只优化单个独立内核，既不考虑编译器的结构性决策，也不对模型进行端到端验证。我们提出 KernelOPT，这是一个将编译后模型视为结构化产物的多智能体系统。它保留厂商库调用（cuBLAS、cuDNN），并利用五个由性能分析引导的 LLM 智能体专门针对生成的 Triton 子内核进行优化。由静态验证、多随机种子正确性、模型级 float64 回退验证和性能门控组成的四重验证级联，在优化过程中筛选候选方案，并对重新拼接后的模型进行端到端验证。如果没有候选方案通过全部四道门控，系统会保留编译器基线。该系统接受 PyTorch nn.Modules、独立 Triton 内核和 Helion 内核。在 250 个 KernelBench 问题上评估时，KernelOPT 在所有问题上相对于 \texttt{torch.compile} 取得了几何平均加速：1.40 倍（Level 1：51/100）、1.15 倍（Level 2：31/100）和 1.07 倍（Level 3：12/50）。

## Abstract
Deep learning inference and training performance depends critically on GPU kernel efficiency. Modern compilers such as PyTorch Inductor automatically generate GPU kernels from high-level model code, but frequently underperform expert-written implementations by wide margins. Recent LLM-assisted kernel optimizers can close this gap for standalone kernels, yet treat compiled models as black boxes, generally optimizing individual standalone kernels without respecting the compiler's structural decisions or verifying the model end-to-end. We present KernelOPT, a multi-agent system that treats compiled models as structured artifacts. It preserves vendor library calls (cuBLAS, cuDNN) and exclusively targets generated Triton sub-kernels using five profiling-guided LLM agents. A four-gate verification cascade of static validation, multi-seed correctness, model-level float64-fallback verification, and performance gating filters candidates during optimization and verifies the re-stitched model end-to-end. If no candidate passes all four gates, the system preserves the compiler baseline. The system accepts PyTorch nn.Modules, standalone Triton kernels, and Helion kernels. Evaluated on 250 KernelBench problems, KernelOPT achieves geometric mean speedups over \texttt{torch.compile} of 1.40$\times$ (Level 1: 51/100), 1.15$\times$ (Level 2: 31/100), and 1.07$\times$ (Level 3: 12/50) across all problems.

## 1. 核心问题与研究动机

- **背景**：深度学习推理/训练性能高度依赖 GPU 内核效率。PyTorch Inductor（`torch.compile` 默认后端）可将算子下沉为 Triton 内核，相对 eager 模式取得 2.27× 几何平均加速，但生成代码仍显著落后专家实现。
- **编译器局限的具体表现**：
  - 自动调优（autotune）的 tile-size 搜索空间有限；
  - 融合（fusion）启发式偏保守；
  - 跨算子重写仅依赖固定的手工模式匹配，缺乏通用代数化简框架。
- **现有 LLM 内核优化器的共同缺陷**：
  - 将编译后的模型视为**黑盒**，只优化孤立内核，不尊重编译器的结构性决策（dispatch decisions）；
  - 缺少对**重新拼接（re-stitched）模型**的端到端验证——即"权重提取正确性 + 性能门控"。
- **关键洞察**：编译产物本身是**结构化 artifact**——GEMM 交给 cuBLAS、卷积交给 cuDNN，Triton 只负责 pointwise/reduction 等子内核。编译器的分派决策通常是合理的，**真正次优的是剩余 Triton 代码的质量**。因此 LLM 应当"配合编译器结构"而非"绕开编译器"。
- **整体含义**：提出 KernelOPT，一个 dispatch-aware 的多智能体系统，只优化 Triton 子内核，并在模型级做严格验证；若所有候选均未通过验证，则保留编译器基线，保证**零回归**。

## 2. 方法论

### 2.1 核心思想
- 将 `torch.compile` 生成的模型形式化为 $M_0 = \langle \{k_1,\dots,k_m\}, L \rangle$：$\{k_i\}$ 为可优化的 Triton 子内核，$L$ 为固定的 cuBLAS/cuDNN 外部库调用。
- 优化目标：
  $$k^* = \arg\min_{k \in \mathcal{K}} \tau(k) \quad \text{s.t.} \quad V(k, k_0) = 1$$
  其中 $\tau(\cdot)$ 为 `do_bench` 实测时间，$V$ 为验证函数；搜索空间 $\mathcal{K}$ 无法枚举，通过 LLM 变换算子 $A_\theta: \mathcal{K} \times \mathcal{P} \to \mathcal{K}$ 访问（输入内核 $k$ 与 NCU 分析导出的优化方案 $p$）。

### 2.2 两阶段工作流（multi-kernel 模式五阶段）
1. **Inductor-aware synthesis**：用 `torch.compile(max_autotune)` 追踪模型，通过正则识别 `extern_kernels`（cuBLAS/cuDNN）并标记为不可替换；合并可融合的相邻算子组（如 `linear→mul→hardtanh→gelu`），由 LLM 从 ATen 算子图生成独立 Triton 内核，并用 2 个随机种子在 `allclose(1e-4)` 下做 eager 校验，失败最多重试 $K$ 次。此阶段本身即可带来大幅加速（如 L2-018 的 33×）。
2. **Baseline profiling**：`ncu --set full`（kernel replay）采集 SOL 吞吐、时长、寄存器、占用率及 NCU rules。
3. **Strategy analysis**：确定性分类瓶颈层级——near-optimal（任一 SOL > 80%）、memory-bound、compute-bound、underutilized；多内核输入额外用 LLM 决策 fuse-vs-optimize。
4. **迭代优化**：$T$ 轮 plan → execute → profile → beam selection。
5. **Re-stitch & verification**：替换子内核后做四门验证。

### 2.3 五智能体架构（LangGraph 状态机）
- **Profiler**（确定性）：分析源码中的 `@triton.jit`/`@helion.kernel`/`async_compile` 标记，配置 NCU（Triton/Helion 用 application replay），解析 CSV 构造结构化 profiling context，将 top-3 NCU rules 注入 planner 提示。
- **Strategy Analyst**：按 SOL 指标确定性分类瓶颈层级。
- **Planner**：每轮生成 $N$ 个优化方案，含 **meltdown detector**——当最近最多 6 个方向经归一化字符串匹配塌缩为 ≤2 个唯一方向时，强制多样性。
- **Executor**：最多 $K$ 次重试，**在同一对话内接收编译错误与正确性失败反馈**实现自纠；严格保持函数签名、禁止引入未定义常量、禁止替换为 PyTorch 计算、禁止 TF32 用于 `tl.dot` 累加。
- **Summarizer**：通过 diff 代码与 profiling 指标做因果归因，泛化为可复用经验项。

### 2.4 Profiling-guided Beam Search（Algorithm 1）
- 建模为有根树 $G=(V,E)$，节点为内核 $k_v$ 与延迟 $\tau(k_v)$，边为 LLM 变换。
- 用 **UCB($c=1.4$)** 平衡探索与利用。
- **多样性选择**（两阶段）：
  $$\text{DiverseSelect}(C,B) = \underbrace{\{\arg\min_{c \in C_i} \tau(c)\}_{i \in \text{chains}}}_{\text{每条链最优}} \cup \underbrace{\text{top-}(B - |\text{chains}|)}_{\text{全局最优}}$$
- 连续 2 轮无改进则提前终止；最终 $k^*$ 必须通过完整 $V$，否则返回 $k_0$。

### 2.5 四门验证级联
$$V(k,k_0) = \underbrace{V_{stat} \wedge V_{corr}}_{\text{每候选（门1–2）}} \wedge \underbrace{V_{model} \wedge V_{perf}}_{\text{端到端（门3–4）}}$$
- **门1 静态验证**：dry-run 捕获语法错误与运行时崩溃。
- **门2 多种子正确性**：3 个种子 `[0, 42, 1337]`，`allclose(1e-3)`；权重被 Inductor 外置时按 shape/dtype 匹配提取真实参数。
- **门3 模型级正确性**：更严 `1e-4` 容差；失败时启用 **float64 回退**：
  - 定义 $d_{ref}=\|r_{f32}-r_{f64}\|_\infty$，$d_{opt}=\|o_{f32}-r_{f64}\|_\infty$；
  - 若 $d_{ref} \ge 10^{-8}$，则误差比 $\rho = d_{opt}/d_{ref} \le 10$ 通过（正确的 TF32 内核 $\rho \in [1,3]$，算法错误的内核 $\rho > 100$）；
  - 若 $d_{ref} < 10^{-8}$（如 max/argmax 等精确操作），退化为尺度相对检查 $d_{opt}/\max(\|r_{f32}\|_\infty, 10^{-12}) \le 10^{-4}$；
  - 另有绝对上界 $d_{opt} \le \max(5\times10^{-3}, 10^{-3}\|r_{f32}\|_\infty)$；
  - 通过 `torch.compile(m, backend=fcapture)` 拦截参数展平，保留真实模型状态。
- **门4 性能门控**：$V_{perf} = \mathbb{1}[\tau_M(k_0 \to k) \le \gamma \cdot \tau_M(k_0)]$，$\gamma = 1.03$（3% 噪声裕度）；`do_bench(warmup=25ms, rep=100ms)` 在子进程中隔离执行以防 CUDA 状态泄漏。被拒时定向重试最多 2 次，仍失败则保留基线。

- **两大加速机制**：
  - **算法级重写**：如 L1-012（对角矩阵乘法 $O(N^3) \to O(N^2)$ 行缩放，88.63×）、L1-015（下三角矩阵乘法跳零迭代，20.26×）、L1-014（上三角求解，14.04×）；
  - **算子融合**：L2-018 将 5 个算子融合为一个内核并做代数化简（33.11×）、L2-064（8.30×）、L2-022（7.18×）。
- **教程内核也能获益**：10 个 Triton 教程中 4 个改进（最佳 1.70×，TF32 张量核配置）；10 个 Helion 教程中 5 个改进（最佳 1.08×，conv2d tiling 调整）。
- **回退分析（85 个回退）**：
  - 库主导 61 个（72%）：37 个 GEMM 主导（cuBLAS）+ 24 个 Conv 主导（cuDNN），厂商库在 H200 上已接近峰值；
  - 性能门控拒绝 15 个（全在 L1）——例如 L1-049 子内核 NCU 提升 5.84×，但端到端因 Triton dispatch 开销反而变慢，若无门 4 会被误报为改进；
  - 无 Triton 内核 7 个（LSTM/GRU 走 cuDNN RNN）；
  - 端到端正确性失败 2 个。
- **消融结论**：移除任一组件，优化成功率从 38% 降到 ≤10%；beam search 与 NCU profiling 各贡献 74%（19→5），性能门控贡献 84%（19→3）；**Inductor-aware 合成最关键**——去掉后 L2 优化数归零，因为 LLM 会浪费预算去替换高度优化的 cuBLAS/cuDNN。作者由此强调：**系统有效性来自结构性编排，而非 LLM 原始编码能力**。
- **更广义结论**：LLM 驱动的程序优化系统应当"**配合编译器**（利用其结构化标注）而非"绕开编译器"。

## 7. 优点

- **问题定位精准**：识别出"编译器分派决策合理、Triton 代码质量次优"这一关键结构，把 LLM 算力集中到真正有增益空间的地方，避免了无效开销。
- **四门验证级联设计严谨**：
  - 分层验证（搜索期宽松 1e-3 / 终验严格 1e-4）；
  - **float64 回退 + 误差比 $\rho$** 巧妙区分"TF32 累加顺序差异（$\rho\in[1,3]$）"与"算法性错误（$\rho>100$）"；
  - **权重提取**通过 `fcapture` 拦截 Inductor 参数展平，解决"随机权重导致输出无意义"的隐蔽陷阱；
  - **性能门控**捕获"子内核变快但端到端变慢"（dispatch 开销、隐式 `.contiguous()` 拷贝）的常见假阳性。
- **工程细节扎实**：子进程隔离 `do_bench` 防 CUDA 状态泄漏；meltdown detector 防

止方向塌缩；有界 FIFO 经验记忆采用非对称阈值（$s^+=1.05$ 比 $s^-=1.20$）——边际改进信息量低、显著回归信息量高，符合"避坑优先"的工程直觉。
- **可复现性与透明度**：开源完整代码；明确给出 LLM 后端、tokens 消耗、GPU-hours 分解、超参设置；对"benchmark-derived guidelines 提取于评估三周后、不影响结果"这一潜在污染点做了主动披露。
- **零回归保证**：通过性能门控 + 基线保留策略，把"LLM 优化器可能引入的性能抖动"转化为可控风险，使系统可作为编译器的"可选增强层"而非"替换层"，工程落地性更强。

## 8. 局限与待商榷之处

- **缺少同类方法的直接 head-to-head 对比**：以"硬件敏感性（H200 vs H100/Trainium）"与"架构不匹配（孤立内核 vs 完整 `nn.Module`）"为由，未与 KernelAgent、AccelOpt、K-Search、CudaForge、Astra 等做定量比较。这一辩解部分成立，但也意味着"优于现有 LLM 优化器"的核心主张缺乏受控实验支撑，只能靠文献综述间接论证。若要坐实，至少应在相同硬件上重跑 1–2 个可比基线。
- **单一硬件、单一 LLM**：仅在 H200 上验证，仅用 Claude Sonnet 4.6；跨 GPU 架构（如 A100、B200、消费级卡）与跨模型（GPT、Gemini、开源模型）的泛化性未知。作者虽称后端可插拔，但未给出实证。
- **成本极高**：~1,100 GPU-hours + 1.15 亿 tokens 用于 250 题；单次 NCU 提示约 60K tokens，要求后端 >100K 上下文。这意味着系统对长上下文模型有强依赖，且对"每题平均收益 vs 成本"的经济性讨论不足——对大量"回退"题（85/250 = 34%）而言，算力基本被浪费。
- **消融规模受限**：6 组消融仅在 50 题（C6 仅 20 题 L2）上做，虽通过 Fisher 精确检验达到 $p<0.01$，但小样本 + 分层加权采样的代表性仍有边界；作者自己也承认全量需 ~5,000 额外 GPU-hours。
- **加速主要来自少数"算法级重写"**：L1 的 1.40× 由 88.63×、20.26×、14.04× 等极端案例拉高，几何平均对少数离群值敏感；若看中位数或"优化成功率（38%）"，收益更为温和。**大部分题（回退 85 + 未显著改进）并未受益**。
- **依赖 NCU 与 Inductor 内部结构**：正则识别 `extern_kernels`、`fcapture` 拦截参数展平、`async_compile` 标记解析等均绑定 PyTorch/Triton/Inductor 具体版本（2.7.0 / 3.3.0），上游 API 变动可能使系统失效，**脆弱性较高**。
- **仅限单 GPU 推理**：未涉及分布式（TP/PP/EP）、训练反向传播、通信-计算重叠、MoE 路由等场景，适用范围相对窄。
- **NCU 分析开销未充分讨论**：kernel replay 模式下对 250 题做 `--set full` 采集本身耗时显著，虽计入总预算，但未见"分析成本 vs 优化收益"的分项拆解。

## 9. 方法论层面的启示

- **"LLM 应作为编译器的协作者而非替代者"**：本文最有价值的观点不是某个具体技巧，而是**把优化空间限定在编译器结构标注的缝隙里**（只改 Triton 子内核，不动 cuBLAS/cuDNN 分派）。这与"让 LLM 从头写 CUDA 打败 cuBLAS"的思路形成鲜明对比，也是消融中"去掉 Inductor-aware 合成后 L2 优化数归零"这一结果的根本原因。
- **验证比搜索更关键**：四门级联（静态 → 多种子正确性 → 模型级 float64 回退 → 性能门控）说明，在 LLM 生成代码的场景下，**如何可靠地说"不"** 往往比"如何生成更好的代码"更决定系统成败。尤其 float64 误差比 $\rho$ 的设计，为"区分数值容差与算法错误"提供了一个可复用的模式。
- **性能门控的必要性**：L1-049 案例（子内核 5.84× 但端到端变慢）是一个极具代表性的反例，提醒所有"内核级优化"研究：**局部指标不等于全局收益**，dispatch 开销与隐式内存拷贝会吞掉子内核收益。
- **有界记忆 + 非对称阈值的工程合理性**：只记录"显著改进"与"显著回归"，避免被大量边际案例淹没；跨运行策略追踪器（成功率 <30% 标记 `AVOID`）提供了一种低成本的"元学习"机制。

## 10. 一句话总结

KernelOPT 通过 **dispatch-aware 的多智能体编排 + NCU 分析驱动的 beam search + 四门验证级联**，把 LLM 的优化能力精准投放到 Inductor 生成 Triton 子内核这一"次优但可改"的空间，在 KernelBench 250 题上取得 L1 1.40× / L2 1.15× / L3 1.07×（合计 1.23×）的几何平均加速且零回归；其最大贡献是**"与编译器协作"的系统性框架与严谨的验证方法论**，最大短板则是**缺乏与同类 LLM 方法的直接对比、单一硬件/模型验证以及高昂的算力与上下文成本**。
