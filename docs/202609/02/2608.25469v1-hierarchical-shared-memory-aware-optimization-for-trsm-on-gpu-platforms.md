## 摘要
三角多右端项求解（TRSM）是基本的BLAS Level-3操作，支撑着LU/Cholesky分解、稀疏直接求解器和矩阵求逆。在本文研究的左侧下三角情形中，高效的GPU实现仍具挑战性，因为前向代入引入了严格的行向依赖，而共享内存过于稀缺，无法容纳宽数据类型（如双复数）的两个操作数矩阵。本文提出了HSMA-TRSM，一种面向NVIDIA A100、NVIDIA H800和Hygon DCU Z100加速器上左侧下三角TRSM的分层共享内存感知优化框架。对于小规模场景（m,n<=64），我们通过循环展开和指令重排设计了流水线计算-内存重叠机制，并提出一种双线程组七级流水线策略，以应对双复数类型的共享内存限制。对于大规模问题，我们引入了一种对角块解耦优化，其对角块求逆的共享内存占用为O(IB)，从而可根据矩阵规模和硬件特性自适应选择块大小。一个基于离线分析和在线查找的编译时配置选择框架，为每个平台选择最优块大小，且零运行时开销。在NVIDIA A100、H800和Hygon DCU Z100上评估，HSMA-TRSM相比cuBLAS和rocBLAS分别实现了最高2.05倍和2.06倍的加速比。在共享内存受限的双复数小规模算例中，以及在自适应分块改善以GEMM为主的更新的大规模实型算例中，性能提升最为显著；而在某些场景下，成熟的厂商内核留下的优化空间较小。

## Abstract
Triangular Solve with Multiple Right-hand Sides (TRSM) is a fundamental BLAS Level-3 operation that underpins LU/Cholesky decomposition, sparse direct solvers, and matrix inversion. In the left-side lower-triangular case studied in this paper, efficient GPU implementation remains challenging because forward substitution introduces strict row-wise dependencies, and shared memory is too scarce to hold both operand matrices for wide data types such as double complex. This paper presents HSMA-TRSM, a hierarchical shared memory-aware optimization framework for left-side lower-triangular TRSM on NVIDIA A100, NVIDIA H800, and Hygon DCU Z100 accelerators. For the small-scale regime (m,n<=64), we design a pipelined compute-memory overlap mechanism through loop unrolling and instruction reordering, and propose a dual thread-group seven-stage pipeline strategy to address shared memory constraints for double complex types. For large-scale problems, we introduce a diagonal block decoupling optimization with an O(IB)shared-memory footprint for diagonal block inversion, enabling adaptive block size selection based on matrix scale and hardware characteristics. A compile-time configuration selection framework based on offline profiling and online lookup selects the optimal block size per platform with zero runtime overhead. Evaluated on NVIDIA A100, H800, and Hygon DCU Z100, HSMA-TRSM achieves peak speedups of 2.05xover cuBLAS and 2.06xover rocBLAS. The gains are strongest in shared-memory-constrained double-complex small cases and in large real-type cases where adaptive blocking improves GEMM-dominated updates, while mature vendor kernels leave less optimization headroom in some regimes.

## 论文总结：HSMA-TRSM——面向GPU平台的TRSM分层共享内存感知优化

### 1. 核心问题与整体含义（研究动机和背景）

- **TRSM 的定义与重要性**：三角多右端项求解（TRSM）是 BLAS Level-3 中的基础运算，用于求解 `op(A)X = αB`，其中 A 为三角矩阵、B 为稠密多右端项矩阵。它是 LU/Cholesky 分解、稀疏直接求解器、矩阵求逆和最小二乘问题中的关键环节，其执行效率直接影响上层数值计算应用的整体性能。
- **核心挑战（动机）**：
    - **行向前代依赖**：左侧下三角 TRSM 的前向代入具有严格串行的逐行依赖链，限制了并行度与流水线挖掘潜力。
    - **共享内存容量瓶颈**：GPU 片上共享内存极度稀缺（DCU 为 64KB/block，A100/H800 目标配置为 48KB/block），而双复数（double complex）等宽类型数据占用量极大——单块 64×64 双复数矩阵即占满 64KB，导致矩阵 A、B 无法同时驻留片上。
    - **小规模场景低算术强度**：小规模 TRSM（m, n ≤ 64）为访存密集型（算术强度约 O(1)），无法通过 GEMM 直接计算；传统粗粒度"载入-计算-回写"阶段划分阻碍了内存延迟隐藏。
    - **大规模场景固定分块欠优**：厂商库（如 rocBLAS）对大矩阵固定分块大小为 128，无法随矩阵规模与硬件特性自适应调整；其融合算子在对角块求解中需 `4 × I_B² × sizeof(datatype)` 共享内存（即 O(I_B²)），严重限制了可行分块上限。
    - **可移植性不足**：既有优化工作多为单一架构定制（如仅 CUDA），难以在 NVIDIA 与 Hygon DCU 等异构平台间高效迁移。
- **整体含义**：本文旨在提出一套层次化、共享内存感知的框架，在同一声明下同时解决小规模访存瓶颈、大规模共享内存污染、跨平台可移植性三个层面的问题，填补厂商实现（cuBLAS/rocBLAS）和各学术优化方案在此空间中的空白。

### 2. 方法论：核心思想、关键技术细节与流程

**总体核心思想**：以 64 × 64 为分界（该分界有实验数据与性能交叉点支撑），将问题划分为两个优化域——小规模直接求解（共享内存驻留）和大规模分块 GEMM 化求解，并分别针对各自资源瓶颈（访存 vs 片上容量 vs GEMM 密度）做专门设计。整体框架按"矩阵规模 × 数据类型"自动选取最优执行路径，用编译期配置选择实现零运行时开销的跨平台自适应。

**关键技术细节（分模块）**：

- （1）小规模（m, n ≤ 64）：
    - **共享内存直接求解策略**：将矩阵 A 整块缓存至共享内存，矩阵 B 的列按线程/线程组分配并滞留于寄存器中。不同列之间相互独立可并行，而对行间依赖，采用逐行推进方式计算，在加载阶段用向量化指令（`float4`、`double2`）提升带宽利用率。
    - **计算-访存流水线重叠**：利用 GPU 访存指令异步特性（`ld.shared` 仅到 `__syncthreads` 才阻塞），改变传统"先载入 A→载 B→解 B→写回"的粗粒度分段流程，重构为逐行流水线。
    - **循环完全展开 + 指令重排**：通过把将来行的加载提前、把已完成行的写回延后，加深 load-compute-store 流水线的深度，消除相邻迭代间的流水线气泡。
    - **双线程组七级流水线（面向双复数）**：当 B 为双复数且 m=64 使 A 单独占满 64KB 共享内存时，采用 2×2 分块矩阵 A（A₁₁, A₂₁, A₂₂）与 4×1 列分块矩阵 B（B₁, B₂, B₃, B₄）的分区方案，在 16KB 子区上构造两个线程组分工合作的七阶段流水线（加载阶段 / 求解阶段 / 更新阶段 / 回写阶段互相穿插），实现在内存容量受限下的计算与访存完全重叠。

- （2）大规模（m > 64 或 n > 64）：
    - **两阶段分块算法**：
        - 阶段 1（并行对角块求逆）：将三角矩阵 A 按对角线切分为 `(k+1)` 个 N_B×N_B 对角块；因对角块相互独立，将各块并行调度到不同线程块上同时求逆，求得 `D_0⁻¹, ..., D_k⁻¹`。
        - 阶段 2（顺序 GEMM 更新与求解）：对第 r 个对角块，先执行更新 `B_r ← B_r − A_{r,[0:r]} × X_{[0:r]}`（K 维随迭代增长，为 `r × N_B`），随后用预计算逆 `D_r⁻¹` 做对角块求解 `X_r = D_r⁻¹ B_r`。阶段 2 因数据依赖必须顺序执行。
    - **对角块解耦（核心创新）**：传统融合算子（对角块求逆 + 回代 + 小 GEMM）需要 `4 × I_B²` 的共享内存（O(I_B²)）。本文将流程"解耦"，重构为**纯回代式对角块求逆算法**，基于列级数据驻留（每次只加载相邻两列，维护当前列+已解列数据）；由于回代天然具有列间依赖，每步只需当前待解列，无需整块驻留。由此共享内存占用降为 `2 × I_B × sizeof(datatype)`——复杂度由 O(I_B²) 降至 O(I_B)。
    - **双缓冲异步计算流水线**：为消除列级加载串行等待，将共享内存拆分为两个缓冲区 a₀/a₁，交替执行"计算当前列逆矩阵列"与"预取下一列"（`cp.async` 风格异步），两步轮转实现加载-计算时间重叠。双缓冲使实际占用增加到 `4 × I_B`，但总复杂度仍保持 O(I_B)。
    - **自适应分块（编译期配置选择）**：
        - 离线剖析：预构建阶段遍历候选块大小集（32/64/128/256 等），对各"规模 × 数据类型"组合实测性能，滤除次优配置，构建映射表（"规模 × 数据类型 → 最优分块"）。
        - 在线查找：运行时解析输入维度与类型，查表选取最近匹配规模的最优块；未记录规模用最近邻策略。调优开销全部转移到离线阶段；运行时仅一次哈希查表，零附加开销。

### 6. 主要结论与发现

- **小规模区效率大幅提升**：在 m=64 双复数时，A100 达 15.88 GFLOPS（比 cuBLAS 提升 14.5%），H800 达 12.47 GFLOPS（相对提升 105.4%），DCU 达 3.53 GFLOPS（相对于 rocBLAS 提升 96.1%）。H800 顶点达到 2.05 倍加速比（双复数），DCU 浮点复数达 86.3% 相对提升。float/double 在 NVIDIA 平台普遍提升多在 1.1×–1.3× 区间（因 vendor 内核本身已较强）。
- **小规模双复数是亟需专门设计的边界条件**：大块即 64KB 满载场景更适合用分区流水线（而非转成大规模 GEMM 路径），因为 GEMM 预处理的启动/分块开销此时还无法被摊销。
- **对角块解耦突破分块上限**：将共享内存足迹从 O(I_B²) 压缩到 O(I_B) 使更大块（如 512）成为可能；矩阵越大，收益越集中在大规模 GEMM 更新部分——A100 双复数规模 2048→8192 时，GEMM 更新占比从 54.8% 增至 88.0%，而对角块求逆占时占比从 20.7% 降至 3.7%。
- **自适应分块优于固定块**：相比 rocBLAS 固定 N_B=128，在 DCU 上将 m=1024 的 double 提升 39.3%、m=8192 提升 23.8%（float 在 m=16384 提速 1.63×；double 达 2.06×），验证了"无单一固定块大小能在全规模范围内最优"的核心论断。
- **跨平台有效性**：编译期查表方式把调优成本转移至离线，runtime 仅一次查表无额外开销，在三种平台上均能稳定生效。

### 7. 优点

- **问题定位精准**：明确指出"小规模 → 访存密集 O(1) 算术强度"与"大规模 → 需 GEMM 化提高算术强度"的矛盾，由此将框架自然分为两条互补路径（roofline 模型贯穿全文）。
- **极具针对性的分层设计**：以 64 为分界而非仅取共享内存容量推断，与实测性能交叉点匹配；并对边界特殊情况先判是否大块与双复数，体现工程判断力而非一味增加复杂度。
- **双线程组七级流水线的创新性**：面向"矩阵 A 单独占满 64KB 共享内存"特殊边界，设计了两个线程组（加载/计算职能分离）完成存储下界场景下的异步流水，方案简洁且资源需求可控。
- **资源最优化的精巧算法优化**：将传统 O(I_B²) 对角块求逆重构为 O(I_B) + 双缓冲，既保住了异步效果又腾出分块选择的自由度。该结构具备一般性——

### 8. 局限性

- **理论深度有限**：对 64 分界的形成仅有实验验证，缺少进一步的上界分析或性能模型推导（如精确的访存/计算权衡解析式），其普遍指导意义因此受限。
- **未覆盖非方阵与 batch 场景**：论文全部实验均为方阵（m=n）；对带状三角阵、多右端项列数远大于行数（或反之）的极端宽/高场景、以及 STRMM/BATCH-TRSM 等生产形态未做适配说明。
- **跨平台“可移植”仍有隐含假设**：虽然设计不依赖 CUDA 专有特性，但对 `cp.async` 等指令的利用暗示底层需具备类似异步拷贝能力，迁移到无此指令集或共享内存更小的架构时需要回退方案。
- **消融实验缺失**：未逐项单独验证“列级驻留”“双缓冲”“流水线重构”“向量化加载”各自的量化贡献，读者无法判断各技术在不同规模区间的边际收益；离线剖析开销（构建映射表所需的总机器时）也未透明报告。
- **边界情形覆盖不足**：m=64 之外的邻近规模（如 80/96）由最近邻查表策略近似处理，但实验数据未报告该近似策略相对精确调优的性能损失。

### 9. 对研究领域的启示

1. **“以共享内存为中心的算法重构”成为 GPU 数值库开发的新视角**：本文表明，在存储墙上瓶颈突出的 GPU 上，与其追求 GEMM 峰值利用率，不如优先减少片上驻留量，改变数据结构与任务划分来换取容量余量——这一原则可推广到稀疏直接求解器、特征值分解等更多 Level-3 类算子。
2. **离线调优 + 编译期配置替代运行时启发式**：大部分厂商库的启发式调参依赖运行时决策，本文用“离线测量构建映射表”的方式实现了零运行时开销的自适应，为跨厂商、跨代际 GPU 的 BLAS 层开发提供了可复制的工程范式。
3. **大小规模之间的“性能断层”值得更多关注**：现代 GPU 数值库的优化通常聚焦大 GEMM，而 m、n≤128 的“内存受限区”在深度学习小 batch、科学计算小矩阵中有实际需求；本文提出的规模分层与路径选择思想提示该区域有独立优化的必要性与可行性。
