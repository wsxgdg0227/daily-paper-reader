## Abstract
We introduce PTXBench, a benchmark for evaluating and adapting large language models (LLMs) to use architecture-specific PTX for GPU kernel optimization. PTXBench measures functional correctness, whether selected target instructions execute at runtime, and speedup over frontier libraries across GEMM and attention workloads on H100 and B200 GPUs. Our evaluation shows that architecture-specific PTX capability remains uneven: success rates fall substantially on complex attention backward workloads, and executing the target instructions does not necessarily translate into competitive performance. No evaluated model consistently matches frontier libraries across the suite. We further adapt Qwen3.6-27B using supervised fine-tuning. Repair-conditioned training improves several tasks, but generalization remains uneven; data coverage, balance, and the quality of the reasoning teacher matter in addition to dataset size. PTXBench provides an auditable testbed for measuring and improving LLMs' ability to exploit evolving GPU architectures.

## 论文提出的方法论

### 核心思想

论文提出 **PTXBench**，一个针对“架构特定 PTX 编程能力”的可控测试平台与适配框架。其核心思路是将问题收集（FlashInfer-Trace 工作负载）、架构受控知识（知识包）和评估流程三者分离，使得同一个流程可以扩展到不同算子集合、模型和硬件。除了端到端正确性外，它单独度量“目标指令是否在运行时真正执行”，并将“功能正确性”“目标指令执行”和“相对前沿库的加速比”三者相互解耦。

### 关键技术细节

- **任务设计**：每个 PTXBench 实例由参考算子（基于 cuBLAS、cuDNN、FlashInfer 等前沿库实现）、固定工作负载、目标 GPU 架构、以及要求使用的目标 PTX 指令族构成。模型从零生成带内联 PTX 的 CUDA 内核（CUDA-PTX），而非修改已有参考代码。
- **受控架构知识包**：为了测量“架构特定推理”而非“文档检索能力”，基座提示中有知识包，包含：架构参数、PTX 指令的 CUDA 包装函数、布局/同步/内存一致性契约，以及专家验证过的调度原则。一个架构知识包的 token 数约为 20k–30k。消融实验表明：若没有这些架构提示，模型几乎不使用指定的 PTX。
- **多轮智能体协议（MiniPTXAgent）**：
  - 模型在固定轮次内生成内核，系统编译候选内核后进行内存安全检查、错误返回、功能评测和延迟测量。
  - 正确性检查用 `torch.allclose`（`atol=rtol=1e-2`），并检查输出形状与数据类型。
  - 性能测量：每次运行有 10 次 warmup 和 50 次计时迭代，取中位数，参考 latency 与候选 latency 之比为加速比。
- **目标指令执行检测**：
  - 静态分析 SASS（CUDA 二进制汇编）看是否出现选定的指令族，如 Hopper 上的 `HGMMA`/`UTMA` 系列，Blackwell 上的 TCGEN05 路径的 `BUTC*`/`LDTM`/`STTM`。
  - 但静态存在不足够，还要用 Nsight Compute（NCU）动态统计“谓词激活的线程计数”，确认指令真的在固定工作负载下执行，而不是出现在死代码或未启动 kernel 中。
- **Fixit 适配方法**（面向后续 SFT 监督数据构造）：
  1. 从待适配模型 π0 采集失败内核 k⁻ 及执行反馈 e（错误信息等）。
  2. 用修复教师 πR 生成修复后的内核 k⁺；只保留通过功能正确性检查的修复。
  3. 让推理教师 πT 生成一段修复推理过程 r，说明从失败到修复的因果路径。
  4. 学生模型被训练为：给定原始问题 x、失败内核 k⁻、反馈 e，学习输出“推理 r + 修复内核 k⁺”。

### 归一化指标

论文借鉴 KernelBench，定义了“输出正确内核且加速比超过 p 的轮次比例”等聚合度量：

- `Fast_p`：成功率与速度分布混合的指标；
- `Fast Inst.p`：仅计算“正确 + 执行目标指令 + 超过加速比 p”的轮次；
- `Target instruction correctness`：功能正确且运行时执行了目标指令。

## 实验设计

### 使用的基准与场景

- 在 **H100（Hopper）** 和 **B200（Blackwell）** GPU 上评测。
- 主要负载为 BF16 GEMM、非因果与因果的 MHA 前向/反向，共 5 类问题。
- 主负载形状：MHA 用 batch=4，heads=48，seq=4096，head_dim=128；GEMM 为 A(8192×5120) × B(7168×5120)ᵗ。
- 性能参照库：GEMM 用 cuBLAS；MHA 用 cuDNN；GQA 用 FlashInfer。
- 泛化测试扩展到 head_dim=64/96 的 MHA、GQA（ragged/paged 等）以及 Triton 跨语言生成等。

### 对比的模型

- 评测组：Gemini 3.1 Pro、Claude Opus 4.8、GLM-5.2、Qwen3.6-27B。
- 适配实验组：以 Qwen3.6-27B 为待适配模型，Gemini 3.1 Pro 作为修复教师，GLM-5.2 或 Qwen3.6-27B 自身作为推理教师。
- 另与 Triton 内核生成、CuTeDSL 等上层语言生成做了比较性实验。

### 实验类型

- **能力横评**：同样负载在 H100/B200 上比较 4 个模型的正确定性、目标指令执行率和最佳加速比。
- **上下文消融**：对 Gemini 3.1 Pro 比较“仅架构参数 / 加 PTX 模板函数 / 再加架构契约”的效果。
- **SFT 数据配方实验**：构造 7 个训练检查点（s0~s6），对比 KernelGen vs Fixit 格式、问题覆盖是否平衡、推理教师是否更强等因素。
- **泛化与跨语言迁移**：观察 s1 对 d64/d96/GEMM/GQA 的迁移，以及在 Triton 生成上的正确性与性能变化。
- **SFT vs 测试时提示**：对比带专家指导/检索修复样例的 prompt-time 方法与权重更新的 SFT。

### 充分性评估

- 优点：消融设计清晰，覆盖了训练数据构造的多个关键维度；对正确率、目标指令执行率和性能做了分离度量；多轮 agent 环境下评估更贴近实际用法。
- 不足：
  - 主负载规模还不算广，只涉及 BF16 GEMM 与 attention 的有限形状；

## 论文的主要结论与发现

1. **能力不均衡**：
   - LLM 在 GEMM 与 MHA forward 负载上经常能得到正确内核，但在复杂的 attention backward 上成功率大幅下降。
   - 即使代码中执行了目标 PTX 指令，也未必带来可观的加速；许多正确内核仍明显慢于 cuBLAS/cuDNN/Flash

Infer 等前沿库。这说明“会用新指令”和“用得足够高效”是两种能力，前者只是后者的必要不充分条件。

2. **架构特定知识注入是 PTX 有效使用的前提**：
   - 消融实验显示，仅提供架构参数时模型几乎不生成任何目标 PTX 指令；加入 PTX 模板函数与架构契约（布局、同步、内存一致性规则）后，目标指令使用率显著跃升。
   - 上下文知识包 token 规模约 20k–30k，说明模型并不天然具备“架构细节→合法内联 PTX”的推理能力，需要显式的受控提示来补偿。

3. **后训练（SFT）能带来明显收益，且与测试时提示互补**：
   - Fixit 格式（失败内核 + 执行反馈 → 推理修复过程 + 修复内核）比单纯 KernelGen 格式（直接生成正确答案）在目标指令执行率与端到端成功率上更优。
   - 带推理教师（GLM-5.2）的镜像训练在部分任务上优于仅有弱推理教师（Qwen3.6-27B）的配方；覆盖更多问题类型（含 GEMM、backward）会造成相互干扰，需要在训练数据配比上谨慎权衡。
   - 训练后模型（s1）的泛化能力在部分形状（d64 forward 等）上有提升，但在 GQA、d96 backward、Triton 跨语言生成上仍不稳定，甚至出现正确率下降，说明任务分布外泛化仍是瓶颈。

4. **静态与动态指令检测相互补充**：
   - SASS 静态分析可以快速过滤掉完全不含目标指令族的候选；NCU 动态计数能揭示“指令存在但从未执行”的情况（如死代码、未启动 kernel、谓词恒为 false）。
   - 基准设计中的一个被低估的复杂点：CUDA 的 stream-ordered 内存分配可能导致内核在 profiling 时尚未完成对临时 buffer 的写入，造成无法分类的错误，这提示评估管线需要处理异步执行带来的时序歧义。

5. **正确性与速度需要分开报告**：
   - 论文指出，仅报告“内核生成正确率”会掩盖大量在正确但性能低下的候选；仅报告“加速比超过阈值的比例”又无法区分性能来自目标指令还是其他优化技巧。PTXBench 的三维度量（正确、执行目标指令、加速比）为后续内核生成研究提供了一个可复现的评估模板。

## 论文的局限性（作者未充分展开讨论的部分）

- **数据规模与泛化范围有限**：训练与主评测仅覆盖 BF16 精度下的 5 类问题与少量形状，未涉及 FP8/FP4、卷积、稀疏算子、多节点通信等工业界更广泛的高价值场景。
- **硬件覆盖仍然偏窄**：虽然同时评测了 Hopper 与 Blackwell，但未涉及更老架构（如 Ampere）以考察模型能否区分“版本正确”的 PTX 约束（如 `cute::arch` 中不同代际 TMA 的语义差异）。
- **对模型规模的依赖未知**：所有 SFT 实验集中在 27B 模型上，未验证结论在更大（或 MoE、推理时扩展）模型上是否成立；评测组的 API 模型也多为闭源，无法复现其具体训练条件。
- **推理过程（CoT）的质量控制较粗**：Fixit 方法中学生的推理文本由教师生成，论文没有系统度量“推理文本本身的正确性是否与最终修复质量强相关”，也没有将推理监督与直接“只给修复代码”的对照组做严格隔离。
- **评测稳定性问题**：正确性阈值使用 `atol=rtol=1e-2`，对 BF16 较宽松但对量化输入可能过宽；性能取中位数而非更稳健的几何均值，且未报告多次独立评测的方差。

## 论文价值评估与领域定位

- **方法论价值**：PTXBench 首次将“架构特定指令使用能力”从“端到端算子性能”中独立出来度量，为后续 LLM for GPU kernel 的研究提供了一个可扩展的评估与数据收集框架。其“问题收集—知识包—评估解耦”的三段式设计，使得该基准容易移植到新算子、新 GPU 架构与新模型。
- **数据与训练价值**：论文提出的 `Fixit` 数据构造管道（失败采集 → 教师修复 → 推理解释 → 学生模仿）不依赖人工标注，具备规模化潜力；该管道也适用于其他“需要精确底层 API 调用”的代码生成任务（如 CUDA Graph、NPU 自定义算子）。
- **实践启示**：对使用 LLM 做 GPU 内核优化的工程师而言，论文提示：应当把架构手册片段与 verified PTX 指令包装函数放入上下文，并建议在 harness 中同时做 SASS 静态扫描与 NCU 动态 profiling，避免误判模型真实能力。它也有力地说明“生成速度快于库”并不等于“比库更有用”，除非在相同 workload 与架构约束下做苹果对苹果的比较。

---

## 总体评价

论文选题精准命中当前 LLM 驱动系统优化的痛点：现有基准无法回答“模型是否真的理解并使用了硬件特定指令”。通过构造受控知识包、双层面指令检测和分离式指标，PTXBench 给出了有说服力的证据——当前主流 LLM（包括编码能力较强的闭源模型）在以架构特定 PTX 直接编程方面仍明显不足；也通过 Qwen3.6-27B 的 LoRA 适配实验，展示了后训练数据配方的可行性。

从研究严谨性来看，最为突出的是其指标设计：**正确率、目标指令执行率与加速比的三维解耦**，以及 **SASS 静态检查 + NCU 动态计数**的双层验证。这使得“模型看似在调用 PTX”与“模型实际让 PTX 在运行中起作用”两种情形可以明确区分。实验消融的组织也足够细致，7 组 SFT 配方对比在资源允许范围内尽量回答了“什么数据、什么反馈形式、什么教师能带来最大收益”的问题。

然而，论文在训练/推理成本透明度、评测方差、系统噪声处理上的披露略显不足；主负载的算子覆盖面较窄；所有权重更新实验局限于单一模型尺度，可能限制结论的外推强度。此外，其“参考库加速比”的基线选取（cuBLAS/cuDNN/FlashInfer 的默认 API 调用，而非手调最优 kernel）可能低估了前沿库在特定形状下的理论峰值表现，使“超过 1.0×”的门槛偏容易达成。

总体而言，该论文在问题定义、评估协议、数据管道与实验方法论上均有实质贡献，堪称“架构特定代码生成能力评测”领域的一个基础性工作；其遗憾在于问题复杂度过高，使得最终呈现的实验覆盖度尚未完全支撑其雄心勃勃的框架——但这并不削弱其作为后续研究起点的重要性。
