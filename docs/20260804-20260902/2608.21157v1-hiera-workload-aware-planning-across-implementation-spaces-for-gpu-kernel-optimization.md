## 摘要
高性能GPU内核支撑着现代深度学习和科学计算。随着工作负载日益多样化以及GPU硬件快速发展，开发自动化GPU内核生成与优化的高效方法变得越来越重要。现有的基于LLM的方法通常在一个固定的实现空间内进行优化，限制了优化灵活性或搜索效率。我们提出了HIERA，一种用于GPU内核优化的分层搜索空间规划框架。HIERA构建契约增强的任务规格，在PyTorch算子、CUDA库和自定义CUDA内核之间选择适当的实现空间，并利用性能分析反馈和专家知识指导结构化的迭代优化。在KernelBench上跨多个不同工作负载级别和基础LLM的实验表明，与现有免训练方法相比，HIERA在整体实现有效性、样本效率和优化性能方面表现更强，同时无需额外模型训练即可与基于训练的CUDA-L1保持竞争力。一个针对科学计算中专用模板算子的案例研究进一步实现了较cuDNN 1.53倍的加速，展示了该通用框架超越标准机器学习工作负载的潜力。

## Abstract
High-performance GPU kernels underpin modern deep learning and scientific computing. As workloads become increasingly diverse and GPU hardware evolves rapidly, developing efficient methods for automated GPU kernel generation and optimization has become increasingly important. Existing LLM-based methods typically optimize within a fixed implementation space, limiting either optimization flexibility or search efficiency. We propose \textsc{HIERA}, a hierarchical search-space planning framework for GPU kernel optimization. \textsc{HIERA} constructs contract-augmented task specifications, selects an appropriate implementation space across PyTorch operators, CUDA libraries, and custom CUDA kernels, and uses profiling feedback and expert knowledge to guide structured iterative refinement. Experiments on KernelBench across multiple various workload levels and base LLMs show that \textsc{HIERA} delivers stronger overall implementation validity, sample efficiency, and optimization performance than existing training-free methods, while remaining competitive with the training-based CUDA-L1 without additional model training. A case study on a specialized stencil operator from scientific computing further achieves a \(1.53\times\) speedup over cuDNN, demonstrating the potentiality of the general framework beyond standard machine-learning workloads.

## 1. 核心问题与研究意义

- **背景**：GPU 高性能内核是现代深度学习与科学计算的基础。尽管 cuBLAS、cuDNN、PyTorch 算子等厂商库与框架原语提供了高度优化的常见计算模式实现，但硬件快速演进使得优化实现难以跨架构维护与重调，且固定库原语无法覆盖日益多样化的专用工作负载（如复杂科学计算算子）。
- **核心问题**：现有基于 LLM 的 GPU 内核自动生成与优化方法（如 KernelBench-Caesar、CUDAForge 等）通常**在预定义、固定的实现空间**内进行搜索。若固定在高层次（PyTorch 算子/库），会错失需要自定义融合、形状特化和直接 GPU 控制才能获得的优化机会；若固定在低层次（纯自定义 CUDA），则模型需在庞大且弱结构化的低层决策空间中导航，在有限候选预算下大量资源会被编译失败、正确性错误或低收益实现消耗。
- **关键洞察**：执行与 profiling 反馈只能在所选实现空间内指导细化，**无法判断该实现空间本身是否适合当前工作负载**。因此应将"实现空间选择"本身显式纳入优化过程，作为一个工作负载感知的规划问题。
- **总体含义**：HIERA 将实现粒度作为显式优化决策，实现"先选对空间、再在空间内结构化细化"的粗到细优化范式，填补了既有无训练 LLM 方法在跨粒度实现空间规划上的空白。

## 2. 方法论

### 2.1 问题形式化

给定任务 τ、参考实现 fτ、目标硬件 H 和搜索预算 B，优化目标为在预算内找到最快有效实现：

- 加速比定义：s(x; τ, H) = t(fτ; H) / t(x; τ, H)，其中 t(·) 为执行延迟；
- 优化目标：x* = arg max_{x∈CB(τ)} s(x; τ, H)，约束 Valid(x; τ) = 1（编译通过且满足接口与语义要求）。

### 2.2 契约增强任务规格（Contract-Augmented Task Specification）

为了避免模型重复生成非优化目标的样板代码，HIERA 将每个 KernelBench 任务转换为"契约增强"规格：

- **固定文件**：扩展包装器（`torch_demo.py`）、C++ 绑定源码（`cpp_source.cpp`）、正确性参考（`groundtruth.py`）保持不变；Level 2/3 额外提供参数语义文件（`params_semantics.json`），描述参数角色、约束与依赖。
- **模型只生成** `cuda_source.cu` 候选实现，并与固定工件组装、经 PyTorch 扩展入口编译。
- 该设计将候选生成聚焦于性能关键的实现选择，减少代码生成与评估中的歧义。

### 2.3 跨粒度搜索空间规划（Cross-Granularity Search-Space Planning）

- 搜索空间决策代理（SSDA）在每一步从三个**嵌套且权限递增**的实现空间中选择：
  1. **Pure CUDA**：仅允许自定义 CUDA 内核；
  2. **CUDA Libraries**：额外允许 cuBLAS 等优化库；
  3. **CUDA Libraries + PyTorch 算子**：进一步允许高层 PyTorch 算子。
- 依据工作负载特征动态选择空间：复合/模型级负载避免不必要的低层重建，简单算子级负载则保留细粒度 CUDA 控制以获得更优性能。

### 2.4 领域引导的优化方向剪枝

在选定空间内，SSDA 基于经验瓶颈归纳出 5 个可操作优化方向集合 D = {C, P, M, R, T}：

- **C**：控制流与边界特化（对应发散/冗余执行）；
- **P**：线程与 warp 级并行（对应并行度不足）；
- **M**：内存事务效率（对应全局内存访问效率低）；
- **R**：数据复用与搬运流水线（对应片上复用受限/搬运重叠不足）；
- **T**：Tensor Core 与指令流水线利用（对应计算指令未充分利用）。

SSDA 根据任务规格、所选实现空间、当前候选、profiling 反馈 Ft、专家知识 E 和固定评分准则 R 对各方向打分：

- s_t = SSDA(τ, g_t, x_t, F_t, E; R) = {s_d_t}_{d∈D}；
- 主方向选取：d*_t = arg max_{d∈D} s_d_t。

### 2.5 策略生成与候选迭代

- **策略规划代理（SPA）**：将选定方向转化为可执行的结构化策略 πt = SPA(τ, g_t, x_t, F_t, d*_t, E)，给出具体变换步骤与实现约束；
- **优化代理（OA）**：应用策略生成下一组候选内核：X_{t+1} = OA(τ, g_t, x_t, F_t, π_t)；
- **反馈驱动评估**：候选与固定模板组装后经编译检查与正确性验证，有效候选在目标 GPU 上测延迟并用 NVIDIA Nsight Compute（NCU）剖析；记录源码、编译/正确性结果、延迟、profiling、所选空间与方向，最强候选作为下一轮父代。

## 3. 实验设计

### 3.1 基准与数据集

- **KernelBench 前三层**，共 250 个 PyTorch 工作负载：Level 1（100 个算子级任务）、Level 2（100 个融合算子任务）、Level 3（50 个模型级负载）。
- **科学计算案例**：2D box stencil，半径 R=3（7×7、49 个模板点），输入 10240×10240，重复 10240 次，采用 FP64 计算；以 cuDNN `cudnnConvolutionForward`（单通道 7×7 零填充互相关）作为稠密参考。

### 3.2 对比方法与变体

- **主对比基线**：KernelBench-Caesar（官方迭代工作流）、CUDAForge（Coder–Judge 反馈细化框架）、CUDA-L1（基于对比强化学习的训练式方法）。
- **基础 LLM**：DeepSeek-V3.2、Qwen3.6-Plus、Gemini-3.6-Flash（CUDA-L1 不随基础模型变化）。
- **实现空间对比变体**：在随机抽样的 90 个任务（每层 30 个）上比较 Pure CUDA、CUDA Libraries、CUDA Libraries + PyTorch 与动态选择的 HIERA。
- **消融变体**：HIERA w/o Contract（去掉契约增强规格，需生成全部支撑文件）、HIERA w/o Planning（去掉分层规划代理，使用固定优化提示直接细化）。

### 3.3 评估协议与指标

- **主对比协议**：三轮细化、每轮 6 个候选，总预算 B=18；采样温度 0.3；FP32 评估，3 次预热 + 100 次测量取最快有效实现。
- **有限预算评估**：报告 B ∈ {1, 6, 12, 18} 的累计结果（同一生成轨迹中提取）。
- **指标**：fast 0（至少一个有效实现的任务比例）、fast 1（最优有效实现超过参考的任务比例）、fast 2（最优有效实现 >2× 加速的任务比例）。
- **硬件环境**：NVIDIA A100-PCIE-40GB、Intel Xeon Gold 6430、Ubuntu 20.04.6、CUDA 12.8、PyTorch 2.7.1+cu126、cuDNN 9.5.1；每个优化任务分配单张 GPU。

## 6. 主要结论与发现

- **样本效率与优化性能领先**：B=1 时 HIERA 达 71.6% fast 0 与 32.4% fast 1，较 KernelBench 高 30.8/22.4 个百分点、较 CUDAForge 高 52.4/13.6 个百分点；B=18 时达 92.4% fast 0 与 60.4% fast 1，全面超越两个无训练基线；fast 2 在小预算下也领先。
- **跨模型泛化性好**：在与 LLM 条件化基线的 27 组对比中取得 22 组最佳或并列最佳；fast 1 在所有层级上均排名第一，说明 HIERA 能可靠地将"正确实现"转化为"实际加速"。
- **可与训练式方法竞争**：在 Level 1/2 的平均指标上，无需 RL 训练的 HIERA 超过训练式 CUDA-L1。
- **自适应空间优于任何固定空间**：Pure CUDA 潜力最大（最高 9.32×）但均值仅 1.00×、中位数 0.62×、方差 1.79；引入库与 PyTorch 算子可降低方差但牺牲峰值；HIERA 动态选择实现空间达到最高均值 1.42×、中位数 1.15×，方差较 Pure CUDA 降低 23.4%。
- **消融结论明确**：去除契约增强使复杂负载（Level 2/3）fast 0 分别下降 73/60 个百分点；去除分层规划主要损害加速率（Level 2 的 fast 1/fast 2 从 62/20% 暴跌至 6/6%），说明二者功能互补。
- **科学计算可行性**：stencil 案例运行时从首轮 13.71 ms 降至第 5 轮的 4.71 ms，较 cuDNN 的 7.23 ms 实现 1.53× 加速，验证了框架在标准 ML 负载之外的潜力。

## 7. 优点

- **问题视角新颖**：将"实现空间选择"本身形式化为工作负载感知的规划问题，突破了现有方法在固定空间内优化的局限，概念清晰且具有推广价值。
- **契约增强设计务实**：固定非关键样板

代码，只让模型生成性能关键的 CUDA 源码，既规避了 LLM 在冗长外围代码上的低效生成与编译失败，又使候选间的差异集中于优化相关的实现决策，提升了评估信号的信噪比。这种"契约增强"思想对未来工具链设计有直接借鉴意义。

## 8. 局限性

1. **Profiling 开销与预算未透明化**：尽管 HIERA 在候选数上样本效率高，但每次有效候选都需实测延迟并做 NCU 剖析，而论文未报告剖析时间占总预算的比例。在真实场景中，profiling 成本可能远超 LLM 推理成本，成为实际部署的隐性瓶颈。对比基线（如 KernelBench-Caesar）是否也承担相同 profiling 开销未明确说明，对比公平性存在潜在质疑。
2. **外部条件敏感性强**：框架严重依赖 PyTorch 扩展编译的固定包装器与 cpp_source 接口。若目标负载无法用 PyTorch 扩展封装（如独立可执行文件或自定义运行时），或参考实现不满足 KernelBench 的接口约定，HIERA 的契约增强规格便难以复用，通用性受限。
3. **实现空间离散且粒度选择有限**：HIERA 仅提供 Pure CUDA、CUDA Libraries 与 CUDA Libraries + PyTorch 三个固定嵌套空间。更多样的中间粒度（如仅用特定库函数、混合不同语言的算子间融合）未纳入选项，可能在某些负载上无法达到最优。此外"嵌套且权限递增"的设计隐含假设高层空间总能模拟低层空间的行为，但在数值语义（如 FP64 与 TF32 间的精度差异）上不一定成立。
4. **优化方向先验存在领域偏见**：SSDA 的 5 个优化方向（C/P/M/R/T）源于 KernelBench 类 GPU 内核的常见瓶颈归纳。对科学计算、图计算、稀疏线性代数等领域，瓶颈可能不在这些维度中，或需要更细粒度的子方向区分。论文未验证方向集合在多领域上的完备性。
5. **正确性验证依赖固定参考**：框架的 Valid(x; τ) 判断依赖于 KernelBench 提供的 groundtruth 参考实现。若参考实现本身有数值不稳定、精度饱和或未覆盖的边界情况（如极端形状、NaN/Inf 输入），验证可能产生假阳性或假阴性，进而污染优化轨迹。
6. **科学计算案例证据单薄**：2D stencil 案例仅在一个半径与输入规模上、用单一姿态（cuDNN 卷积对比）验证，不足以证明框架在更广科学计算负载（如稀疏三角求解、FFT、粒子模拟）上的通用性；且该案例的 FP64 + 5×10 候选协议与主实验的 FP32 + 3×6 协议不一致，削弱了跨协议结论的可比性。
7. **未提供失败模式归因**：报告 fast 0 在 Level 3、某些基础模型与小预算下仍不理想，但未深入分析失败究竟源于编译问题、正确性 bug、方向误判还是模型能力不足，难以指导后续针对性改进。

## 9. 启示与未来工作

- **规划先于搜索**：本工作最核心的启示是在自动内核优化中将"在哪搜索"置于"如何搜索"之前。任何固定的候选生成协议都隐含了对最优解位置的假设，而动态、工作负载感知的空间规划能显著提升样本效率与性能上限。这一思想可推广到算子自动调度、编译优化序列选择（如 LLVM pass ordering）等领域。
- **Profiling 成本最小化**：既然实测与剖析是主要的隐性开销，未来可探索代价模型（cost model）或回归预测器先粗略过滤候选，仅在预测的前 k 个候选中做真实 profiling；或对相似形态的负载做 profiling 迁移学习。
- **跨领域方向扩充与自动化发现**：建议将优化方向集合扩展为可扩展本体，或让 SSDA 基于 profiling 数据自行归纳瓶颈（如通过聚类 NCU 指标），增强框架对不同领域负载的适应能力。
- **更细粒度、更具表达力的空间谱系**：未来可引入连续的"空间混合"（如每轮在库调用与自定义内核间按比例分配候选）、模板化算子库，以及允许对同一负载的不同数据通路（如 cutlass 的 tile 配置）进行空间内再规划，形成真正的分层嵌套搜索。
- **可复现性与基准一致性**：建议公开完整的流程日志（包括每轮的编译失败原因、profiling 指标与预算分配），并统一案例研究的评估协议，以便社区复现与公平对比。
- **训练式规划器的潜力**：HIERA 免训练即可达与 CUDA-L1 竞争的结果，想象空间在于利用这些搜索轨迹作为监督信号，训练一个小型规划器来替代 LLM 驱动的 SSDA/SPA 推理，从而降低单次优化的推理延迟与 token 成本，并隐式编码任务-空间-策略的映射经验。

## 10. 总体综合评价

HIERA 是一篇问题导向清晰、方案设计完整、实证支撑扎实的自动 GPU 内核优化论文。其最大的理论贡献在于把"实现空间选择"显式建模为规划决策，并通过契约增强、域引导剪枝与多代理策略分解，将 LLM 在超大类搜索空间中的低效探索转化为"粗粒度定空间 → 细粒度定策略"的结构化搜索。实验体系覆盖了广泛的主对比、有限预算敏感性、变体对比与消融分析，证据链较为完整，结论与设计动机自洽。虽然在 profiling 成本量化、跨领域通用性与案例研究丰富度上有提升空间，但作为将规划式 LLM 智能引入内核优化的早期尝试，其思想深度、工程完成度与实证充分性均达到较高水准，对该方向后续研究具有显著启发价值。
