## 摘要
多右端项三角求解（TRSM）是一种基本的BLAS Level-3运算，是LU/Cholesky分解、稀疏直接求解器和矩阵求逆的基础。本文研究的左侧下三角情形中，高效的GPU实现仍具挑战性，因为前向代入引入了严格的行依赖，而共享内存对于双复数等宽数据类型而言过于稀缺，无法同时容纳两个操作数矩阵。本文提出HSMA-TRSM，一种面向NVIDIA A100、NVIDIA H800和Hygon DCU Z100加速器上左侧下三角TRSM的层次化共享内存感知优化框架。对于小规模情形（m,n≤64），我们通过循环展开和指令重排设计了流水线化的计算-内存重叠机制，并提出了双线程组七级流水线策略以解决双复数类型的共享内存约束。对于大规模问题，我们引入了一种对角块解耦优化，其对角块求逆的共享内存占用为O(IB)，从而能够根据矩阵规模与硬件特性进行自适应块大小选择。基于离线剖析与在线查找的编译期配置选择框架，以零运行时开销为每个平台选择最优块大小。在NVIDIA A100、H800和Hygon DCU Z100上的评估显示，HSMA-TRSM相比cuBLAS实现了最高2.05倍的加速，相比rocBLAS实现了最高2.06倍的加速。在共享内存受限的双复数小规模情形以及自适应分块改善以GEMM为主导的更新的大型实数类型情形中，加速效果最为显著，而在某些情形下，成熟的厂商内核留下的优化空间较小。

## Abstract
Triangular Solve with Multiple Right-hand Sides (TRSM) is a fundamental BLAS Level-3 operation that underpins LU/Cholesky decomposition, sparse direct solvers, and matrix inversion. In the left-side lower-triangular case studied in this paper, efficient GPU implementation remains challenging because forward substitution introduces strict row-wise dependencies, and shared memory is too scarce to hold both operand matrices for wide data types such as double complex. This paper presents HSMA-TRSM, a hierarchical shared memory-aware optimization framework for left-side lower-triangular TRSM on NVIDIA A100, NVIDIA H800, and Hygon DCU Z100 accelerators. For the small-scale regime (m,n<=64), we design a pipelined compute-memory overlap mechanism through loop unrolling and instruction reordering, and propose a dual thread-group seven-stage pipeline strategy to address shared memory constraints for double complex types. For large-scale problems, we introduce a diagonal block decoupling optimization with an O(IB)shared-memory footprint for diagonal block inversion, enabling adaptive block size selection based on matrix scale and hardware characteristics. A compile-time configuration selection framework based on offline profiling and online lookup selects the optimal block size per platform with zero runtime overhead. Evaluated on NVIDIA A100, H800, and Hygon DCU Z100, HSMA-TRSM achieves peak speedups of 2.05xover cuBLAS and 2.06xover rocBLAS. The gains are strongest in shared-memory-constrained double-complex small cases and in large real-type cases where adaptive blocking improves GEMM-dominated updates, while mature vendor kernels leave less optimization headroom in some regimes.

## 1. 论文的核心问题与整体含义

论文聚焦于 GPU 平台上的 BLAS Level-3 运算 TRSM（Triangular Solve with Multiple Right-hand Sides），具体处理左侧下三角情形（`op(A)X = αB`）。

- **核心难点**：
  - TRSM 依靠前向代入求解，存在严格的行间串行依赖，难以充分并行；
  - 小规模（`m,n ≤ 64`）时，矩阵需放入共享内存，但 A100/H800 每线程块共享内存预算仅为 48KB，DCU Z100 为 64KB；对于双复数（double complex）等宽数据类型，单个 64×64 矩阵就要 64KB，无法同时缓存 A 与 B；
  - 大规模情形下，厂商库（如 rocBLAS）固定使用块大小 128，无法根据矩阵规模与硬件特性自适应调整；传统对角块求逆的共享内存开销高达 O(IB²)，严重限制可用块大小；
  - 已有优化往往面向单一架构，跨平台性能可移植性差。

- **整体意义**：TRSM 是 LU/Cholesky 分解、稀疏直接求解器、矩阵求逆等数值计算的核心构件，其 GPU 性能直接影响上层应用。论文提出的 HSMA-TRSM 框架，通过层次化、共享内存感知的优化，在三种不同 GPU 平台上实现了对 cuBLAS/rocBLAS 最高约 2.05×/2.06× 的加速。

## 2. 方法论

论文提出 **HSMA-TRSM（Hierarchical Shared Memory-Aware TRSM）**，核心是以问题规模为分层依据，自适应选择计算策略。

### 整体框架划分
- 以 `m,n ≤ 64` 作为小规模与大规模的分界；
- **小规模**：采用共享内存直接求解（direct solving），此时计算强度约 O(1)，是访存受限问题，优化重点是数据复用和访存-计算重叠；
- **大规模**：采用分块算法，将主要计算转化为 GEMM，此时是计算受限问题，优化重点是块大小选择和 GEMM 效率。

### 小规模优化
1. **共享内存直接求解**：
   - A 存入共享内存，B 的不同列分给不同线程、保存在寄存器；
   - 按行进行前向代入求解：
     `x_{i,j} = (1/a_{ii}) * (αb_{i,j} - Σ_{k=1}^{i-1} a_{ik}x_{k,j})`
   - 不同列之间相互独立，可并行处理。

2. **计算-访存重叠**：
   - 利用 GPU `ld.shared` 等指令异步执行的特性，将「求解第 i 行」与「加载第 i+1 行」重叠；
   - 通过**完全循环展开 + 指令重排**，将未来行的加载提前、已完成行的写回延后，形成更深的 load-compute-store 流水线，消除行间 pipeline bubble。

3. **双线程组七级流水线（针对 Double Complex）**：
   - 64×64 double complex 矩阵恰好占满 64KB，无法同时缓存 A 与 B，因此将 64KB 共享内存划分为 4 个 16KB 子区；
   - A 按 2×2 分块，B 按 4×1 分块；
   - 128 个线程分为两个线程组，一个负责访存、一个负责计算，构成七级流水线，在共享内存受限条件下仍能实现计算与访存的完全重叠。

### 大规模优化
采用两阶段分块算法：
- **Phase 1：并行对角块求逆**——将三角矩阵 A 沿对角线分为若干 `N_B × N_B` 对角块，各对角块之间相互独立，可并行求逆；
- **Phase 2：串行 GEMM 更新与求解**——对第 r 个对角块先执行 `B_r ← B_r - A_{r,[0:r]} × X_{[0:r]}` 的 GEMM 更新，再使用逆矩阵完成求解。

#### 对角块解耦优化（关键创新）
- 传统融合算子方式将「对角块求逆、回代、小规模 GEMM」放入同一 kernel，需要 `4 × I_B² × sizeof(datatype)` 共享内存（例如 `I_B=64`、double complex 时高达 256KB），严重限制块大小；
- 论文将其改为**纯回代（back-substitution）式对角块求逆**，把加载粒度细化到**列级**，共享内存中只保留当前列与已求解列，使共享内存占用从 **O(I_B²) 降为 O(I_B)**；
- 为隐藏列级加载延迟，引入 **double buffering**：两块 buffer 交替用于「计算当前逆矩阵列」和「预取下一列」，使访存与计算重叠，最终共享内存占用约 `4 × I_B × sizeof(datatype)`，仍为 O(I_B)。

#### 自适应分块算法
- 采用「离线 profiling + 在线查找」两阶段策略；
- 预构建阶段遍历候选块大小（如 32、64、128、256 等），在目标硬件上测量不同规模与数据类型下的性能，记录最优块大小，生成「规模 × 数据类型 → 最优块大小」映射表；
- 运行阶段仅通过哈希表查找，采用 nearest-match 策略处理未覆盖的矩阵规模；
- 相比 rocBLAS 固定 128 的块大小，可以按矩阵规模选择更合适的配置。

## 6. 论文的主要结论与发现

1. **整体加速效果**：HSMA-TRSM 在 A100/H800/DCU Z100 上相对 cuBLAS 达到最高 **2.05×** 加速，相对 rocBLAS 达到最高 **2.06×** 加速。
2. **小规模最显著收益集中在共享内存稀缺场景**：
   - double complex 在 H800 上峰值加速 2.05×，在 DCU 上 1.96×；
   - float complex 在 DCU `m=64` 时相比 rocBLAS 提升 86.3%；
   - 而 float/double 通常仅提升 1.1×–1.3×。
3. **大规模收益集中在 GEMM 主导的实数场景**：
   - DCU 上 float 峰值达 6010 GFLOPS，double 为 3654 GFLOPS；`m=16384` 时加速分别为 1.63× 和 2.06×；
   - A100 上 double complex 高层性能为 17111 GFLOPS，优于 cuBLAS 与 MAGMA；
   - 对角块解耦将共享内存开销从 O(I_B²) 降到 O(I_B)，使更大的块大小成为可能，帮助大型问题更早、更强地切换到高效 GEMM 路径。
4. **厂商库的成熟场景优化空间有限**：例如 H800 的 double complex 与 cuBLAS 基本持平，说明在某些 regime 中厂商内核已经很强，不能据此判定所提方法无效。
5. **可移植性**：编译期离线配置选择 + 在线查找，实现了跨平台零运行时开销的调优，说明该框架具备较好的性能可移植性。

## 7. 优点

- **问题切分清晰**：以 64 为界区分小规模直接求解与大规模分块求解，并用 Roofline 模型解释访存受限/计算受限的优化重点，逻辑自洽。
- **解决真实硬件痛点**：明确处理了共享内存不足以容纳双复数矩阵这一实际瓶颈，提出的双线程组七级流水线设计有一定独创性。
- **关键复杂度优化**：对角块求逆从 O(I_B²) 共享内存开销降为 O(I_B)，是一个显著的算法/工程双层收益，直接扩大了可选的阻塞配置空间。
- **零运行时开销调优**：离线 profiling + 在线查表的编译期配置选择框架，避免运行时自动调优的额外成本，兼顾性能与可移植性。
- **实验基线较强**：与 cuBLAS、rocBLAS、MAGMA 等一流实现对比，并做了数值误差验证，结论具有一定说服力。
- **跨平台验证充分的三架构设定**：覆盖 NVIDIA A100 / H800 与国产 Hygon DCU，比只在单一厂商 GPU 上评估的同类工作更有跨平台价值。

## 8. 不足与局限

- **问题形式覆盖有限**：只研究左侧下三角、`op(A)` 为非转置的 TRSM；代码/算法是否容易推广到右侧、上三角、转置/共轭转置等情形并未展开。
- **规模边界依赖于启发式选择**：`64` 作为小/大规模分界来自 profiling 观察与经验分析，论文没有系统性地展示该边界在不同架构/数据类型下的最优性。
- **块大小映射表并非连续精确最优**：运行时最近邻匹配减少了调优开销，但无法保证未测试规模下的配置仍是最优；该误差的影响未被充分量化。
- **性能差距解释偏定性**：部分场景与厂商库差距较小（如 H800 double complex），论文将其解释为厂商内核成熟，但没有提供更细粒度的内核级剖析（如 stall、occupancy、shared memory bank conflict 等）来支撑这一结论。
- **实验统计细节不足**：只报告 9 次运行的平均值，没有标准差、分布或置信区间，实验结果可能受系统噪声影响。
- **缺乏与更多第三方库的对比**：未与 KBLAS、hipBLAS、SA-TRSM 等其他优化实现做横向比较，难以全面定位该方法在更广泛的 TRSM 优化研究中的位置。
- **算力成本信息披露不足**：没有注明各平台使用的 GPU 数量、离线 profiling 所需的总机时等资源信息，可复现性和成本评估受限。
- **尚未覆盖多 GPU / 分布式场景**：论文全部实验基于单 GPU 单 kernel，无法直接推断到多卡扩展场景；作者也在 Future Work 中承认需要继续研究 batched TRSM、稀疏与混合精度等方向。
