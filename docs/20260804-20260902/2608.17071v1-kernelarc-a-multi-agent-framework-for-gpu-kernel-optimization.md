## 摘要
我们提出了KernelArc，一个在异构工作负载中自主优化GPU内核的多智能体框架。策略专用智能体并行运行，并通过仅结论共享内存、确定性基准守卫以及带平台期触发草稿的只读跨智能体状态进行协调。我们使用类别代表性的SOL-ExecBench工作负载，在NVIDIA H100和B200 GPU上评估了KernelArc。所得实现涵盖自定义BF16 GEMM、静态cuBLASLt Expert-API配置表、融合的混合专家反向传播、形状门控解码器层融合、原生NVFP4分组查询注意力以及分页预填充注意力。在2026年7月30日记录的公共SOL-ExecBench排行榜快照中，这些提交在代表性的L1、L2、量化和FlashInfer任务上排名第一。这些轨迹支持了论文的核心动机：在固定候选预算内，共享的多智能体搜索能拓宽探索范围并达到更强的现有方案，而各个协调特性的价值则取决于内核和优化阶段。

## Abstract
We present KernelArc, a multi-agent framework for autonomous GPU kernel optimization across heterogeneous workloads. Strategy-specialized agents run in parallel and coordinate through conclusions-only shared memory, a deterministic benchmark guard, and read-only cross-agent state with plateau-triggered drafting. We evaluate \kernelarc{} on NVIDIA H100 and B200 GPUs using category-representative SOL-ExecBench workloads. The resulting implementations span custom BF16 GEMM, static cuBLASLt Expert-API configuration tables, fused mixture-of-experts backward, shape-gated decoder-layer fusion, native NVFP4 grouped-query attention, and paged prefill attention. At the public SOL-ExecBench leaderboard snapshot recorded on July~30, 2026, these submissions ranked first on representative L1, L2, Quantization, and FlashInfer tasks. The trajectories support the paper's central motivation: shared multi-agent search can broaden exploration and reach stronger incumbents within a fixed candidate budget, while the value of individual coordination features depends on the kernel and optimization stage.

## 一、核心问题与整体含义（论文动机与研究背景）

- **问题背景**：从现代 GPU（如 Hopper、Blackwell）上获得极致性能日益困难。硬件提供了 WGMMA、TMA、异步屏障、NVFP4 等高吞吐原语，但真正提速需要将它们与数据布局、访存层次、寄存器压力、同步与启动开销协调起来，传统人工性能工程成本极高。
- **自动化需求**：LLM 智能体被看作可编程的替代方案，可以完成 profile、提出结构变换、编辑 CUDA/PTX/DSL 代码、选库与 autotune、选择精度、做正确性测试等。已有单智能体系统（如 AutoKernel）证明该循环可行，但其成功依赖人工设计的 playbook 和充足的顺序预算。
- **单智能体瓶颈**：单智能体一次只能沿一条局部历史推进一个 incumbent，在固定候选预算下覆盖的算法族较少，且容易在局部平台期过拟合某个设计，把“搜索轨迹的平台”误当作“硬件性能上限”。
- **论文核心主张**：KernelArc 提出**共享式多智能体搜索**，在固定候选预算内拓宽探索范围、达到更强的 incumbent。论文同时指出：不同协调特性（共享内存、leaderboard 访问、plateau 触发、retention 约束等）的价值取决于具体内核与搜索阶段，不应把某一机制孤立地视为普遍有效。

## 二、方法论（核心思想、关键技术细节与算法流程）

### 1. 问题形式化
- 目标为寻找最优实现：
  - \( k^* = \arg\max_{k \in K} S(k; W, H)\)，满足对所有 workload \(w \in W\) 有 \(C(k,w)=1\)（正确性约束）。
  - \(S\) 为性能评分（如所有 shape 下几何平均延迟的倒数）。
  - 搜索空间 \(K\) 不仅包括固定模板参数，也包括结构化源码变化（替换算子为库调用、更换 DSL、融合 epilogue、加入 warp specialization 等）。

### 2. 架构组成（图 1）

- **策略专用智能体（Strategy-specialized agents）**：
  - 提供 8 个策略技能：library、memory、compute、fusion、precision、reduction、scheduling、custom-b200。
  - 每个技能是带 YAML 元信息的轻量种子文档，作用是提供“优化的观察透镜”，而非规定最终方案。
  - 另有 meta-skills：playbook-index（策略适用性）、memory（共享经验）、sol-benchmark（基准协议）。

- **仅结论共享内存（Conclusions-only shared memory）**：
  - 只有两类结论可写：Wins（成功优化，含加速比、shape 和 WHY 字段，默认每类内核保留 16 条，按速度降序）、Traps（失败死路，含 WHY 字段，默认 FIFO 保留 16 条）。
  - 不共享迭代计数、心跳、进度日志；记录带字段长度上限（strategy 160 字符、reflect 1200 字符），降低上下文污染。
  - retention horizon 是配置旋钮，论文不做“有界优于全历史”的断言。

- **确定性外部守卫（Deterministic benchmark guard）**：
  - Cascade gate：廉价预检（语法、入口、无 ctypes/subprocess/cpp_extension）。
  - Benchmark：在 GPU 锁下执行 SOL-ExecBench bridge，测量聚合延迟。
  - 返回 REJECT / KEEP / ACCEPT / REVERT：
    - KEEP：仅当通过所有 workload 且超过 incumbent 一定分数裕度；
    - ACCEPT：正确但非提升的近最优 lateral candidate，可留作探索工作点；
    - REVERT：回滚到上一最佳；
    - REJECT：廉价预检失败，不计入 plateau 计数。
  - STOP 条件包括平台期、目标达成、时间预算耗尽、候选数上限。

- **算法流程（Algorithm 1 Agent Optimization Loop）**：
  - 初始化：bootstrap 解目录、测量基准线。
  - 迭代中：recall wins/traps；可选读内部 leaderboard 及 sibling archive。
  - 若 plateau counter \(r \ge r_{\text{draft}}\) 则触发 drafting，要求切换 DSL、算法或数据布局，否则形成本地策略假设。
  - 提交候选给 guard；按 KEEP/ACCEPT/REVERT/REJECT 分别更新 \(r\)、记录 win/trap 或保持 working code。
  - 直到 guard STOP 或策略/轮次预算耗尽。

- **Launcher Loop（Algorithm 2）**：
  - 按策略组生成多个 agent，每个 agent 独享 solution dir，共享同一内存路径。
  - 可选 campaign leaderboard publisher 定期扫描 agent 目录并发布只读最优；agent 异常退出时由 launcher 重新拉起，guard archive 保留 best。
  - div：per-agent best 保持在 guard archives，campaign leaderboard 仅用于只读跨 agent 状态。

### 3. 关键设计理念
- “LLM 负责生成式推理，确定性代码负责评估与协调”：避免 agent 自我判定其编辑是否更优。
- 共享记忆只传播“经过验证的结论”，不传递完整历史，降低上下文污染并提升可复现性。
- Explicit plateau escape：持续非改进到达阈值后，智能体被要求换算法、换 DSL、换布局，而非继续局部微调。

## 三、实验设计（数据集、场景、benchmark、对比方法）

### 1. 评测基准
- **SOL-ExecBench**：Speed-of-Light Execution Benchmark，以 SOL 分数（越高越好，1 为硬件极限）聚合多输入 shape 上的性能。SM 时钟锁定、L2 flush、CUPTI tracing。共 235 个问题分为四类：
  - L1：单算子构件（GQA、RMSNorm、SwiGLU、RoPE 等）；
  - L2：完整融合块，复杂度约为 L1 的 3–10 倍；
  - Q：量化类，包括 FP8 blockwise / NVFP4 block-scaled；
  - FI：FlashInfer-Bench 独立推理原语。
- 论文没有做 235 个任务的 suite-wide 评估，只选择每类代表任务。

### 2. 实验场景与任务
- **Motivating GEMM study（单智能体边界研究）**：
  - 固定形状 \(4096\times4096\) BF16 GEMM，NVIDIA H100 SXM（132 SM，理论约 989 TFLOPS BF16 Tensor Core）。
  - 使用单智能体（私有无共享内存）+ 详细 Hopper 专用 playbook。
  - 比较：同一协议下 cublasGemmEx 测得的“最强 cuBLAS baseline”（742 TFLOPS）。
- **SOL-ExecBench 跨类别评估**：
  - L1-030：注意力输出投影 + residual（16 shape，B200）；用 Claude Opus 4.6。
  - L2-025：MoE expert-parallel 反向（256 expert、top-8、H=4096、I=2048、FP32、16 shape，T=2048–6144）；用 Kimi K3。
  - L2-053：decoder layer（self-attention + MLP），形状门控融合；用 Kimi K3。
  - Q-031：NVFP4 grouped-query attention；用 Kimi K3。
  - FI-014：paged prefill causal GQA（32 Q heads、4 KV heads、D=128、page size 1、30 变长 workload）；用 Kimi K3。
- **消融研究**：
  - 仅在 FI-014 上进行，因为完整端到端消融成本高。
  - 三种配置 × 5 条轨迹：Single（私有内存 + 无 leaderboard）、Multi-bounded（双 agent、共享 win/trap 内存、上限 16 条、只读 leaderboard）、Multi-unbounded（双 agent、无共享内存上限）。

  - 对比方法并非外部系统，而是 KernelArc 自身的配置消融；公共结果则对比“PyTorch reference”和“NVIDIA optimized baseline”。

## 六、主要结论与发现

1. **共享多智能体搜索优于单智能体**：在 FI-014 消融中，固定 100 候选预算下 Multi-unbounded 的几何平均 speedup 是 Single 的 2.04×，Multi-bounded 是 Single 的 1.28×；Multi-unbounded 的几何平均 latency 约 0.0085 ms，明显低于 Single 的 0.0132 ms。
2. **共享经验有实际作用**：multi-agent 轨迹能从单智能体平台期脱离（L1-030 从 Single 的 SOL 0.441 提升到 KernelArc 的 0.481）；共享 traps 阻止重复 death ends；共享 wins 重定向邻近搜索。
3. **平台期触发 drafting 有效**：当连续非改进到达阈值时强制切换算法/DSL/布局，能突破局部搜索固定点。
4. **深度与广度是互补 regime**：
   - 单智能体 + 详细 playbook + 8 小时可将固定 BF16 GEMM 从 4.6 TFLOPS 提升到 766 TFLOPS（超过同一协议下 cuBLAS 742 TFLOPS，约 77% 硬件峰值），体现“沿一条窄路径的深度”；
   - 跨 shape 多任务（如 SOL-ExecBench）更需要“广度”，此时共享多智能体价值更明显。
5. **生成成果的区间可观**：
   - L1-030：SOL 0.481（当时第一；后续快照 0.490500、第三）；
   - L2-025：SOL 0.535，16/16 shapes 快于 baseline，1.13× baseline，291× reference；
   - Q-031：SOL 0.988，16/16 shapes 快于 baseline，43.8× baseline，1327× reference；
   - FI-014：SOL 0.986，30/30 shapes 快于 baseline，143.8× baseline，61972× reference。
6. **机制价值依阶段而变**：同一个特征（记忆共享、只读 sibling inspection、plateau drafting）在早期探索、平台期逃逸、后期局部精修阶段的作用可能不同，不能把全部功劳归于单一抽象。

## 七、优点

- **问题定义清晰**：把 kernel optimization 建模为带正确性约束的测量门控搜索，与之前单智能体范式形成明确对比。
- **架构设计有启发性**：“结论-only memory” + “确定性 guard” 是在实际工程约束（正确性、benchmark 噪声、LLM 幻觉、并发写冲突）下提出的合理方案；分离“生成式推理”与“确定性评估”很有价值。
- **诚实的不确定度报告**：给出几何均值、95% 轨迹 bootstrap 区间、置换检验 p 值和单条 legacy trajectory 的敏感性分析，不回避消融的不稳定性。
- **对搜索预算的定义严谨**：以候选位置为单位，REJECT 和 crash 也计预算，提前停止的轨迹将最后最优值 carry-forward，避免虚增收益。
- **覆盖多种实现形态**：从 PTX 手写 GEMM、cuBLASLt 静态配置到 Triton/CuTe/CUTLASS 生成的 NVFP4 和分页注意力，证明框架不只优化一种算子族。
- **细节丰富且可复现性好**：附录给出了每个问题的主要算法流程（Algorithm 3–7），关键技巧包括 residual aliasing、count-sort + batched GEMM、代数梯度复用、SM100 dual-GEMM scatter-atomic、NVFP4 寄存器内量化、split-causal cuDNN 路径等，对实践者有直接参考价值。

## 八、不足与局限

- **未做 suite-wide 评估**：只覆盖 5 个代表任务，不能估计全 235 题的平均胜率；leaderboard 排名随时间变化（L1-030 已从第一降到第三），所有“排名第一”均为特定日期快照。
- **消融规模小且多因素混淆**：FI-014 只有 5 trajectory/配置；Multi-bounded vs Multi-unbounded vs Single 同时改变 agent 数量、memory scope、leaderboard access 和 retention horizon，无法分离具体机制贡献；置换检验在剔除个别轨迹后显著性下降。
- **不同任务使用不同 LLM backbone**：没有在相同 backbone 下做跨任务控制，因此跨任务能力比较可能受模型差异影响。
- **深度结论非常 shape-specific**：766 TFLOPS 只针对 4096×4096、重复调用协议和特定 cuBLAS 版本；不能证明任何通用 GEMM 内核优于 cuBLAS。
- **缺少 wall-clock / token / dollar 的统一计量**：消融用候选数做预算，但每个候选的 LLM 推理成本和 GPU benchmark 时间并不相同；论文没有给出候选-时长的等价关系。
- **平台期 drafting 与各机制的因果效果没有独立验证**：作者自己也承认无法断言“保留期限有界 vs 全历史”孰优，也无法给出 per-mechanism causal effect estimates。
- **单点验证为主**：很多精彩工程技巧（如 fp4 寄存器内量化、cuDNN SDPA split-causal）只在一个任务上有效，通用性未验证。
- **可复现性门槛高**：依赖私人 LLM API、付费 backbone、特定 B200/H100 环境和 SOL-ExecBench 私有协议；外部研究者难以低成本复现完整流程。
