## 摘要
高性能机器学习系统日益依赖GPU内核，而此类内核的可编辑源代码可能不可用、由程序生成，或因与最终机器码差距过大而无法暴露剩余优化空间。现有的LLM内核优化器与自动调优器主要面向CUDA、Triton、HIP或张量程序源码进行操作，并对照参考实现进行验证。我们研究了一种更严格的场景：优化已编译的AMDGPU代码对象，此时部署的二进制文件是唯一的行为参照。我们提出AsmEvo，一种面向AMD GPU内核的智能体级汇编优化器。给定AMDGPU代码对象K0，AsmEvo重构可重汇编的表示，通过长程智能体提出底层编辑，重建保持ABI的优化对象，并仅在与K0在相同启动条件下通过差异验证后接受候选方案。AsmEvo结合了代码对象恢复、元数据感知重建、分析引导的热点窗口编辑、正确性门控计时以及保守的就地补丁回退。我们使用AsmEvo在多种AMD GPU内核上进行了广泛实验。在MI308X上，AsmEvo提升了30个选定KernelBench内核中的29个，达到1.35倍几何平均加速和3.88倍最大加速。在MI300X生产负载上，它提升了所有评估的AITer二进制以及vLLM/SGLang Triton汇编内核，分别达到1.09倍/1.31倍和1.18倍/1.34倍的几何平均/最大加速，同时保持了功能等价性。

## Abstract
High-performance ML systems increasingly rely on GPU kernels whose editable source is unavailable, generated, or too distant from final machine code to expose remaining optimizations. Existing LLM kernel optimizers and autotuners mainly operate on CUDA, Triton, HIP, or tensor-program source and validate against reference implementations. We study a stricter setting: optimizing an already compiled AMDGPU code object, where the deployed binary is the only behavioral oracle.   We present AsmEvo, an agentic assembly-level optimizer for AMD GPU kernels. Given an AMDGPU code object K0, AsmEvo reconstructs a reassemblable representation, proposes low-level edits with a long-horizon agent, rebuilds an ABI-preserving optimized object, and accepts candidates only after differential verification against K0 under identical launches. AsmEvo combines code-object recovery, metadata-aware rebuilding, profiling-guided hot-window editing, correctness-gated timing, and conservative in-place patch fallback.   We conduct extensive experiments with AsmEvo on various AMD GPU kernels. On MI308X, AsmEvo improves 29 of 30 selected KernelBench kernels, reaching 1.35x geometric-mean and 3.88x maximum speedup. On MI300X production workloads, it improves all evaluated AITer binaries and vLLM/SGLang Triton assembly kernels, reaching 1.09x/1.31x and 1.18x/1.34x geometric-mean/maximum speedups, respectively, while preserving functional equivalence.

## 一、论文的核心问题与整体含义（研究动机和背景）

### 问题背景
- 现代ML系统越来越依赖GPU内核的性能，但最终性能不仅取决于高层调度，还取决于编译后的底层决策，包括：等待计数器放置（wait-counter placement）、指令选择、寄存器分配、内核描述符和ABI可见元数据等。
- 现有的编译器（如TVM）、张量程序自动调优器（Ansor/AutoTVM）、DSL（如Triton）、以及厂商库（如AITer、rocBLAS、Composable Kernel）虽然高效，但制造了一个"实际边界"：一旦内核被编译成AMDGPU代码对象（如HSACO），剩余的优化机会可能不再通过源码暴露出来——而许多部署场景中源码根本不存在。

### 现有方法的不足
- 现有LLM内核优化系统（如KernelBench、KernelEvolve、Kevin、CUDA Agent等）主要从高层规范生成和优化CUDA、Triton、HIP或张量程序内核，假设存在可编辑的源码制品和独立的参考实现。
- **关键差异**：对于已编译的代码对象内核，两者都不存在——原始二进制既是部署制品，也是唯一的行为参照（behavioral oracle）。

### 论文的核心研究问题
> **能否直接在汇编级别优化内核，仅用原始编译的二进制来定义可接受的行为？**

这是首次将无源码、保持ABI的GPU内核优化形式化为一个正确性门控的后编译问题：原始二进制充当差分正确性参照，每个报告的加速都必须通过外部验证。

## 二、论文提出的方法论

### 总体框架概述
AsmEvo是一个面向AMDGPU代码对象和恢复后的AMD GCN汇编的后编译优化器，包含六个关键组件：

1. **代码对象恢复（Code-Object Recovery）**
   - 从AMDGPU ELF容器中重建可编辑汇编s(K₀)
   - 恢复目标文件段、符号、注释、内核描述符、AMDGPU元数据和AMD GCN指令体
   - 重建 `.amdhsa_kernel` 声明，并重新符号化PC相对控制流，使分支在指令插入/删除/重排后保持有效
   - **单项往返门控（Round-trip gate）**：重新汇编并重链接s(K₀)，与K₀比较生成的指令体、内核描述符和元数据（仅掩蔽链接决定的字段），通过后方可进行后续编辑

2. **双层级差分参考（Two-Tier Differential Oracle）**
   - **第一层（合成推断）**：当可从描述符和元数据推断启动结构时，推断参数偏移、标量类型、指针角色、缓冲区大小和启动维度，生成确定性输入（覆盖代表性形状、步长、数据类型、边界值、随机种子），分配带金丝雀值（canaries）的守卫区域以检测越界写入
   - **第二层（真实派发捕获）**：对混合数据类型、非连续张量、块表、嵌套指针结构或应用自定义工作区布局的生产内核，拦截真实应用派发，记录kernarg缓冲区、网格和工作组维度、引用的设备内存区域及派发前内存状态。候选在原始虚拟地址回放这些捕获的内存，使嵌套指针无须重建应用级结构即可保持有效
   - 等价性判断：`eq(K′, x) ≡ cos(K′(x), O(x)) ≥ θ ∧ ‖Δx‖∞ ≤ τ ∧ ι(K′, x)`，其中浮点输出用余弦相似度和L∞容差检查，整数缓冲区/不透明状态/守卫区域用逐字节精确检查

3. **元数据感知重建（Metadata-Aware Rebuild）**
   - 重新扫描编辑后的汇编，计算VGPR/SGPR/AGPR、LDS和scratch使用量
   - 同时重算内核描述符和AMDGPU元数据中的资源字段，然后重新链接对象
   - **冻结**kernarg布局、kernarg段大小、符号接口和启动语义，保持与原始启动器兼容
   - 回退机制：仅当正常重建失败且编辑是资源中性和大小不增加时，使用保守的就地字节补丁；补丁候选仍需通过相同的接受标准

4. **性能分析与热点窗口定位（Profiling and Hot-Window Localization）**
   - 使用硬件计数器、指令采样和静态分析识别大内核中的停顿主导指令窗口
   - 总结指令组成、依赖链、内存行为、占用率约束和资源压力供搜索驱动使用
   - 局部编辑先应用于热点窗口，再拼接回完整汇编后重建和验证
   - 减少了搜索上下文并阻止无关修改，但不削弱全内核接受标准

5. **门控验证框架（Gated Verification Harness）**
   - 每个候选严格按算法1的顺序经过：汇编有效性 → 静态资源/ABI一致性 → 功能等价性 → 性能测量
   - **正确性严格先于计时**：防止"快但不正确"的候选获得正面优化信号
   - 计时使用预热 + R次事件计时启动的中位数
   - 返回值包括：`asm_invalid`、`abi_invalid`、`divergent`、`ok`（含加速比），作为结构化反馈交给搜索代理

6. **长程智能体搜索（Long-Horizon Agentic Search）**
   - **分工原则**：确定性控制器负责所有正确性关键操作——构建验证、资源检查、等价性判定、计时、提交门控、血统管理、终止条件；LLM只负责分析和提出编辑、解释结构化失败并重新规划
   - **提交门控**：`g(c) ≡ [∀x eq(c,x)] ∧ ŝ(c) ≥ max(m⋆, s_floor)`，其中m⋆ = (1 + max(ϵ, k·cv))·ŝ(K⋆)，方差感知阈值防止测量噪声推进搜索
   - **已验证血统树**：接受的候选形成树结构而非单链；每个节点记录父节点、验证加速比、修改的指令窗口、资源用量和优化原理；报告的全局最优保证no-regress不变性
   - **多起点探索**：团队模式中规划器分配正交优化方向（延迟隐藏、依赖减少、寄存器压力控制、内存访问重构、指令简化）给并行worker，从不同已验证血统节点选择起点
   - **已验证组合**：基于同一基线的多次成功编辑逐步增量应用，每步重建和验证；仅在通过所有正确性门控且优于两个父候选时才提交组合
   - **反停滞监督**：有界运行内存存储成功洞察、失败签名和重复候选哈希；检测到长时间无改进时请求重定向或回溯到早期验证节点

   - L1的多个大加速（Conv2D 3.88倍、MinGPT-NewGelu 3.82倍、RMSNorm 2.63倍、上三角矩阵乘法2.28倍）说明单个固定peephole规则不够，需要多样化策略
   - 最大L2加速（2.55倍）在融合内核中实现，验证了全内核验收单元对融合流水线的重要性
   - 生产内核收益来自局部而非结构性编辑：长延迟内存操作调度、等待计数器放置、缓存提示和buffer-load变体选择、归约转换或地址生成工作

4. **总体判断**：已部署的二进制确实保留了可恢复的低层优化空间；在有确定性门控的情况下，智能体搜索可以安全利用这些空间

## 七、优点

1. **问题定义新颖且有实际价值**：首次系统性地解决"只有编译后HSACO、无源码、无独立参考"的真实部署场景中的内核优化问题
2. **正确性先于性能的架构设计**：将正确性验证与计时严格分离，LLM无法宣布正确性或性能——这使得"快但错误"的候选无法污染搜索信号。这是对现有LLM内核优化器（广泛存在的"验证不充分导致快但错误被奖励"问题）的直接回应
3. **双层级差分验证设计务实**：合成推断适合benchmark内核，真实派发捕获适合生产级指针丰富的内核，两者互补覆盖了实际全谱
4. **端到端验证完整**：不仅报告replay-harness中的加速，还通过替换真实对象跑AITer单元测试和vLLM/SGLang框架测试来确认drop-in可用性
5. **往返保真门控**：在编辑任何内容之前先验证重建表示与原始对象逐字节匹配（掩蔽链接决定字段），保证后续编辑操作在忠实表示上进行
6. **提交门控考虑测量噪声**：方差感知阈值（cv项）防止时序抖动推进搜索，no-regress不变性保证全局最优不倒退
7. **血统树而非破坏性单链**：允许从任何已验证节点分支，有效支持多方向探索和反停滞回退
8. **结果报告诚实细致**：包括每个算子的详细结果、提交率（5.1%）、逐内核生产结果等，没有隐藏失败案例

## 八、不足与局限

### 方法本身的局限（论文自述）
1. **经验性而非形式化等价**：保证仅限于评估过的输入和启动配置；新形状需要新推断输入或新的派发捕获
2. **当前实现校准于CDNA级AMD GPU**：架构外推到其他GPU需要适配恢复和重建实现
3. **复杂应用状态依赖真实派发捕获**：某些场景无独立可用的测试harness时只能依赖应用内捕获
4. **可实现收益取决于已编译内核剩余的优化头部空间**：对高度优化的vendor二进制可能收益很小（如部分AITer内核仅1.0倍出头）

### 实验层面的局限
1. **缺少消融研究**：热点定位、多起点策略、血统树、反停滞机制等核心设计选择的独立贡献均未量化
2. **未做与替代搜索机制的对比**：虽然论文声称"在同一harness内比较搜索驱动"，但正文未展示具体对比实验数据
3. **搜索代理单一**：只使用Claude Opus 4.8，未评估不同LLM或非LLM搜索策略在同一验证框架下的表现
4. **无预算敏感性**：12小时/内核的预算选择未做变化分析；最优时间—收益平衡点未知
5. **无门控参数敏感性**：提交门控的超参数（ϵ=0.002, k=0.85, s_floor=1.0）的选取依据和鲁棒性未讨论
6. **等价性验证本身的强度未量化**：θ=0.9999和τ=10⁻³的阈值选取理由不够清晰；对某些宽松场景阈值可能过严或过宽

### 潜在偏差风险
1. **选样偏差风险**：KernelBench选30个算子、AITer仅保留4个代码对象，可能有意或无意偏向头部空间较大的内核；论文未说明未选内核的结果
2. **"非1.00倍不可验证"的排列效应**：尽管做了源码级预优化，预优化轮次可能在某些算子产生了"尚未完全收敛"的基线，为汇编级优化留出额外空间；在已极度优化的生产库上表现较温和（多个内核回到1.0倍附近）
3. **生产内核选择偏差**：AITer和Triton各自只选4个内核，代表性有限
4. **时钟不可锁定**：论文承认共享硬件无法锁时钟，依赖大启动配置和中位数来压制噪声；不同共享环境下的结果可重复性需要进一步验证
5. **单厂商生态验证**：方法整体架构宣称"architecture-agnostic"，但实验完全在AMD生态内，缺少对NVIDIA或其他GPU平台的验证
