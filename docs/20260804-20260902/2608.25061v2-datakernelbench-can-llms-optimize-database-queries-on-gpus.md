## 摘要
GPU越来越多地加速数据库系统，但特定查询的峰值性能通常仍依赖于手工编写的内核。现有的LLM内核基准测试聚焦于机器学习算子，未覆盖不规则、异构、数据移动密集的数据库风格算子。我们推出了DataKernelBench，将SQL转换为经过验证的PyTorch TorchPlan程序，并评估LLM通过执行引导修复，在CUDA或Triton中优化核心张量受限片段或完整查询的能力。在使用H100 GPU的TPC-H SF10上，针对十个专有及开放权重模型，最强的完整查询CUDA配置实现了相对TorchPlan基线2.11倍的加速，且完全通过。我们发现，性能更高的实现通常采用内核融合和执行策略变更，更强的模型从完整查询特化中获益最多，并且工作负载上下文比硬件上下文更重要。为处理大于GPU内存的数据，我们通过Dask-cuDF扩展TorchPlan，实现在四个H100 GPU上对TPC-H SF100进行按需分区加载，取得了2.54倍的加速。项目页面：https://kerneldf.github.io/datakernelbench

## 速览
**TLDR**：数据库GPU内核优化与机器学习算子优化不同，现有LLM基准并未覆盖这类不规则、数据移动密集的查询负荷。本文通过DataKernelBench将SQL化为可执行的TorchPlan程序，并让十个专有或开源模型采用CUDA/Triton改写核心片段或完整查询，经执行反馈自动修复。在H100上以TPC-H SF10测试，最佳的全查询CUDA方案相对TorchPlan加速2.11倍且全部通过；对超显存规模扩展到四块H100和SF100，仍达到2.54倍提速。该研究显示融合与执行策略调整是关键，强模型受益于全查询特化，并首度建立数据库查询风格内核的LLM优化基准。 \
**Motivation**：当前缺少面向数据库GPU查询内核的LLM优化基准，已有工作多基于机器学习算子。 \
**Method**：将SQL转换为验证过的PyTorch TorchPlan，让LLM用CUDA或Triton优化核心片段或全查询并依据执行结果修复。 \
**Result**：在TPC-H SF10上，最优的CUDA全查询方案比TorchPlan快2.11倍且通过全部测试；扩展至四卡后仍取得2.54倍速度提升。 \
**Conclusion**：证明融合与执行策略调整是关键，强模型更受益于全查询特化，开创了LLM数据库查询优化基准。

## Abstract
GPUs increasingly accelerate database systems, but query-specific peak performance still often relies on hand-written kernels. Existing LLM kernel benchmarks focus on machine learning operators, leaving irregular, heterogeneous, data-movement-heavy database-style operators untested. We introduce DataKernelBench, which translates SQL into validated PyTorch TorchPlan programs and evaluates LLMs that optimize either the core tensor-bounded snippet or the full query in CUDA or Triton through execution-guided repair. Across ten proprietary and open-weight models on TPC-H SF10 with an H100 GPU, the strongest full-query CUDA configuration achieves $2.11\times$ speedup over the TorchPlan baseline at full pass rate. We find that higher-performing implementations commonly use kernel fusion and execution-strategy changes, stronger models benefit most from full-query specialization, and workload context matters more than hardware context. To handle data larger than GPU memory, we extend TorchPlan with Dask-cuDF for on-demand partition loading on TPC-H SF100 with four H100 GPUs, achieving $2.54\times$ speedup. # DataKernelBench：LLM 能否在 GPU 上优化数据库查询？

## 1. 核心问题与研究动机

**背景与问题缺口：**
- GPU 正越来越多地用于加速数据库分析工作负载（大规模扫描、谓词求值、连接、聚合等），但查询级峰值性能仍严重依赖**手工编写的内核**，成本高、维护难。
- 现有 LLM 内核生成基准（KernelBench、TritonBench、MultiKernelBench）只覆盖**机器学习算子**——稠密、规则、同构的张量计算，无法代表数据库风格负载中**不规则访存、异构算子组合、数据移动密集、数据依赖控制流**等特征。
- 由此产生的核心问题：**既然 SQL 可表达为张量程序（TQP 范式），最强代码 LLM 能否合成超越通用编译器（如 torch.compile）的专用 GPU 内核？**

**研究意义：**
- 面向"定期报表、仪表盘刷新"等高频重复查询，查询可被定制优化；判断 LLM 能否在已有张量查询管线中注入"定制内核"，以缩小通用编译与手写内核间的性能差距。

## 2. 方法论

**总体流程：SQL → TorchPlan（验证过的中间表示）→ LLM 注入 CUDA/Triton 内核 → 执行引导修复（execution-guided repair）。**

**TorchPlan 设计：**
- 每个查询被转化为一个可执行 PyTorch 张量程序，先由 DuckDB 差分验证，再由 torch.compile 作为基线执行。
- 两函数拆分：
  - `run_query`：处理 cuDF 表访问、连接、投影、参数解析与输出格式化；
  - `_query_core`：张量密集型热路径，运行在对齐的 1D GPU 张量上。
- 两个优化层级：
  - **core**：只允许改 `_query_core` 及私有辅助函数（接近 ML 内核基准的任务形态）；
  - **full**：可重写整个内部实现，但必须保持外部 `run_query` API。
- 两种编程接口：**Triton** 与 **CUDA**。

**提示词设计：**
- 六个模块化 Markdown 块：BASE（任务约束+参考代码+SQL）、LEVEL（优化范围）、FRAMEWORK（框架指导+示例）、GPU、ENV（运行环境）、DATA（表名、数据类型、行数、内存占用）。
- 模块化设计支持对硬件/工作负载上下文的受控消融。

**正确性判定：**
- 与基线 TorchPlan 在 SF10 固定数据上比较，按层级报告不匹配：形状 → 列名/顺序 → 行数 → 单元格值。
- 非浮点列必须完全一致；浮点列用 `numpy.isclose`，float32 用 atol=rtol=1e-4，float64 用 1e-6。
- 失败信息作为修复反馈回灌给模型。

**速度与接受标准：**
- 单独计时前先丢弃热身/编译运行；speedup = Tbase/Tcand（中位数之比）。
- 接受条件：功能正确 **且** speedup ≥ smin=1.05（默认）；否则按回退到 TorchPlan 计时。
- 关键默认参数：Rmax=10 轮修复、Nwarmup=2、Ntimed=5、熔断上限 `max(Tmin, Mwarmup·Tbase)`（Tmin=1 分钟），单次计时上限 Mtimed·Tbase（3 倍），总时间上限 Twall=15 分钟。

**超内存扩展：**
- 将完整加载的 cuDF 表改为 **Dask-cuDF 分区按需加载**，`map_partitions` 配合 `_process_partition` 把分区张量化进 `_query_core`，实现跨多 GPU 的分布式执行。

## 3. 实验设计

**基准与场景：**
- 主评测：**TPC-H SF10**（22 条分析查询、8 张表、约 10GB），NVIDIA H100 80GB 单卡。
- 扩展验证（概念证明）：**TPC-H SF100（>GPU 内存）**，4×H100、Dask-cuDF、10GB 分块。
- 数据用 DuckDB tpch 扩展生成，含参考输出。

**对比模型（10 个）：**
- 专有：GPT-5.5、Claude Opus 4.7、Claude Sonnet 4.6、Claude Haiku 4.5、Gemini 3.1 Pro。
- 开放权重：Qwen3.5-397B-A17B、GPT-OSS-120B、DeepSeek-V4-Flash、MiniMax-M2.5、Devstral-2-123B。

**组合规模：** 10 模型 × 2 框架 × 2 层级 = 40 个"模型–框架–层级"配置；每个配置跑全部 22 条查询。

**对比基线：**
- 主基线：TorchPlan + torch.compile（TC），另报告 TorchPlan eager；
- 外部系统：Sirius（GPU 数据库）、DuckDB（CPU）。

**消融/补充实验：**
- full vs. core 优化范围（按 Top-5/Bottom-5 模型分层）；
- 提示词消融（去掉 GPU 硬件上下文 vs. 去掉 DATA 工作负载上下文）；
- TorchPlan 生成器敏感性（Claude Opus 4.7 vs. GPT-5.5 生成的 TorchPlan）；
- 额外正确性验证：开源审计（semantic_match / no_cheating）+ 留出集测试（SF1 + 扰动 SF10：数值 ±30% 抖动、日期 ±30 天偏移）；
- Multi-GPU 扩展（1→4 GPU 缩放）；
- 瓶颈点覆盖（choke-point coverage）与加速比相关性分析。

## 4. 资源与算力

- **GPU 环境**：NVIDIA H100 SXM5 80GB HBM3（Hopper GH100，132 SMs，16896 CUDA 核心，528 第 4 代 Tensor Core，3.35 TB/s 带宽，50MB L2）；SF100 实验使用 4 张 H100。

**数量层面：**
- 主榜单覆盖 10 模型 × 2 框架 × 2 层级 × 22 查询，共 880 条生成轨迹，体量可观；

**充分性与公平性：**
- 优点：所有生成模块共用同一批固定且验证过的 TorchPlan，正确性与计时口径统一；失败/未达标查询按回退到 TC 计时，避免了选择性报告；token 成本、轮数等"生成开销"被显式纳入比较。

  - 只使用 **TPC-H 一个工作负载**，缺少其它分析基准或真实查询负载；
